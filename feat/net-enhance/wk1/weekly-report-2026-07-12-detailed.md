# StarryOS 网络栈优化周报（2026-07-11）

## 本周工作进展

### 一、网络统计字节计数机制改进

#### 1. eBPF 方案探索与调整

回退了完全非侵入式的 eBPF 监测方案，目标是通过 kprobe/kretprobe 机制在不修改内核代码的情况下统计网络收发字节数。然而在实际实现过程中遇到了以下技术障碍：

- **kretprobe sret ABI 限制**：函数返回值在 kretprobe 触发时位于 `RAX` 寄存器而非 `RDI`，导致字节计数为零。修复此问题后发现 eBPF 加载器存在符号过度匹配问题（匹配到 19 个符号），需要进行精确的符号过滤。

- **内核迭代适配成本**：考虑到 StarryOS 正处于快速迭代阶段，完全依赖函数符号的 eBPF 探针可能因内核重构而失效，维护成本较高。

- **Linux 实现参考**：研究发现 Linux 本身的网络统计也是基于内核已有的统计字段（如设备驱动层或协议栈层的计数器），而非完全依赖 eBPF 动态插桩。

基于以上分析，暂时搁置了纯 eBPF 方案，转而采用在内核协议栈关键路径埋点统计的方式，且对齐 Linux。

#### 2. 统计粒度调整：从 L3 到 L2

原实现在 socket 层统计返回的字节数，这对应于 L3（IP 层）或更高层的数据负载，与 Linux `/proc/net/dev` 的 L2（以太网帧）统计语义不一致。做了以下改进：

- **统计位置下移**：将统计点从 socket 返回值改为 smoltcp 物理层（phy layer），在 `Device::send()` 和 `Device::recv()` 处统计完整的 L2 帧长度。

- **驱动层适配**：修改网络设备驱动（`ax-net`）的 `send` 和 `recv` 接口，使其返回实际发送/接收的 L2 帧长度，包含以太网头部（14 字节）、IP 头部、传输层头部及数据负载。

- **语义对齐验证**：通过对比测试确认 StarryOS 的 `/proc/net/dev` 字节计数与 Linux 在相同网络负载下的统计结果基本一致，符合 L2 帧统计的预期。

### 二、文档完善与测试验证

- **eBPF 限制文档**：详细记录了 kretprobe sret ABI 的技术限制及解决方案，为后续开发者提供参考。

- **net-bench 文档更新**：修正了测试套件中过时和不准确的描述，确保文档与实际实现保持一致。

- **测试覆盖补充**：针对字节计数修复增加了端到端验证，确保在真实网络负载下统计数据的准确性。

## 下周工作计划

### 一、网络测试套件完善

在深入分析网络性能测试的最佳实践后，发现当前 net-bench 作为端到端性能基线测试工具已较为完整，但作为性能优化的分析工具存在明显不足：只能发现"系统慢"，但无法回答"为什么慢"和"慢在哪里"。因此下周将重点补充测试套件的可观测性能力。

#### 1. 应用层统计增强

**目标**：补充应用层和多层次的网络统计，便于分析协议开销和定位问题。

**具体工作**：

- **应用层有效负载统计**：在 socket 层补充应用可见字节数（纯数据负载，不含协议头部）的统计，量化协议开销占比。

- **分层统计对比**：同时提供 L2（以太网帧）、L3（IP 包）、L4（TCP/UDP 段）和应用层的字节计数，构建完整的网络栈开销分析视图。例如：
  ```
  L2 total: 10.24 GB
  L3 (IP): 10.10 GB (1.4% Ethernet overhead)
  L4 (TCP): 9.85 GB (2.5% IP overhead)
  L7 (app): 9.20 GB (6.6% TCP overhead)
  ```

- **统计维度扩展**：补充 `/proc/net/dev` 的 packets（包计数）、errors（错误计数）、drops（丢包计数）等维度，完全对齐 Linux 语义。这是判断丢包位置的关键指标。

#### 2. 内核可观测性建设（关键）

**问题背景**：当前测试套件以用户态监测为主，缺乏内核态的性能分析能力。这导致：
- 无法定位内核内部瓶颈（锁竞争、中断处理、软中断、DMA 等待）
- 无法识别 CPU 热点函数和 cache miss 热点
- 无法跟踪数据包在协议栈各层的延迟分布
- 优化工作只能"盲目尝试"，缺乏数据驱动

**关键性**：如果在第二阶段（功能验证）不建立内核可观测性基础设施，第三阶段（性能优化）将陷入"无工具可用"的困境。

**优先级 P0（必须完成）**：

- **perf stat 集成**：将 CPU 效率分析集成到 `run.sh` 标准流程，每次测试自动报告：
  - `cycles/byte`：处理每字节数据的 CPU 周期数（越低越好）
  - `IPC`（Instructions Per Cycle）：CPU 执行效率（越高越好）
  - `cache-miss-rate`：缓存未命中率（越低越好）
  
  这是最低成本获得内核性能可见性的方式，能立即识别 CPU 效率差距。

- **协议栈统计接口**：实现 `/proc/net/snmp` 等价接口，监测协议栈健康度：
  - TCP 重传率（`TcpRetransSegs`）
  - TCP 乱序率（`TcpInOfOrder`）
  - UDP 丢包率（`UdpInErrors`）
  - IP 分片统计（`IpFragOKs`、`IpFragFails`）
  
  这些指标能判断性能问题是否由协议栈异常导致。

**优先级 P1（尽量完成）**：

- **eBPF 数据包路径跟踪**：开发 bpftrace 脚本，跟踪数据包在协议栈各层的延迟分布（virtio ring → L2 → IP → TCP → socket），精确定位瓶颈层次。

- **CPU 热点分析**：集成 flame graph 生成脚本，直观展示 CPU 热点函数。

**预期成果**：
- 修改后的 `run.sh`，集成 perf stat 并在结果中展示 CPU 效率
- StarryOS 中实现的 `/proc/net/snmp` 接口
- 完整的 `/proc/net/dev` 实现（补充 packets/errors/drops）
- eBPF 跟踪脚本库（如时间允许）
