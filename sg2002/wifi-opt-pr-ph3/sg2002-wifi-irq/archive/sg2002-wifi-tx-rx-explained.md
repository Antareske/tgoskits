# 为什么 SG2002 WiFi 下载 12Mbps、上传只有 0.8Mbps？

## 先看现象

用 iperf3 测了一组数据，结果很不对称：

| 方向 | 吞吐量 | 稳定性 |
|------|--------|--------|
| **下载**（手机→板子） | **12 Mbps** | 非常稳定，每秒 1.4MB 左右 |
| **上传**（板子→手机） | **0.85 Mbps** | 一卡一卡的，128KB 发一秒、停一秒 |

下载比上传快了约 **14 倍**。而且这不是新问题——历史上同样的硬件，用"忙等自旋"方案（`yield_now()` 不停检查硬件状态），上传曾达到过 **~10 Mbps**。当前 0.85 Mbps 比历史上 10 Mbps 还慢了 **12 倍**。

为什么同一个 WiFi 模组，两个方向差这么多？为什么旧方案反而更快？

## 一张图看懂数据流向

先理解数据怎么从 WiFi 芯片传到 CPU、又怎么从 CPU 传到 WiFi 芯片。

```
┌─────────────────────────────────────────────────────┐
│                    SG2002 CPU                        │
│                                                      │
│  跑着:  TCP/IP 协议栈  +  WiFi 驱动  +  iperf3       │
│                                                      │
│  和 WiFi 模组通信用的是一种叫 SDIO 的接口              │
│  (可以理解成通过 4 根数据线 + 1 根时钟线               │
│   按寄存器地址读写数据)                                │
└─────────────────────────────────────────────────────┘
         │                          ▲
         │ SDIO 写                  │ SDIO 读
         │ (CPU → 模组)             │ (模组 → CPU)
         ▼                          │
┌─────────────────────────────────────────────────────┐
│              aic8800 WiFi 模组                       │
│                                                      │
│  里面有:  firmware (一个小操作系统)                    │
│          + TX buffer (发送缓冲区)                     │
│          + RX buffer (接收缓冲区)                     │
│          + 无线电收发器                               │
└─────────────────────────────────────────────────────┘
         │                          ▲
         │ 无线电发射                │ 无线电接收
         ▼                          │
     [ 手机 / 测试客户端 ]
```

**关键事实**：CPU 不能直接把数据"发射"出去，也不能直接从空中"抓"数据。所有数据必须经过 WiFi 模组。CPU 通过 SDIO 接口往模组的寄存器读写数据，模组负责把这些数据变成无线电波（或反过来）。

## 下载为什么快？（12 Mbps，稳定）

下载的过程是**被动接收**——数据自己送上门：

```
手机发送数据 (无线电波)
        │
        ▼
WiFi 模组收到，存进 RX buffer
        │
        │  模组拉一根信号线 (CARD_INT) 告诉 CPU:
        │  "喂，我有数据，快来读！"
        ▼
CPU 被中断唤醒 → 从模组 RX buffer 读数据
        │
        ▼
数据交给 TCP/IP 栈 → iperf3 收下
        │
        ▼
CPU 再等下一次 CARD_INT...
```

这个过程的特点是：
- **模组主动通知**：数据到了就拉中断，CPU 立刻响应
- **CPU 角色是被动的**：来一批读一批，读完就等下一批
- **不会积压**：CPU 读的速度（12 Mbps）够快，RX buffer 不会满

这就像快递员送货上门——有人按门铃你就开门拿，拿了就完事，不会在门口堆包裹。

## 上传为什么慢？（0.85 Mbps，一卡一卡）

上传的过程是**主动推送**——CPU 要把数据硬塞给模组：

```
iperf3 有 128KB 数据要发送
        │
        ▼
TCP/IP 栈打包 → WiFi 驱动
        │
        │  驱动通过 SDIO 把数据写进模组 TX buffer
        │  (每次写之前要先"问一下"模组准备好了没有)
        ▼
模组 TX buffer 满了！(容量大约 128KB)
        │
        │  流控机制触发：驱动被"卡住"，不能继续写
        │
        ▼
模组慢慢把 TX buffer 里的数据发射出去
(通过无线电发到手机)
        │
        │  这段时间，CPU 在等待...
        │  大约等 1~2 秒才排空
        ▼
TX buffer 排空了，流控释放
        │
        ▼
CPU 又可以写下一批数据...
```

这个过程的特点是：
- **CPU 主动推**：模组不主动通知"我准备好了"，CPU 得一次次问
- **buffer 有限**：模组只有 ~128KB TX buffer
- **灌满就卡住**：CPU 写数据比模组发射快，很快 buffer 就满了
- **排空很慢**：模组发射速度受限于无线链路，1~2 秒才能排空

这就像一个漏斗——你猛灌一瓢水，漏斗口太细，水慢慢流。你只能等漏斗里的水流完了才能再灌。灌的那一下很快（约 1 秒 128KB），等待的时间很长（1~2 秒）。

所以 iperf3 日志里看到的现象是：

```
发 128KB (1 秒) → 发 0 (卡住 1~2 秒) → 发 128KB → 又卡住...
```

平均下来就只有 0.85 Mbps 了。

## 10ms 睡眠是什么？为什么忙等不是答案？

### 当前代码的等待机制

`poll_int_status` 等硬件标志位时，分两个阶段：

```
Phase 1: 快速自旋 1000 次 (~50µs)
  └→ 绝大多数情况在此命中。BUF_WR_READY 在 25MHz SDIO 上数据到达只需 ~41µs，
     Phase 1 完全覆盖。

Phase 2: 20 次兜底（仅 Phase 1 没命中才进入）
  ├─ XFER_COMPLETE: block_timeout(10ms) → ISR 中断唤醒，几乎不花时间
  └─ 其他位:        delay_ms(10ms)    → 纯睡眠，10ms 后醒来再查
```

**Phase 2 的 10ms 是安全网——正常情况不该走到这里。** BUF_WR_READY 是写一个 512B 块到 SDIO FIFO 后的等待，硬件在几十微秒内就该就绪。Phase 1 的 50µs 足够覆盖。如果频繁掉入 Phase 2，说明 Phase 1 窗口不够——那是另一个问题，不该用"把安全网改成死循环"来掩盖。

### 那旧方案（全部自旋）为什么有 10 Mbps？

Part 1 的 ~10 Mbps 是**一整套优化的总和**，不是单靠自旋：

| 优化项 | Part 1 分支 | 当前分支 |
|--------|-----------|---------|
| SDIO 时钟 | **50MHz** | 25MHz |
| HT 对齐修复 | ✅ | ❌ |
| PHY delay 配置 | ✅ | ❌ |
| 流控重试 | 1 次 + yield | 50 次 + yield |
| 等待方式 | yield_now 自旋 | XFER IRQ + 其余 10ms 兜底 |

**10 Mbps 来自 50MHz SDIO + HT 对齐 + 流控优化 + PHY 配置。** 把差距全部归因于自旋 vs 睡眠，是因果倒置。

### 忙等为什么不是最优解？

忙等的本质：**用 CPU 100% 空转换延迟**。

```
忙等期间 CPU 做的事:
  读寄存器 → 没好 → 读寄存器 → 没好 → ...
     ↑
   TCP 协议栈、WiFi RX、其他任务全部饿死
```

在单核系统上，这意味着等硬件时 TCP 协议栈跑不了——该处理的 ACK 堆积、该收的 RX 数据没人读。

中断驱动才是正确方向：**XFER_COMPLETE 中断让 CPU 在等传输完成时可以去处理 TCP 协议栈、收 RX 数据、调度其他任务。** 这正是本次改动实现的东西，也是 RX 能达到 12 Mbps 的原因——CARD_INT 中断通路和 XFER_COMPLETE 中断唤醒让 CPU 在 I/O 等待期间能高效调度。

### 那么 0.85 Mbps 的真正原因是什么？

可能性排序：

1. **缺失 Part 1/2 优化**：50MHz → 25MHz SDIO 时钟减半，HT 对齐和 PHY delay 修复缺失——这些是已确认有效的优化，影响远比 10ms 安全网大
2. **Firmware TX buffer 流控反压**：128KB buffer 满后等 1~2 秒排空，这是 burst-gap 模式的直接原因
3. **Phase 2 兜底是否被频繁触发**：尚无测量数据。如果 Phase 1 命中率正常（>99%），10ms 睡眠几乎不触发，不是瓶颈；如果命中率异常，需要查的是 Phase 1 的 50µs 窗口为何不够——可能是 SDIO 时钟低、总线竞争、或固件响应慢

**正确的方向**：把 Part 1/2 的优化（50MHz、HT 对齐、流控修复）合入当前分支→板上打点确认 Phase 1 vs Phase 2 实际命中率→根据数据决定下一步。

## 那为什么下载不需要等？

因为下载时 CPU 是**消费者**——模组 buffer 里的数据被 CPU 读走才腾出空间，而 CPU 读的速度够快（12 Mbps），buffer 一直在被消费，不会积压到触发流控。

上传时 CPU 是**生产者**——模组 buffer 里的数据要等无线电发射才能腾出空间，而发射速度受限于无线链路本身的带宽。SDIO 接口（PIO 模式，即 CPU 一条指令一个字的读写）写满 buffer 的速度远快于模组发射的速度。

**本质区别**：

```
下载: WiFi 模组 → 无线电 → CPU（拉模式）
      模组收到多少，CPU 读走多少

上传: CPU → SDIO → WiFi 模组 → 无线电（推模式）
      CPU 写得快，模组发得慢，中间 buffer 满了就反压
```

## 怎么改进？

基于以上分析，优先级排序：

1. **合入 Part 1/2 已验证的优化**：50MHz SDIO、HT 对齐修复、PHY delay 配置、流控重试优化——这些是已验证有效且独立的改进，不依赖等待策略的选择
2. **板上打点确认 Phase 1/2 命中率**：在 `poll_int_status` 中加入计数器，判断 BUF_WR_READY 是否频繁掉入 Phase 2。如果命中率 >99%，10ms 安全网不是瓶颈；如果异常，根据数据调整 Phase 1 窗口
3. **中长期**：启用 SDIO DMA、调大 firmware TX buffer、消除冗余拷贝

**不要做的是**：把 Phase 2 安全网改回忙等自旋。那是走回头路——用 CPU 效率换延迟，且掩盖了真正的问题（SDIO 时钟、固件响应等）。

## 总结

| | 下载（12 Mbps） | 上传（0.85 Mbps） | 历史上传（10 Mbps） |
|---|---|---|---|
| **数据方向** | 被动收 | 主动推 | 主动推 |
| **SDIO 时钟** | 25MHz | 25MHz | **50MHz** + PHY 优化 |
| **等待方式** | CARD_INT 中断 | IRQ + 10ms 安全网 | 全部自旋 |
| **瓶颈** | — | 缺失 Part 1/2 优化 + buffer 流控 | buffer 流控 |

核心认知：
- **中断驱动是正确方向**：XFER_COMPLETE 硬件唤醒让 CPU 在等待期间能处理 TCP/RX，不牺牲 CPU 效率
- **10ms 睡眠是安全网**，正常不应频繁触发。如果触发——查 Phase 1 为什么不够，而非把安全网改成死循环
- **忙等不是答案**：它用 100% CPU 换延迟，掩盖了真正的硬件/配置问题
