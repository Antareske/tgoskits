## 2. 目标与基线

AIC8800D80（SDIO 4-bit，总线实测 23.4375 MHz ≈ 11.72 MB/s）在 SG2002 / LicheeRV Nano 上的数据面吞吐优化。
聚合落地前的上行基线约 8.4 Mbps；当前工作点板端发送约 36 Mbps、接收约 31~34 Mbps。

## 3. 阶段划分与当前位置

阶段边界由 OCR 审查划分，各阶段结论见 `aic8800-optimization-tracker.md` 的「阶段索引」：

- **第一阶段**：credit 本地记账、事务探针、TX 聚合（上行 8.42 → 18.7~19.5 Mbps）、RX 扫描实验。
- **第二阶段**（边界 `ocr-review-20260927.md`）：普通数据 confirmation、typed telemetry、D80 HT40/SGI 与 VHT/HE 能力、速率遥测。
- **第三阶段**（边界 `ocr-review-20260928-bottleneck-round1.md`、首轮进展审查 `ocr-review-20260928-phase3.md`）：
  观测裁决轮、聚合上界轮（K=4→32，有效）、发送环对照轮（环 32→64，无效）、credit 等待轮。
  结论：瓶颈形状是「每笔固定开销（445~604 µs，与承载字节基本无关）+ 事务间空档」决定事务率，**不是每字节速率**。
- **第四阶段（进行中）**：把「CPU 的活」与「总线的活」对齐。方案见 `aic8800-async-optimization-plan.md` §7。

## 4. 已确立、可继续引用的结论

- 写往返按设备中断切成三段：`pre`（设备+总线+命令，含主机侧成形）／`isr`（实测中位 2 µs）／`post`。
  **`post` 段（实测 396~415 µs）到"我们的代码开始跑"为止，即全部是唤醒/调度延迟**，不含任何收尾工作（此口径 2026-09-28 更正）。
- 执行器 `handoff`（中断 → 执行器恢复，239~346 µs）与 `post` 量的是同一段，不是互补的两块。
- 写跨度（`emitted()` → `completed()`）**不含**成形/准备（发生在交接之前），因此不能用来读准备路径的收益。
- 接收侧：实测批上限 63 块（31.5 KiB）、`65+` 桶零样本，refill 平均约 8 ms；重武装时卡中断已 asserted 约 2%。
- 空口：`mpdu/ampdu` 有流量样本中位 8.0、上四分位 15.0、最大 40.0，与每笔交出的约 20 帧同量级。
- 单核：启动日志 `smp = 1`，设备树只有一个 `cpu@0`。重叠只能协作式，不存在"另一个核做准备"。

## 5. 已被证否、不应再走的方向

固件/空口限制 TX（证据链由两个窗口拼成且含恒等式）、RX 受限在交付节奏（分子口径不全）、上游供帧不足（饱和窗口约 7%）、
SDIO 时钟（翻倍上界 <1.6×）、环深（§2.25）、`ack` 计数比值（口径未定，§2.26）。
「更大的 K」曾被列入此项，其判据已撤回，**该方向回到开放**。

## 6. 第四阶段已完成的调查与改动

### 6.1 发送路径的主机侧成本（读代码 + 板测计数）

一笔写的 payload 在主机侧被完整搬运五遍：

| # | 位置 | 内容 |
| --- | --- | --- |
| 1 | `rdif/owner/output.rs` `take_tx_frame` | 帧坐着池化 DMA 缓冲来，进门即 `to_vec()` 成普通 `Vec` |
| 2 | `protocol.rs` `ethernet_tx_frame` | 分配 + 清零 + 拷贝（每帧一次） |
| 3 | `device/owner.rs` `append_frame` | 再拷进聚合缓冲 |
| 4 | `device/owner.rs` `wire_bytes()` | 整篇分配 + 拷贝，**每个状态机步都重来** |
| 5 | `rdif/owner/operation.rs` | `CpuDmaBuffer::new_zero`（分配+清零）+ `copy_from_slice_cpu`，每笔写一次；完成时 `drop` 释放 |

两道挡住"零拷贝到 DMA"的墙：**分层**（`device/` 拿不到 `DeviceDma`/`SdioCard`，要池须从 rdif 注入并拆
`SdioRequestKind` 的 `Clone/Eq` 派生）；**所有权**（聚合缓冲不能 `mem::take` 进请求——`discard_pending_transmit`
能在提交前丢掉请求，那笔写之后还要再成形）。

### 6.2 本轮改动（未提交）

- 旋钮 `aic,tx-prep-direct`（默认 0）：直接准备路径，消掉 #2/#3/#4 的每帧分配、追加拷贝与按步全量拷贝，交给请求的一份改走可复用 scratch。
- 旋钮 `aic,tx-credit-wait-us`（默认 300 µs，0 = 完全不进等待分支）。
- 探针（零行为）：`prep frames n/bytes | append bytes | handoff bytes | wire_bytes calls`（确定性计数器）、
  `dma tx alloc n/bytes | release n`、`owner step tx/rx/control n/avg`。

## 9. 本轮实测结论

- **B 臂机制成立（确定性计数器）**：每写建帧分配 13.88 → 0.0001、追加拷贝 18,393 B → 0、`wire_bytes` 调用 1.0014 → 0.0001；交接字节不变。
  非零的那一次是内部生命周期写（不走直接路径）。
- **写跨度上看不出变化**——该尺子不含成形/准备，结构上量不到；不以它判收益。
- **credit 等待**：效果确认（关掉后最薄 3–6 桶写笔占比 4.17% → 16.91%），代价确认（等待合计多 1.155 s，约占会话 0.5%），
  **收益不可判**（A 臂全程受 PC 高负载影响，C 臂干净；thin 与 reserve 两类等待共用同一计数器，无法分项）。
- **吞吐无可归因差异**：三臂板端发送中位均为 36.7 Mbps。
- **DMA 缓冲形状确认**：分配 6070 次 : 释放 6070 次（1:1），拷入 84.1 MB，除以 5574 笔写 = 15.1 KB/笔，自洽；
  其中 496 次（8.9%）来自邮箱/控制写（遥测同样每笔分配一次）。**时间仍未知**——按每次搬运 15 KB 计，量级远小于唤醒延迟的 396 µs/笔。

## 10. 下一步

1. **测 `attrib` 镜像**：看 `owner step tx avg` 与 396 µs 的对比。
   - 若收尾工作很小 → 396 µs 基本全是唤醒路径，火力转向那里（机制候选：同权重 Fair 线程的条件抢占被拒）；
   - 若很大 → 收尾内有实活，DMA 缓冲池与双槽准备就有依据。
2. 之后再谈「双槽聚合 + 分片准备」（在飞的 2.5 ms 里成形下一笔）与 DMA 缓冲池：
   池能同时消掉 pre 段的分配+拷贝与收尾段的释放，但**其收益目前只有次数依据、没有时间依据**。
3. 遗留可选项：`aic,tx-prep-direct` / `aic,tx-credit-wait-us` 两个旋钮的默认值是否改、探针何时裁剪（开 PR 前必须移除）。

## 12. 读数口径纪律（硬性）

每个数落进文档前先登记六项：总体、加权方式、范围（单窗口/活跃窗口集合/整段）、时间戳粒度、计数器是否跨提交可比、选样规则。

禁止：跨口径相减或相除；拿最大值配平均值；用按构造成立的量作验证（分段之和等于总跨度、占比之和为 100%）；
取"最后 N 个""最忙几个"却不给全分布；把单窗口当整段；用跨会话吞吐作收益证据（只作方向）。

**首选确定性计数器**（分配次数、调用次数、拷贝字节数）——不受加权与选样影响。

已知口径陷阱：每字节成本有「按笔加权」与「按字节加权（Σt/ΣB）」两种，同批日志可差 20~30%；
探针 `write credit … bytes=` 是**窗口合计**不是每笔均值；跨会话吞吐不可比。
