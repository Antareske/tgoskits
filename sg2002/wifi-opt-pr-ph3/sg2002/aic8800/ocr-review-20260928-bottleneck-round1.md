## 一、本轮问题的回答：瓶颈在哪

### 结论（三方质证后收敛，每点均有 ≥2 个独立实例的读数支持）

**瓶颈的形状是「每笔 SDIO 事务的固定开销 + 事务间空档」决定事务率，而不是每字节速率；而每笔能装多少字节被
`packets = 4`（6144 B）钉死——两者相乘构成上行的算术天花板。**

拆开讲：

1. **每字节不是瓶颈。** 两个方向的**边际**成本相同：写 **9.11~10.43 MB/s**、读 **9.88 MB/s**；
   换算成斜率是 **85.3 ns/B**，正好是 23.4375 MHz × 4 bit = 11.72 MB/s 的铭牌速率。
   原先"写 5.7 MB/s 对读 9.5 MB/s（差 1.7×）"是**固定项摊薄程度不同**造成的假象（写每笔 6144 B、固定项 516 µs；读每笔 21246 B、固定项 463 µs）——
   提出该论据的一方在质证中自己撤回了它。
2. **固定项真实存在且与承载字节基本无关**：对 771 个上行窗做窗内回归，**0/771 出现负截距**，中位 **445 µs**（IQR 366–550）；
   对全量 2169 个分桶窗口（1,033,731 笔写）的独立拟合给出 `span = 480 + 0.096·B`，同时命中均值（预测 5.05 MB/s，实测 5.052）与观测上界（1154 个窗口无一超 5.72 MB/s）。
   例外是 1 块桶（147 µs，占 15% 的写）——"与帧数无关"过强，实际是"在 2 块以上几乎不随字节缩放"。
3. **固定项里至少一半已实测是主机侧**：`owner 20.65% + poll 3.33% + park_sw 12.50% = 36.5% 墙钟 / 360 µs 每笔写`（1447 个 executor 窗口，Σdt≈3010 s）。
   其中 `handoff`（中断→执行器恢复，239~346 µs/笔）**按构造 100% 是内核软件时间**（两端时间戳都在软件里，区间内无总线操作）。
4. **`aic,tx-aggregation` 是真旋钮**：credit **并不系统性夹取聚合深度**——`credit max` 中位 **131**、1105/1154 个窗口 ≥31（直接读数），
   `aggregate_limit()` 在 credit ≥34 时不夹；把 credit 均值五等分，`backoff/写` 从 1.649 掉到 0.000（40×）而速率只从 5.21 变 5.07 MB/s（−3%）。
   聚合收益的上调估计为 **1.87×**，与同床对照的 2.1× 同量级。
5. **空口税真实但不可叠加**：09-28 忙会话逐秒 `[wifi-sta-info]` 增量显示首次尝试失败率 **24~28%**（坏姿态 35~40%），
   但它已含在实测读数内，且同床共模（厂商付同样的税仍达 7.1 MB/s）——不能加到天花板上再乘一次。
6. **时钟不是主因**：翻倍时钟的上界在 **1.15×**（窗内口径）到 **1.34~1.56×**（事务层口径）之间，两者都 < 2×。
   它仍是唯一能解释 RX 那 1.61× 的候选，故那次 `debugfs` 读回仍值得做，但**不应作为主攻方向**。

### 仍然未定论的一项

固定项在"**设备反压**（固件不放行/排不出去）"与"**主机侧 park / 中断恢复 / 拷贝**"之间的**最终归属**。
三方一致同意裁决它需要**两条测量，缺一不可**：M1（把每笔写跨度按提交时 credit 分桶）+ M3（SDIO 提交/完成边界时间戳）。

### 对"信息已经足够多"的回答

**足以否证**三条既有结论、给出瓶颈的形状与算术天花板、并定出上面 6 条；**不足以**在"设备 vs 主机"之间定论。
但差的不是"更多测试"，而是两条具体测量——其中 M-K1（打开一个**已注册却从未启用**的 tracepoint）**零代码改动**。

## Blockers

> 本轮的 blocker 定义：**在澄清前不应据此继续投入**的证据链缺陷（不是"不能合入"的代码缺陷）。

### 1. C1 的证据链由两个窗口拼成，且其核心分解是恒等式

- **Location**: 分析文档 §2.18；`drivers/net/aic8800/src/device/probe.rs:260-306,347-361,406-424`
- **Issue**: `period ≡ gap + rtt` 是**定义式分解**（三者用同一批 owner 调用入口时间戳），"周期 64% 是单笔写自身"不含独立信息。
  而提供"64%"的窗口（`tx_writes=1203`）里 credit 均值是 **36.1**、回退占写次数 **4%**；"credit 均值 7.1、回退 225 次/秒"来自**另一个**窗口（`tx_writes=950`）。
  用 A 窗口的"写自身占比"配 B 窗口的"credit 贴地板"推出"写自身 = 固件缓冲排空"，是把两张表拼成一条因果链。
  此外 credit 采样节奏**内生**（只在 `consume_transmit_flow` 采样，`data_plane.rs:604`），同会话 `credit n` 变化 19 倍且与均值强负相关。
- **Why It Matters**: C1 是全分支方向的前提（"TX 侧不再在提交调度上投入，转向 RX 侧"）。**质证中 A 阵营自己把 C1 从"证伪"改判为"未判定"。**
- **Flagged by**: @principal-1, @principal-2, @ephemeral-2 (+ @performance-2 部分)
- **Evidence**: 🔒 由 ≥3 个互不通信的实例独立从原始日志复算得到同一结论。

### 2. C2 的分子口径不全，且"空档被 RX 吃掉"因果倒置

- **Location**: 分析文档 §2.19 的"读占用窗口的比例"行；`device/probe.rs:406-425`（`close_gap`）
- **Issue**: "50% 占空比"的分子只算了 RX **数据**读。把同一窗口的 RX 控制读、credit 读、TX 写计入后，
  **占用是 58.2%~69%**（三个独立实例分别算得 58.2 / 61.5 / 63.0 / 69.0），"空着"只剩 31~42%。
  更关键的是 `gap rx2+` 的 3.4~5.4 ms **不能归给 RX 事务**：`close_gap` 是**事后**按"空档里完成了几笔 RX 事务"分类的，空档越长分到的 RX 越多；
  同窗 RX 事务总时长只有 **95~106 ms**，而归属给它的空档是 **500~746 ms**（80% 不是 RX）。
- **Why It Matters**: C2 是"RX 受限在交付节奏、方向转向 RX 侧"的全部依据；且它会把注意力从 40% 左右的死时间上引开。
- **Flagged by**: @performance-1, @performance-2, @ephemeral-1, @ephemeral-2 (+ @principal-1 作为因果断言证伪)

### 3. "纯上行受上游供帧限制 = 否"被按「计数」关闭，按「时间」并不成立

- **Location**: `device/probe.rs:225-228,415-423`（`supply_nanos` 与 `supply_count` 在同一行打印）；`requirements.md` §2
- **Issue**: 关闭它用的"88% 的写完成时刻帧已在环里等"是**按笔**的计数口径。同一行的**按时间**口径是
  `supply none n=24~26 avg=17755~22134 µs` = **426~575 ms = 窗口的 21%~28.7%**，且占全部空档时间的 **45.9%~59%**。
  同一个计数器在 §2.11（UDP）被读成"瓶颈在驱动之上"，在 §2.18 被读成"不在上游"——**判定阈值从未定义**。
- **Why It Matters**: 这是本轮最可能"被误排除"的候选。TCP 上行里两到三成的窗口时间在等新的上游帧，意味着
  **ack-clocking / 发送窗口 / 板载协议栈**可能与其他因素同量级。A 阵营在质证中主动把该项从"被关闭"升级为"待判"。
- **Flagged by**: @performance-2, @ephemeral-2, @principal-1

## Should Fix

### 1. 把 `packets`（`aic,tx-aggregation`）从 4 提上去——DTB 旋钮，零代码改动

- **Location**: `drivers/net/aic8800/src/device/data_plane.rs:847-853`（`aggregate_limit`）、`device/owner.rs:300-315`、`drivers/ax-driver/src/net/aic8800/fdt.rs:73-92`
- **Issue**: 两个入库 DTB **都没有** `aic,tx-aggregation` / `aic,tx-aggregate-bytes` 属性（已用 `dtc` 核实）⇒ 上板一直跑默认 **4 帧 / 6144 B**；厂商对应 32 帧 / 96 KB。
- **Why It Matters**: 在 ~480 µs 固定项的模型下，每笔字节数是"提交字节/秒"的直接乘数；上调估计 **1.87×**（TX 方向）。
- **Suggestion**: 在一轮里扫 4 / 8 / 16 / 32，并**同时报告 credit 分布**（因为若某些窗口 credit < 34 仍会夹取——`credit max` 中位 131，但确有窗口贴低）。

### 2. 探针口径修正集（读数语义，不裁剪任何探针）

- **Location**: `device/probe.rs`、`net/ax-net/src/queue_runtime/executor/probe.rs`
- **Issue**: ① `credit` 采样内生 → 报告应带"读次数 / 写次数"之比使偏置可见；② `gap` 的 rx 桶改名为"空档期间的 RX 事务数"并注明只描述共现；
  ③ `ChainMiss::Idle`（`prepare_next_transmit` **之后**判定）与 `supply none`（完成时刻采样）不同义，同窗相差 8.6 倍却并列在同一张表；
  ④ 每类成本改用 `Σbytes / Σµs` 而非桶均值（`size <=2k` 桶的均值 1271 µs 高于 `>8k` 桶，样本互相重叠）；
  ⑤ `open_window` 未重置 `last_write_done` / `in_flight`，窗口边界有一个跨界 period/gap；⑥ `probe.rs:123-124` 注释写"issued"而实现是"完成时刻"；
  ⑦ `wait_us` / `poll_us` / `owner_us` 是**均值**而 `waits` / `polls` 是计数，字段名不区分（本轮曾因此误读）。
- **Why It Matters**: 本轮几乎所有的口径争议都出自这几处；它们都是纯报告层面的修正。

### 3. 遥测可用性：把"唯一能回答对端是否给机会"的读数放出来

- **Location**: `device/mailbox.rs:289-306`（打印门键在 `TxRateDescriptor` 上，而它**包含 rssi**）、`lmac.rs:1077-1078,1275`（`retries`）、`:1246-1280`
- **Issue**: ① 逐秒 ack 增量只在"速率描述符恰好变了"时被打出来（当前能还原逐秒序列纯属 rssi 抖动的副作用）；
  ② `retries` 是保护帧组内的 `nRetry:3`（**配置常数**，厂商宿主侧从不读它），被打印在 `txfailed` 旁，极易被读成"观测到 2 次重传"；
  ③ `acknowledge_failed` / `acknowledge_succeeded` 是**寿命累积**计数、原样打印，分析里被当作稳态失败率（"累计 15%" 出自另一会话；本会话逐秒是 20~25%）。
- **Suggestion**: 打印门改为"计数器变化即打印"或每周期打印；`retries` 改名或去掉；报告累积计数时同时给增量。

### 4. 主机侧拷贝链的浪费（**注意：`rdif/owner/operation.rs` 不在本分支 diff 内，属既有代码**）

- **Location**: `drivers/net/aic8800/src/rdif/owner/operation.rs:89-96,114-121,192-193`、`memory/dma-api/src/common.rs:20-31`、`drivers/net/aic8800/src/rx.rs:233`、`device/data_plane.rs:1022`、`rdif/owner/output.rs:250`
- **Issue**: 每笔 RX 事务先对**整块** 21 KiB DMA 缓冲 `new_zero`（逐字节 `write_bytes(0)`），随即被 DMA 全量覆盖——100% 无用的写遍历；
  随后 `alloc::vec![0; length]` 再分配 21 KiB、拷出、逐 MPDU `to_vec()`、`ethernet_from_llc` 再 `vec![...]`、publish 再 `copy_from_slice`：
  **每 21 KiB 过约 5 遍拷贝、约 28 次分配**，且全部串行在关键路径上（单 owner 一笔在飞，无法被重叠）。
- **Why It Matters**: 它是"主机侧 360 µs/笔"里唯一**主机自己可控**的一段；若 M1/M3 判给主机侧，这是第一个要削的点。
- **Suggestion**: 本轮不改代码。候选：读方向改用**非零填**的 DMA 分配；RDIF 环直接持有 DMA 缓冲（零拷贝交付）；或把 `parse_fifo → decapsulate → publish` 合并成"一次读、一次写目的地"。

### 5. 时钟策略的硬编码与单向性需要写明

- **Location**: `drivers/blk/cv181x-sdhci/src/clock.rs:20,29-53`、`platform.rs:8-10,208-212`
- **Issue**: ① `HighSpeed/Sdr25` 一律返回 `25_000_000`，`Sdr50/Sdr104/Ddr50/Hs200` 直接 `Unsupported`；
  ② `clamp_clock` 用 `hz.clamp(min, max)` **只向下夹** ⇒ DTB 的 `max-frequency` **永远无法把速率提上去**；
  ③ `clock.rs:20` 用**未夹取**的 `target_hz` 判 `high_speed`，与随后夹取后的实际频率不一致。
- **Why It Matters**: 运维/后续开发者从 DTB 读到的 `max-frequency = <0x17d7840>` 会以为这是可调杠杆，实际它已触顶——
  这会让"调 DTB 提时钟"成为一条反复被尝试的死路。另一面：若只为可读性，可在 `clock_hz_plan` 上写明"该上限是代码常量、DTB 只能调低"。

## 证伪条件（各阵营自报，供下一轮判读）

- **设备反压成立**：M1 的跨度随 credit 单调上升且差 > 150 µs；或 M3 显示控制器持有 ≥ 85% 的 `park_hw`。
- **主机侧成立**：M1 斜率几乎平坦；且提交延迟 + 中断后处理 ≥ 30% 的跨度。本轮实测的**下界**是：内核软件时间（`handoff`）占 TX 重窗 20.4% 墙钟、`park_sw` 占 12.50% 墙钟。
- **聚合天花板被证伪**：M8 把 K 提到 32 后 TX < 30 Mbps（若 ≥ 45 Mbps 则 TX 归聚合算术）。
- **时钟被彻底关闭**：M7 读到厂商侧 ≤ 25 MHz；或提到实际时钟后 RX < 40 Mbps 且 TX < 35 Mbps。
- **空口被排除**：M4 报 `avg_ampdu_len ≥ 16` 而 credit 仍贴低。

## What's Working Well

- **探针设施的设计水准高于一般调试打印，且本轮全部结论都建立在它之上**：`size blk …` 分桶让"跨度 = 固定项 + 每块传输"的分解不需要任何新测量就能做出来；
  `park_split`（把 park 按最后一个 IRQ 切成传输段与交接段，`executor/probe.rs:106-113`）用极少代码把一个原本不可见的量变成每窗口都有的读数；
  `gap rx0/rx1/rx2+` 分桶、`supply core/ring/none` 分类、`rdif_at_write` 都直接支撑了本轮的关键论证。**不建议裁剪。**
- **`supply core 83%→98%` 这条读数把"主机不缺帧"钉死了**——它是本轮唯一不依赖推断的正面结论。
- **诚实记录负面与自证的工程习惯**：RX defer 的负面结论被完整保留并据此改回默认 0；§2.3 对 `wake` 语义、§2.12 对帧统计口径都做过教科书写法的口径自查；
  §2.20 把 SDIO 时钟从"关闭"降级为"待一次读回定论"（明确指出未定，没有写成"否"）——这是本项目文档里质量最高的单节之一。
- **同床对照的实验设计是对的**：同一天、同一热点、同一块板、四个方向、两栈各取最好轮，并把"姿态不佳时厂商同样塌到 5.35~22.1 Mbps"显式记录下来。
- **`fd80b2b69`**（普通 Ethernet data 用 `hostid=0`，不再逐帧索要固件确认）去掉的是一笔真正的每帧开销，实板 `data_confirmations=0` 已验证。
- **`MM_GET_STA_INFO` 被当作非致命遥测**（遥测失败不打断启动，`a366b59ee` 的收窄）是正确取舍；`me_config_payload` 的六个布尔字段与厂商在本芯片上的**有效**值逐项一致，
  `enum mm_features` 的位序与我们四个常量逐位相等，`mm_get_sta_info_cfm` 的偏移与厂商结构逐偏移相等——这几处经独立核对无缺陷。
- **`kernel-coupling-1` 的附带收窄**：SDHCI 的 100 µs `RegisterPending` 只作用于总线配置请求与 `WaitingInhibit/WaitingBusy` 状态的命令，
  **不是**每笔 CMD52 的普遍税——避免了一条会被反复怀疑的假线索。

## Clarifying Questions

1. **同床对照里厂商那一轮的姿态是否做过显式确认？** 两侧都取"各会话最好值"（极大值统计量），且厂商侧还经历了"找到较好姿态后"的挑选；
   四个比值 1.4/1.6/2.1/2.3 的离散度本身不支持"均匀"。若要继续用这条对照，需要**同一次会话内、rssi/MCS 分布匹配的窗口**相比。
2. **上行窗口的 `credit max = 132` 超过 128（0x80 是空邮箱读数）**——该字节高位是否有别的含义（V3 的额外比特），还是池子实际大于 128？
   这决定"均值 13~30"是"池子还很宽"还是"读了半个字节"。
3. **`owner_us` 合计 502 ms（窗口 25%）与全部已记账控制+credit 事务 54 ms 不自洽**：要么大部分控制读是 owner 内轮询完成（于是其耗时被记成 0），
   要么 `owner_us` 大部分不是事务时间。两者必有其一，现状无法区分（`class_min = 0us` 的存在支持前者）。
4. **`[wifi-probe]` 与 `[wifi-probe-rx]` 两行是否覆盖同一个 2000 ms 窗口？**（两行相隔 91 µs）本轮全部 TX/RX 对比建立在这个假设上。
5. **`ChainMiss::Idle` 的语义**：除 `prepare_next_transmit` 返回 None 外，是否还有第三处路径（`link.tx_indices()` 为空、内帧构帧失败）会让它在有帧时也返回 None？
6. **`ant_div_on`**：固件特性字 bit 18 为 0 已被两位 reviewer 核查（因此硬编码 0 与厂商一致），但该位是"能力位"还是"当前配置回显"？
   若为回显，则该常量会掩盖一个与已确认的天线姿态问题直接相关的特性。
