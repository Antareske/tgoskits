# 聚合首轮板测「发送停住」审查结论（2026-09-25）

本文记录对「最小聚合（每笔 CMD53 带 4 包）」首轮板测停住现象的审查结论，
以及交叉审查（终稿见 `probev5-aggregation-crossreview-20260925.md`）后对本文的修订。
原始串口日志：`probev5-board-20260925.log`。周期索引见 `aic8800-optimization-tracker.md` 周期 P5。
文中的提交哈希与分支名已随 2026-09-25 的分支迁移更新为 `sg2002/wifi-opt` 上的编号；迁移前的编号见该跟踪文档的「分支与提交」一节，交叉审查存档（`probev5-aggregation-crossreview-20260925.md`）保留当时的编号。

修订后的结论：

1. **确证一条由本次聚合改动引入的缺陷**：驱动把每个线上帧补齐到 512 字节后首尾相接，
   与固件按 `4 + align4(声明长度)` 步进遍历帧流的规则不符，**第 2..K 帧被静默丢弃**（第 0 节）。
   该缺陷即本轮停住的原因，**已由修复后的板测闭合**：上行从 256 KB 后停住恢复到 69.8 MB / 19.5 Mbps
   （周期 P4 的 K=1 基线 8.42 Mbps），详见第 7 节。
2. **一处推理已作废**：原第 2.2 节「`tx_ready` 深度 0 ⇒ 帧没有到达驱动」不成立（第 0 节）。
   因此「停住点在驱动之上」这一结论不再成立，停住位置回到未确定。
3. **原第 3.2 节「完成事件挤占缺陷未触发」的论证不成立**：该路径静默无计数，无法从日志反证（第 3.2 节）。
4. **四条已确证的缝隙**（停机与取消路径不回收进行中的写、M2/M4 内部写可携带用户帧、批次部分入队失败、
   适配层推迟队列未纳入活性判定）均已修复，见第 0.3 节。

### 0.1 作废的推理

| 2.1 节、2.3 节 | 把「256 KB」当作停住症状/送达量 | 256 KB 是**发送侧应用写入量**（iperf3 首行区间即为整额），不是送达量 | 只作为用例规模记录 |

### 0.2 交叉审查确认的缺陷（本次聚合引入）

固件按 `4 + align4(声明长度)` 步进遍历一笔写内的帧流，读到 `packet_len == 0` 即终止。
厂商驱动逐帧只做 4 字节对齐（`aicwf_sdio.c:2214-2240` 写入 `[4B 头][28B desc][payload]`，
`:2243-2247` 补零到 `TX_ALIGNMENT = 4`），整笔才在 `aicwf_sdio_aggr_send` 补齐到 512；
本驱动 RX 解析器同样是 `4 + align_up(packet_len, 4)`、`packet_len == 0` 终止（`rx.rs:119`、`:174`）。

聚合实现把**每个帧**先补齐到 512 再拼接，于是固件读完第 1 帧后按步长落进该帧自己的零填充，
读到长度 0 即停止：**第 2..K 帧被丢弃，而 CMD53 正常完成、K 个 token 全部完成、K 个信用全部扣减、日志无任何错误**。
单帧写一直正确，正是因为尾部零字节恰好充当流结束标记。

### 0.3 随本次修订一并修复的缺陷

| 缺陷 | 修复 |
| --- | --- |
| 聚合写按帧补齐 512，破坏固件帧流遍历（0.2 节） | 逐帧只按 4 字节对齐，整笔末尾才补 512（`protocol.rs::stream_frame_len`、`ActiveTx` 的流长度记账） |
| 内部（EAPOL M2/M4）写被追加用户帧，`TxCompletion::Internal` 分支不回收其 token → DMA 缓冲永久滞留 | 只在用户写在飞时增长写；`Internal` 完成分支同样归还 `extra_tokens` |
| `TxBatch` 部分入队失败会把 `TxQueueFull` 升级为设备 `Failed`，且丢弃的 token 无人归还 | 入队失败时归还本帧与批次内其余 token，设备保持 `Ready` |
| `drive_shutdown` / `finish_cancel` 不处理在飞的写，取消后作废写会被重发 | 两条路径都取走在飞的写并归还其 token |
| `pending_tx_tokens` 未纳入 `has_pending` / `has_runnable_pending` | 两个判定都纳入该队列 |
| 以上各项缺少红-绿测试 | 新增 6 个测试，均先在改前实现上验证为红 |

1. 驱动侧的 token 与缓冲**没有失衡**：每个窗口 `tx_submit == tx_done`（97/97、1/1）。

2. 停住**不是驱动报错导致的**：两轮日志（`probev5-*`、`probev4-*`）除 U-Boot 启动阶段一行

**`tx_ready` 深度的读法（更正）**：该深度在 `finish_idle`（`executor/mod.rs:745`）采样，

该读数只说明写**事务**变快（每笔 CMD53 携带 4 帧，写次数减少），不说明载荷已送达对端：
若每笔只有第 1 帧存活，则每**帧**的实际成本为 1102 µs，反劣于 K=1 的 706~780 µs（更正，原「275 µs/包」作废）。

## 3. 完成事件挤占事件队列（引入于 `9b0b505b7`，修于 `a9bdf9ce8`）

### 3.1 机制

`device/owner.rs` 的 `push_event` 在事件队列满时，会淘汰队列中**最旧的** `Receive` 事件来给非接收事件腾位置。
`9b0b505b7` 把一笔写的完成从 1 个事件改成 K 个事件（`consume_transmit_data` 对该笔的每个 token
调用该提交里的 `complete_tx_token`），于是完成事件速率乘以 K。当队列接近容量且接收帧较多时，
每个完成事件都会淘汰一个已入队的接收帧。

### 3.2 本轮是否触发：无法从日志判定（更正）

原论证以「完成事件产生速率（按 `tx_done` 计）低于排空速率（按 `owner_calls` 计）」推断队列不会被填满，
并以 `rx_done` 代表接收帧积压。该论证不成立：

- `rx_done` 是**交付量**（已交给协议栈的接收帧），不是**产出量**（驱动入队的接收帧）；
  两者之间存在淘汰与丢弃，只有产出量才决定队列是否接近容量。
- 淘汰路径（`push_event` 的 `remove_event`）**无计数、无日志、静默丢弃**，
  因此「本轮未触发」在现有读数下不可证伪。

结论：该缺陷的触发与否**未判定**；保留其存在性，不宣称本轮未触发。

### 3.3 仍然修掉的理由

- 当接收密集且写频繁时（双向、下行），接收帧会持续占据队列接近容量，此时完成事件会**逐个淘汰接收帧**；
  完成事件只是回收缓冲，淘汰接收帧换不来任何收益。
- 修正后：一笔写只发布一个 `TransmitAggregateComplete` 事件，事件量回到 K=1 的水平；
  队列满时完成改为等待（进 `device` 侧的 `pending_completions`，由后续推进逐个补发）而不是淘汰。
- 该提交**未上板验证**。

## 4. 进行中的写在停机与取消路径上不回收 token

| 位置 | 修订前 | 修订后 |
| --- | --- | --- |
| `device/progress.rs` 的 `drive_shutdown` | 只排空 `data.tx` 与 `internal_tx` 的 token，不处理 `active_tx`（含其 `extra_tokens`） | 取走在飞的写并归还其 token（0.3 节） |
| `device/progress.rs` 的 `finish_cancel` | 同样不处理 `active_tx`，取消后作废写会被重发 | 同上 |

这两处在 `9b0b505b7` 之前即存在：完成路径与失败路径会回还 `active_tx` 的 token，
停机与取消路径不会。聚合把每笔写携带的 token 从 1 个提高到 K 个，放大了同一缝隙。
（复核更正：取消路径的 token 原先**并非丢失**，而是随作废写一起被重试并归还；
真正的缺陷是作废写在取消后仍被重新发出。）

本轮用例不进入这两条路径（无取消、无停机），因此它们不解释本轮停住。

## 5. 已核对、未发现问题的点

1. **token 与缓冲回流平衡**：每个窗口 `tx_submit == tx_done`（97/97、1/1），无泄漏迹象。
2. **每帧自描述**：每个线上帧自带 `packet_len` 与 CRC 覆盖头（`protocol.rs`）、
   按 512 B 对齐、每帧有自己的 hostdesc（长度、目的/源 MAC、ethertype、接口与站点索引），
   厂商代码同样以多帧写提交（BSP 侧 `MAX_AGGR_TXPKT_LEN = 1536*4`，fdrv 侧 `1536*64`），本轮取 4 与 BSP 一致。
   （更正：本条原结论是「拼接后即为固件可遍历的帧流」，**该结论错误**——
   逐帧补齐 512 会破坏遍历，见 0.2 节。）
3. **写内不存在驱动侧设置的流量类别混合**：本驱动写入 hostdesc 的字段只有长度、flags、目的/源 MAC、
   ethertype、接口索引与站点索引，不含流量类别；类别由固件按载荷判定，且每个帧各自带一份 hostdesc。
4. **credit 记账自洽**：`aggregate_limit()` 取 min(层给的 K, 缓存读数 − 命令保留量)，
   无读数时只带 1 包；完成时按包扣减；命令与生命周期事务完成、取消时使缓存失效。
   （未核实：厂商**命令路径**按字节检查信用（`aicwf_sdio.c:1838`：`len > buffer_cnt * BUFFER_SIZE`），
   本驱动按「一个包一个缓冲」扣减；该差异是否会在读数接近保留位时透支固件池，需要固件口径或对照实验。）

## 6. 停住的位置

**能确定的**：停住期间驱动无错误、token 与缓冲计数平衡、写事务仍能完成。
**不能确定的**：停住发生在哪一层——原「帧没有到达驱动」的依据（`tx_ready` 深度）已作废（0.1 节）。

候选三条：

| 候选 | 与现有读数的关系 |
| --- | --- |
| (a) 固件按 4 字节步长遍历帧流，逐帧补齐 512 使第 2..K 帧被丢弃（0.2 节） | 机制在代码层面确定成立，且与「写事务完成很快」不矛盾（事务快不等于载荷送达）；与 K=1→K=4 的速率塌陷（周期 P4 纯上行 8.42 Mbps → 本轮 99.9~524 Kbps）时间同步。**但它是否是停住的唯一原因，现有日志仍无法闭合**：缺对端接收计数，且 `Retr`/`Cwnd` 不可信 |
| (b) 板端 TCP 发送缓冲与对端窗口停在固定边界 | 「每轮恰为 256 KB」与「Retr 0」都支持，但两者均为弱证据（2.3） |
| (c) 板端进程/调度层面停滞 | 周期 P4（K=1）已出现同形态先例：驱动空转、帧不产出、无错误 |

## 7. 判定结果（2026-09-25 修复后板测）

布局修复（`a8d6fca2e`，逐帧 4 字节对齐、整笔补 512）后的镜像 `…aggr4fix_20260925.img` 板测，
原始日志 `probev6-board-20260925.log`：

| 用例 | 修复前（周期 P5，K=4） | 修复后 |
| --- | --- | --- |
| 上行 30 s | 256 KB 后停住（210 Kbps） | 69.8 MB / **19.5 Mbps**（周期 P4 的 K=1 基线 8.42 Mbps） |
| 上行 10 s | 256 KB 后停住（99.9 Kbps） | 22.4 MB / **18.7 Mbps** |
| 下行 30 s | 80.0 MB / 22.3 Mbps | 109 MB / **30.4 Mbps**（周期 P4 27.3） |
| 双向 30 s | 停住 | 正常（板端 TX 12.5 + RX 6.5 Mbps） |

写侧读数与之一致：每窗口约 900 笔写中 626~839 笔为 4 包写，单笔 1086~1141 µs ≈ 275 µs/包。
即候选 (a) 成立：**第 2..K 帧被丢弃即为本轮停住的原因**，修复后停住消失、上行达到 K=1 基线的 2.3 倍。
（对端计数未单独采集：修复后的送达量本身已构成证据，且 `Retr`/`Cwnd` 口径不可信。）

遗留两点，与本节结论无关：

1. **首轮双向用例仍会停住**：`[RX-S]` 自第 1 秒即为 0、`[TX-S]` 恰为 640 KB 后归零、
   client terminated，期间驱动侧空闲无错误。周期 P4 日志（K=1、无聚合）在同一序列位置出现逐字相同的一轮，
   故属此前记录的「上层连接停滞」类，非本轮改动引入。
2. `Retr` 与 `Cwnd` 在板端始终为不可信读数，后续判据不要依赖它们。
