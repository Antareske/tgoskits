## 背景

dev 主线对 aic8800 驱动进行了全面重构（含 #2222 等提交），其板级验证在 AIC8800DC 实板（AKA）上完成；用户板卡为 LicheeRV Nano 板载 AIC8800D80（走 V3 序列），重构后的启动路径在该板卡上确定性 panic。本分支在 dev 基础上按"范围单一的最小修复 + 确定性回归测试"逐点修复。

## 问题清单 → 修复/改动范围

### 1. V3 wakeup 写回读值校验失配（931.log） —【已修复，板测确认推进】

- **问题**：dev 对 CMD52 RAW 写回读值要求等于写入值；V3 wakeup 写（fn1 0x02 写 0x11）的 RAW 回读字节为写前寄存器值 0x01（芯片尚在浅睡），判定失配 → `SdioWriteReadbackMismatch { expected: 0x11, actual: 0x01 }` → 启动失败 panic。完整证据链见关联分析文档。
- **修复**：`device/startup/vendor.rs` 对 V3 wakeup 写（index 2、非 reinitialize）退化为形状校验（接受 Byte、丢弃读回值）；就绪判定仍由 VendorReady 的 sleep-status READY 轮询负责。提交 `ebd0ca2aa`。
- **测试**：2 条回归（`v3_wakeup_write_accepts_a_non_echoing_read_back_byte`、`v3_vendor_writes_still_enforce_the_read_back_value`），旧实现上实证失败（`Err(SdioWriteReadbackMismatch { expected: 17, actual: 1 })`）。
- **板测验证**：2.log 越过 wakeup 写与 VendorReady 检查，推进至 ReadRevision——生效。

### 2. ReadRevision 邮箱确认超时（2.log） —【已修复，待板测】

- **问题**：`AIC mailbox timed out for DebugMemoryRead { address: 1078984704 } waiting for message 0x0401 in Confirmation phase`。地址 0x40500000 = CHIP_REV_ADDR，即 ReadRevision 阶段的第一条 ROM 调试邮箱（DBG_MEM_READ_REQ 0x0400，期望确认 0x0401）。Flow 信用与 FIFO 写均完成，确认 5s 未到达。
- **根因**：dev 重构后邮箱确认由 CARD_INT 驱动（写入后 `WaitForInterruptUntil`）。而 D80 的设备中断使能寄存器（fn1 0x00）只在启动末尾 ArmChipInterrupt 阶段才写 0x07——整个 ROM 阶段（ReadRevision/UploadMain/StartApplication）设备中断从未使能，ROM 不产生 CARD_INT → 确认永不达 → 超时。
- **厂商对照**：厂商驱动 `aicwf_sdio_bus_start`（aic8800_bsp/aicsdio.c）在 ROM 阶段读之前先写 fn0 0x04=0x07（CCCR INT_ENABLE）与 fn1 0x00=0x07（intr_config_reg），其 D80 IRQ handler 正是经 CARD_INT 处理 ROM 邮箱响应；dev 缺失这段时序。
- **佐证**：旧轮询驱动（本分支同步 dev 前）在同一板卡同一阶段以轮询 block_cnt 拿到过 ROM 响应（8 月 wc 系列板测）；DC 实板走 V1 序列与 fn2 邮箱，未覆盖 V3/D80 的该路径。
- **修复**：`device/startup/vendor.rs` 在 V3 VendorSetup(3)（非 reinitialize）新增写 fn1 0x00=0x07（INTERRUPTS_ENABLED），使 ROM 阶段邮箱确认前设备中断已使能（恢复厂商时序）；该写与 wakeup 写同属"RAW 回读字节为写前值"类寄存器（首次写前值为 0x00），同样按形状校验。提交 `83d794e32`。
- **测试**：2 条回归（`v3_vendor_setup_arms_the_device_interrupt_before_the_rom_mailbox_phase`、`v3_rom_interrupt_arm_accepts_the_raw_read_back_byte`），旧实现上实证失败（操作返回 None / `Err(CompletionMismatch)`）。
- **板测验证**：3.log 无邮箱超时、panic 点推进至 Reinitialize(2)——ROM 阶段 IRQ 确认链（ReadRevision/UploadMain/StartApplication）全部走通，问题 2 生效。

### 3. Reinitialize(2) wakeup 写回读值校验失配（3.log） —【已修复，板测确认开机成功】

- **问题**：3.log panic `SdioWriteReadbackMismatch { expected: 0x11, actual: 0x01 }`。3.log 内核 crc32 `cf3093ab` 与问题 2 修复构建产物一致，且全程无邮箱超时——板卡已越过 ROM 阶段，panic 点定位为 Reinitialize(2)：V3 reinitialize 序列（固件启动后）重复写 wakeup 寄存器（fn1 0x02=0x11），其 RAW 回读字节同样为写前值 0x01；问题 1 的形状校验只覆盖了 `!reinitialize` 变体，reinitialize 变体仍走值校验。
- **修复**：`device/startup/vendor.rs` 形状校验覆盖 wakeup 写（index 2）的全部变体（reinitialize 与否同一寄存器同一语义）。提交 `42c8d340f`。
- **测试**：1 条回归（`v3_reinitialize_wakeup_write_accepts_a_non_echoing_read_back_byte`），旧实现上实证失败（`Err(SdioWriteReadbackMismatch { expected: 17, actual: 1 })`，与板测同构）。
- **板测验证**：4.log 第二次启动（内核 crc32 `6eccaa3b`）完整走完启动序列并发布 wlan0（7.976s NIC 上线）——问题 3 生效，后续 Reinitialize(3)/ArmChipInterrupt 值校验亦实际通过。

### 4. AP 事务成功但 PC 搜不到 SSID（6.log） —【已修复，板测生效：PC 可搜到 SG2002】

- **问题**：`wifi-ctl wlan0 ap SG2002 6` 全链成功（日志：control transaction complete、reconfigured as AP 192.168.50.1/24），但 PC 搜索不到 SG2002——AP 逻辑配置完成而 beacon 未上电。
- **根因**：AP 路径的 beacon 上传（APM_SET_BEACON_IE_REQ）与 APM_START（APM_START_REQ）把 `vif_idx` 硬编码为 0，但启动序列已创建的 STA vif 占用索引 0；AP vif 的索引由 ADD_IF 确认的 `inst_nbr` 字段分配（预期 1），确认内容从未被解析。固件对错误 vif 执行 APM 序列或拒绝（CFM 状态字节同样从未校验），beacon 未发送。
- **厂商对照**：`rwnx_send_bcn` 与 `rwnx_send_apm_start_req` 均使用 `vif->vif_index`（即 ADD_IF CFM 的 inst_nbr）；`mm_add_if_cfm { status, inst_nbr }`；`apm_start_cfm.status` 由 `rwnx_cfg80211_start_ap` 显式检查。
- **修复**：解析 ADD_IF CFM（status 非零 → `FirmwareRejected`），把 inst_nbr 钉入 beacon 上传 payload[0] 与 APM_START payload[51]（自然对齐的厂商 `struct apm_start_req` 52 字节布局，逐字段核对：basic_rates@0/13B、pad、chan{freq@14,band@16,flags@17,tx_power@18}、center_freq1/2@20/24、ch_width@28、bcn_addr@32、bcn_len@36、tim_oft@38、bcn_int@40、flags@44、ctrl_port_ethertype@48、tim_len@50、vif_idx@51）；APM_START CFM status 非零同样报错。提交 `4f12a9007`。
- **测试**：3 条回归（vif 索引钉入两处请求、ADD_IF 拒绝透传 status、APM_START 拒绝透传 status），旧实现上实证失败（payload[0] 恒 0 / 拒绝被静默吞掉）。
- **板测判别**：修复后板测若仍无 beacon 且无错误 → 问题在 TX/RF 侧；若报 `FirmwareRejected` 带 status → 固件对 AP vif 语义的拒绝，按 status 继续分析。

### 5. AP 可见但 PC 加入无响应（7.log） —【STA 判别完成，收敛到 AP 态配置】

- **现象**：问题 4 修复后 beacon 正常上电（PC 可搜到 SG2002），但 PC 发起加入时 auth/assoc 始终无响应；7.log 中 AP 事务成功、加入尝试期间无任何驱动侧指示日志。
- **初步判断**：beacon 可见证明设备空口 TX 正常；全满 MAC 架构下关联过程由固件自主完成（主机不在 802.11 管理帧环内，仅在成功后收到 APM_STA_ADD 类指示），因此疑点集中在**固件空口 RX**（D80 的 RX 通路/RF 增益配置）或 AP 态 RX filter（0x1502868c 硬编码值与厂商 `RWNX_DEFAULT_RX_FILTER` 的对应关系待核对）。
- **STA 判别结果（10.log）**：STA 态空口 RX 完全正常（关联、握手、DHCP、ping 全通）——排除"RX 通路整体坏"，问题收敛到 **AP 态配置**（RX filter 值或 AP 专用固件配置，方向明确后对照厂商 `RWNX_DEFAULT_RX_FILTER`/`rwnx_set_rx_filter` 修复）。

### 6. WPA2 启动事务 panic：启动熵缺失（9.log） —【板测 workaround 已出镜像，长期修复待办】

- **现象**：开机自动 STA 镜像 panic：`secure Wi-Fi startup entropy failed: trusted wireless connection entropy is unavailable`（net/ax-net 在提交启动事务前经 `next_wifi_connection_entropy` → `ax_hal::boot::boot_entropy` 取 32 字节可信熵，取不到则 `EntropyUnavailable` → QueueInit panic）。
- **根因**：熵链为 `ax-net → axhal → axplat-dyn → somehal → someboot`，someboot 仅接受两种固件来源——UEFI RNG 协议或 FDT `/chosen/rng-seed`（恰 32 字节）；SG2002 板卡启动链（厂商 fip.bin 的 fsbl/opensbi/U-Boot 2021.10）两者都不提供（全链 grep 无 rng-seed 注入），内核侧按设计**拒绝**以时间戳/地址等可重放源兜底。
- **上游既有机制（PR #2222 调查结论）**：上游已做过同类测试，且 #2222 明确设计并实现了熵注入——`scripts/axbuild/src/starry/boot_entropy.rs` 的 `prepare_for_secure_wifi`：当构建环境提供 `STARRY_WIFI_SSID`+`STARRY_WIFI_PASSWORD` 时，以**主机 OS 随机数**生成 32 字节 `/chosen/rng-seed` 写入**临时 DTB 副本**（源 DTB 不变、tempdir RAII 清理）。但该函数只在 `starry/mod.rs` 的 `run_board_artifact`（CI `starry run` 板卡运行路径）接线，**普通 `cargo xtask starry build` 构建路径不调用**——上游 CI 的 AKA 板测（WPA2/DHCP/iperf 全过）从未经过裸构建+烧写镜像流程，故此前未暴露。
- **镜像流程适配（本次）**：按上游同机制在镜像构建时做单镜像种子注入——构建期随机 32 字节写入临时 DTB（dtc 重编，字节序列与 FDT 属性等价），经 update-kernel `--dtb` 只进入本次镜像；源资产 DTB 保持原版（22679 字节、sha256 `8d71cc…`，已恢复）。注意：同镜像跨次重启复用同一种子（上游 run 路径每次运行换新，闪写镜像流程每镜像换新），仅板测用途。
- **长期方向（待办）**：把熵注入按上游语义接线到镜像构建流程（或 SG2002 平台 TRNG 接入 someboot capture），恢复每次运行新鲜种子。
- **产物**：`sg2002_starryos_20260903-083455_kernel-20260903-162005_kernel-20260904-065455_kernel-20260904-070525_rootfs-20260904-073253_kernel-20260904-081608.img`（内核 crc32 `258b88f8` 不变；FDT 22722 字节、含 rng-seed、sha256 `014a9b11`；latest.img 指向本镜像）。

### 7. STA 数据面在 iperf 负载后停摆（10.log/11.log/12.log/13.log/14.log/15.log/16.log/17.log） —【已修复，板测确认：18.log 三次 iperf 全过】

- **现象**：WPA2 连接全链成功（熵→关联→EAPOL×2→密钥安装→control port→DHCP→双向 ping 通）；板载 `iperf3 -s` 会话运行后数据面失联（板上每秒重发 ARP 无应答，双向 ping 不通）；PC 侧热点仍显示板子已连接（关联级存活）；日志无驱动侧错误。
- **判别实验（11.log，用户已执行）**：失联后 `wifi-ctl wlan0 sta aasta` → SM_DISCONNECT 有 CFM（"stale station association cleared"）→ SM_CONNECT 30s `Sdio(Timeout)` 失败；**且命令执行后立即出现逐字符回显**（CPU 极慢，与 8 月记录的 wifi-ctl sta 逐字符回显同形）。
- **假说 1（OTHER 软 IRQ 未确认，已提交 `c7a9cab61`）**：厂商 D80 IRQ handler 在 OTHER 位置位时读 intr-pending 寄存器（fn1 0x01）、清 bit0（dev-to-host soft irq）、写回；dev 的接收扫描把 OtherInterrupt 当 Empty 直接推进——pending 位永不确认 → CARD_INT 电平持续断言（IRQ 风暴/owner 空转 → 逐字符回显的 CPU 饥饿）且固件等待其中断被消费（数据面停摆、SM_CONNECT 无应答）。2 条回归测试先行（red/green）。**12.log 板测：未根治**，且失联后 AP 切换时固件回异步断连指示 reason 1（关联层最终死亡）；11.log 的 SM_CONNECT 失败是主机侧 SDIO 超时（CMD53 数据写无响应）——指向固件 SDIO 侧在负载后卡死、总线数据通路停摆。
- **假说 2（byte-mode 120 映射，未提交）**：厂商 D80 IRQ handler 把 fn1 count **120** 当 byte-mode 标记、长度取 0x05 寄存器；dev 却读 120 块 = 61KB 超长 FIFO 读——若固件负载下切字节模式，超长读会挂死 SDIO 数据引擎，且无任何错误日志，与 12.log 症状吻合。测试先行 red/green 完成。**13.log 板测：部分价值兑现**——读不再挂死、CPU 不再饥饿（逐字符回显消失、冻结期间 shell 全程可交互），但数据面停摆未根治；本次全程 `other=0`，冻结路径不经过 OTHER 软 IRQ（假说 1 既未触发也未证伪）。
- **13.log 冻结证据（诊断心跳数据）**：iperf 客户端 67.4s 连接成功后 2s 突发窗口内（+22 CARD_INT、RX +214KB、TX 写 26 帧、流控轮询 1619 次仅 26 次获信用），69.4s 起**永久冻结至日志结束（258s）**：0 CARD_INT、0 RX 字节、0 TX 帧、**0 信用**；流控重试（读 fn1 0x03）以恒定 ~865 次/s 持续（总 224943 次），主机事件循环与 SDIO 总线全程健康（心跳持续、CMD52 持续完成）。第二次 `iperf3 -s` 监听成功但 PC 的 SYN 从未到达（PC 端 control socket 失败）——空口 RX 一并死亡。PC 侧（13-pc.log）：iperf 第 1 秒 3.38MB@28.3Mbit/s 后 12.7s 全 0，Retr=0、cwnd 冻结 131KB。
- **判定**：冻结本质 = **固件数据面在负载突发后永久停摆**（零中断、零 RX 交付、零 TX 信用），固件主任务存活（12.log 断连指示），主机侧一切健康。最可疑点为**突发窗口内主机写入的最后 26 帧**：厂商 D80 聚合路径（`aicwf_sdio_aggr`）不写 header[0..1] 长度字段（长度由 SDIO 块计数承载），dev 的 `ethernet_tx_frame` 对 V3 写 header[0..1]=advertised length + CRC8——帧级语义差异是唯一"恰在突发窗口由主机引入"的变量；47 帧前（ARP/EAPOL/DHCP）全部正常，说明差异对特定帧长/内容才致命。次要发现：① RX 解析异常——突发窗口主机从 FIFO 读 214KB、应用层仅收 128KB（40% 被主机解析层丢弃，轻载背景流量无此现象），parse 层对 V3 byte-mode 帧的适配存疑；② 流控重试语义与厂商不同——厂商 `FLOW_CTRL_RETRY_COUNT=50`、退避 200µs→1ms→10ms、超限丢帧，dev 每 1ms 无限钉帧（258s 零信用说明本次非根因，但恢复路径语义应对齐）。
- **假说 3（固件与芯片 revision 不配对）—【Linux STA 板测后彻底排除】**：本板芯片为 **D80 U01、非 H**（板上实测 ReadRevision 读回原始值 `0x0001_0020`，8 月档案回归测试载荷钉住）。**Linux 板端核查（www/sg2002-wifi-fw/ + SSH 实证）**：板端 vendor Linux（5.10.4-tag，Jan-2026 官方镜像）wifi 正常——AP 模式双向 iperf 27.7/27.8 Mbit/s；其主固件 `fmacfw_8800d80_u02.bin` **sha256 `ffb49ede…` 与 starry 加载的完全一致**（同一文件字节相同）；镜像内全部 D80 固件均为 u02 世代（无 u01），bsp.ko 硬编码从混合目录加载。**Linux STA 模式板测（用户执行）**：切 STA 连热点后 iperf **一切正常**——与 starry 冻结场景（STA）同构而 vendor Linux 无异常。**结论：同一颗 U01 芯片 + 同一份 u02 固件 + 同一 STA 场景，vendor Linux 数据面正常 → 硬件/固件彻底洗清，冻结是 starry 驱动 STA 数据面的实现缺陷**。差异点候选：① 接收扫描语义——厂商 D80 IRQ handler 以 `while(intstatus)` 循环**读到计数为 0 为止**（一次中断排空全部数据），starry 为有界单次扫描（每次 CARD_INT 只读一批，依赖下一中断）；② TX 帧格式/单帧写 vs 厂商聚合写；③ 流控轮询语义（厂商退避+丢帧，starry 1ms 无限钉帧）；④ RX parse 不支持 AMSDU（独立真 bug）。
- **假说 4（dev 重构丢失 D80 patch 配置）—【板上生效，但板测证伪：非冻结根因】**：旧驱动（#1185 时代）D80 启动 = 上传 u02 主固件 → `aicwifi_patch_config_8800d80`（把 3 条硬编码 patch 配置写入固件内存：0x00b4 2.4GHz-only USE_5G=0、0x0170 AMSDU_RX、0x0188 user_ext_flags PWROFST_COVER_CALIB）→ start_app；dev 重构后 D80 启动序列无任何 patch config / system config 阶段（仅存于 DC 路径）。**14.log 板测**：patch 序列板上全通（`D80 firmware version 0x06090101` → 重定位分支读回 `0x00179718` → `D80 patch config applied (3 entries)`，14 笔写确认全部通过），但 iperf 冻结签名与 13.log 完全一致（突发 +18 IRQ/+71KB RX/12 帧/1642 流控轮询 → 永久 0 CARD_INT/0 RX/0 信用，主机侧 ~862/s 流控轮询恒定）——**patch 配置非根因**。副作用：AMSDU_RX 开启后 14.log 应用层 0 字节交付（13.log 无 patch 时 60%）——AMSDU 拆包已有实现（`decapsulate_amsdu`），该丢帧的具体层位待查（可能为 `events` 满 256 静默丢弃或聚合帧未走到拆包路径，独立于冻结）；"收 0 字节照样冻结"证明冻结不依赖主机接收，进一步坐实固件侧负载停摆。
