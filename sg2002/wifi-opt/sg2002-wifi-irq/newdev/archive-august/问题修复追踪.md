## 问题清单 → 修复/改动范围

### 1. dev 分支 60s 初始化死锁 —【已修复】

- **问题**：`advance_init_request` 提交下一个纯寄存器总线操作后直接返回 Pending 未推进；协议层按"等待中断"处理，而纯寄存器操作从不产生中断 → 死等到 `DEFAULT_STARTUP_TIMEOUT`(60s) 兜底 panic。证据：dev-wifi.log/1.log（67s panic）。
- **修复**：`drivers/blk/sdmmc-protocol/src/sdio/io/init.rs` 的 `advance_init_request` 改循环——每提交一个新步骤立即以 `ProgressCause::Submitted` 推进一次（首次用调用方 cause）。与 sdhci-host host2 层 register-only 语义严格对齐。
- **测试**：`init_advance_keeps_driving_register_only_steps_within_one_call`（sdio/tests/io_card.rs，旧实现上失败已实证）。
- **板测验证**：5/6/7.log 均在 ~37ms 到达 AIC 启动阶段（dev 无修复必 60s stall）——生效。

### 2. 启动失败原因不透传 —【已修复】

- **问题**：`QueueInit` 无 payload，panic 文本为泛化 "network queue initialization failed"，无法从板测定位根因。
- **修复**：`net/ax-net` 的 `QueueInit(NetError)` 携带真实失败原因（executor 记 `startup_error`、builder 取回）。板测实证：4/5/6/7.log 的 panic 文本均带完整错误链——这是本轮所有根因定位的前提机制。

### 3. VendorSetup 响应形状失配（4 点） —【已修复】

- **问题**：核心 `expect_unit` 期待 Unit，而 rdif 适配层 Direct 完成一律映射 `Byte`（CMD52 R5 恒携带数据字节、`read_after_write: true`）→ 确定性 `MalformedResponse`。失配点共 **4 处**：`VendorSetup`、`Reinitialize`、`ArmChipInterrupt`（startup/mod.rs）、`Shutdown`（progress.rs）。dev 既有缺陷；板测 4/5/6.log 均死于此（此前误诊为"邮箱坏帧"）。
- **修复**（第二轮审查裁决方案 a）：`request.rs` 新增 `expect_write_ack`（接受 Byte、丢弃读回值），4 个消费点统一改用；`request.rs` 固化"请求 kind → 完成形状"契约表；`MalformedResponse` Display 改形状中立措辞（原 "mailbox" 措辞是误诊的语言级诱因）。
- **测试**：4 条阶段注入回归测试（喂 Byte → 断言推进而非 Failed；`ArmChipInterrupt` 断言 `Event(Started)`、`Shutdown` 断言 `Event(Stopped)`），旧实现上全部实证失败。
- **板测验证**：7.log 已越过全部 4 个失配点，到达 ReadRevision 的 revision 校验——生效。

### 4. ReadRevision 版本号解析缺位移 —【已修复】

- **问题**：7.log panic `unsupported chip revision 32`。新代码 `(raw & CHIP_REV_MASK)` 取低 6 位（=0x20=32，实为无关值噪声）；旧板测驱动与厂商驱动均取 `(raw >> CHIP_REV_HIGH_SHIFT(16)) & CHIP_REV_MASK`（=U01=1，合法）。`CHIP_REV_HIGH_SHIFT` 常量已定义但未使用。
- **修复**：`firmware.rs` ReadRevision 分支改为 `(raw >> CHIP_REV_HIGH_SHIFT) & CHIP_REV_MASK`；校验改用 `CHIP_REV_U01/U02/U03` 常量（消除硬编码）。
- **测试**：`read_revision_takes_the_version_from_the_high_half_of_the_read_back`（payload=0x0001_0020 → U01 接受），旧实现上实证失败。

### 5. Ready 态排空误吞实时 RX 数据 —【已修复】

- **问题**（第一轮审查 Blocker 1）：邮箱排空（DrainCount/DrainRead）无条件挂在每次 mailbox 开始，Ready 态控制命令与 RX 路径共用同一 FIFO，drive_ready 控制优先于 RX 轮询 → 实时数据帧被静默丢弃。
- **修复**：`mailbox.rs` 新增 `initial_mailbox_phase`——仅 `AicState::Starting` 以 `DrainCount` 起始（bootrom 残留只在初始化期存在），Ready 态直接 `Flow`。
- **状态**：纯核心行为已改；Ready 态板测（进入 Ready 后的扫描/连接）待验证。

### 6. 邮箱健壮性（坏帧重试 + 残留排空） —【已实现，待板测验证】

- **背景**：原报告 §5 方案（坏帧消费后重试 + 邮箱前排空残留 + 排空读失败容忍）。4.log 的"邮箱坏帧"根因已被问题 3 修正，本项定位相应改为"邮箱阶段的预防性加固"。
- **改动范围**：`mailbox.rs` 的 `DrainCount/DrainRead` 相位、`IoPurpose::MailboxDrain`、坏帧 → warn（携带帧头）→ 回 Count 重试（5s 兜底）、`consume_drain_discard_failure` 容忍。
- **测试**：原有 2 条（排空主路径、坏帧重试不判死）+ 新增 2 条门禁（排空失败容忍、坏帧后成功恢复完整链路）。
- **板测验证**：7.log 第一条邮箱（ReadRevision）走通——drain/flow/write/count/read 全链正常，未触发坏帧重试（待后续观察坏帧场景）。

### 7. 日志与诊断收尾 —【已落实，降级计划登记】

- 数据面热路径（`submit sdio`/`irq snapshot`）降 debug；`sdio: init state` 降 debug；生产路径裸 `unwrap` 改带上下文 `expect`；`startup_error` 兜底改 `expect`；rounds 记账/死臂哨兵/executor 注释等注释收尾。
- **`aic: mailbox count raw=` 暂留 info**（下一轮板测邮箱诊断依赖）；降级计划：邮箱阶段板测验证完成即降 debug（与 flow 无信用路径对齐）。

## 阶段性总结（2026-08-28，8.log 板测）

### 开机成功 🎉

8.log（10.47s **Welcome to Starry OS!**）完整走通 WiFi 初始化全链，全部修复板测生效：

```
ReadRevision（revision U01 接受）→ UploadMain（块上传循环）
→ UploadPatch → StartApplication → Stabilize → Reinitialize(0-4)
→ StackStart 邮箱 → ArmChipInterrupt → Complete → Ready
→ Initialize network subsystem → use NIC 0: "wlan0" → 开机成功
```

关键板测证据：
- `aic: mailbox read 512 bytes expected=0x040c head=[10,00,11,00,0c,04,...]`——邮箱帧 id 匹配、confirmation_payload 校验通过；`flow: credits=4/127` 流控正常
- 问题 3（4 点形状失配）、问题 4（revision 位移）、问题 6（邮箱加固）在真实硬件上全部生效

### 8.log 观察项（非阻塞）

1. **ReadRevision 阶段 count raw=0x01 持续 ~500ms 无 read 行**（7.26-7.75）：此后正常推进。可能为串口捕获丢行（read/warn 行丢失），也可能 Read 在飞——板测捕获环境仍不完整，待后续确认。
2. **eth0 mac 00-00-00-00-00-00**：网络子系统初始化时 WiFi MAC 尚未从固件读回（StackStart 之后才可用），全零 MAC 为已知顺序现象，待接入 STA/AP 时观察实际 MAC。
3. **DHCP bootstrap timed out**：预期行为——wlan 未连接任何网络（见下）。

### WiFi 配置现状（wlan 未拉起的原因）

- **原因**：设备树 `wifi-sd@4320000` 节点未设置 `aic,startup-mode` 属性 → `startup_transaction` 返回 None → 启动后 WiFi 空闲（既不 STA 也不 AP），无链路故 DHCP 超时。**这是当前设计下的预期行为，不是缺陷。**
- **启动默认模式机制**（`drivers/ax-driver/src/net/aic8800/fdt.rs:137-178`）：
  - 缺省 / `aic,startup-mode = "none"` → 空闲
  - `"access-point"` → 启动即 AP（需同时提供 `aic,ap-ssid`、`aic,ap-channel`(1-14)、`aic,ap-prefix-length`、`aic,ap-ipv4`，可选 `aic,dhcp-client-ipv4`）
  - **不支持启动即 STA**（STA 只能运行时切换）
- **运行时切换机制**（`os/StarryOS/kernel/src/file/wext.rs`，Linux wireless-extensions ioctl，对 socket fd 发 ioctl）：
  - `SIOCSIWMODE`(0x8B06)：2 = Managed/STA，3 = Master/AP
  - `SIOCSIWESSID`(0x8B1A)：SSID
  - `SIOCSIWENCODEEXT`(0x8B34)：WPA2 PSK 密码
  - `SIOCSIWFREQ`(0x8B04)：channel（仅 AP）
  - `SIOCSIWCOMMIT`(0x8B00)：原子提交（stage-then-commit 语义，全部 setter 只暂存）
  - 运行时切 AP 的固定策略：IP 192.168.50.1/24、DHCP client 192.168.50.2、默认 channel 6（wext.rs 常量）
  - 用户态调用方式：写小程序发 ioctl（rootfs 暂无现成工具；可注入或自编）

### 新问题：MM_ADD_IF_REQ（0x0006）固件无应答 —【未解决】
