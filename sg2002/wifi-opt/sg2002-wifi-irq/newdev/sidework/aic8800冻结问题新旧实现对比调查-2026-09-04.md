## 1. 结论摘要

1. **冻结根因已定位（代码级证据链完整，板测验证待做）**：`a12c3d11b`（#2250）引入的 `CardIrqWait` 重arm 门控。`rdif/owner/progress.rs` 的 `card_irq_rearm_allowed` 额外要求 `card_irq_wait == Armed`，而 `AicAction::RetryAt` 路径不置 Armed——TX 信用耗尽后设备进入纯流控重试循环，CARD_INT 从此**永不复用**（恒 Masked）。固件侧数据/软中断的 DAT1 电平断言在控制器层面被屏蔽，主机永远看不到，于是"固件有数据待发、主机 0 CARD_INT"死锁。
2. **15.log 冻结探针与根因完全吻合**：冻结期 `misc_int_status=0x04`（4 块数据待发）、`int_pending=0x11`（bit0 软中断挂起）持续 130s+，主机 `irqs/scans` 冻结在 503、`other=0`、无任何 SDIO/解析错误。这排除了"固件停止产生数据"方向（TX 帧格式假说），坐实"主机未消费已产生的中断"方向。
3. 当前工作树（2026-09-04 15:17:59 起）已删除该门控，rearm 条件恢复为 `ready && !active`；该改动未提交、未板测。
4. 其余差异按嫌疑强度登记于第 5 节，其中 **V3 接收长度解码残缺（119/121..126 域）** 是与厂商 D80 分支不等价的确定性代码事实，12.log 已证明同族缺陷（120 误读）会挂死 SDIO 数据引擎。

## 3. 根因：CardIrqWait 重arm 门控（HEAD 版，`a12c3d11b` 引入）

### 3.1 机制

`rdif/owner/progress.rs`（HEAD 版）的 `card_irq_rearm_allowed(card_protocol_ready, sdio_operation_active, card_irq_wait)` 要求三者同时满足才允许 CARD_INT rearm：

- `card_irq_wait` 仅在 `WaitForInterrupt` / `WaitForInterruptUntil` / `Idle` 动作时置 `Armed`；
- `SubmitSdio` 置 `Masked`；
- **`RetryAt` 不置任何状态**。

冻结闭环：

1. 突发窗口内 TX 信用耗尽，`consume_transmit_flow` 置 `retry_at` 后设备返回 `RetryAt`；
2. 每个流控轮询周期：`SubmitSdio(TransmitFlow)` → `Masked` → 完成 → 信用仍为 0 → `RetryAt`；`card_irq_wait` 恒为 `Masked`；
3. `finish_progress` 中 rearm 门控因 `Masked` 恒假 → CARD_INT 在控制器 STATUS_ENABLE/SIGNAL_ENABLE 双寄存器保持屏蔽；
4. 固件到达的 RX 数据与软中断在 `0x04=4`、`0x01 bit0=1` 上挂起、DAT1 电平持续断言，但主机无从感知 → 不排空 → 固件数据面背压 → 信用永久为 0 → 死锁。
5. 设备从此不再返回 `WaitForInterrupt`（active_tx 恒钉住），门控永无机会解除。

### 3.2 与各板测日志的一致性

- 冻结签名（0 CARD_INT / 0 信用 / 0 RX / CMD52 健康）与 12/13/14/15.log 完全一致；#2250 位于分支 HEAD，四个板测镜像（091715/123003/140607/144921）均携带该门控，同源冻结。
- 12.log 的"61KB 超长读挂死 SDIO 数据引擎"是独立缺陷（见 5.1 的 120 误读），不属本机制。
- 冻结前扫描正常的原因：突发期间设备周期性返回 `WaitForInterrupt`（事件投递、扫描收尾），短暂 `Armed` 窗口内 rearm+check 抓到持续电平 → 下一扫描。冻结始于设备首次进入纯 `RetryAt` 循环。

### 3.3 当前状态

- 工作树 `rdif/owner/progress.rs` 于 2026-09-04 15:17:59 修改（晚于 15.log 落盘 15:11）：删除 `CardIrqWait` 状态机与第三个门控参数，`card_irq_rearm_allowed` 恢复为 `card_protocol_ready && !sdio_operation_active`（当前 `rdif/owner/progress.rs:472`，调用点 :157/:439）。
- 修复后的恢复路径：流控重试循环中每次 `finish_progress` 都会 rearm+check；固件电平若持续断言（15.log 证据显示电平状态保持），会被立即抓取 → `publish_card_pending` → 扫描排空 4 块数据 → 信用恢复。修复自洽，但**尚未板测**。

## 5. 残留嫌疑点（按强度排序）

### 5.1【高】V3 接收长度解码与厂商 D80 分支不等价（`registers.rs:95-119`）

- 旧实现（厂商转写）：`intmaskf2 = intstatus | (1<<3)`；`intmaskf2 > 120` 为 func2 逻辑队列——`==127` byte-mode，否则块数取 `intstatus & 0x07`；`<=120` 为 func1 队列——`==120` byte-mode，否则 `intstatus & 0x7F`。
- 当前实现只特判 120；**119（func2 队列 byte-mode 哨兵）被解码为 119 块 = 60,928B 读，121..126（func2 队列 1..6 块）被解码为 121..126 块 ≈ 62-64KB 读**。工作树测试 `v3_interrupt_status_treats_120_as_the_byte_mode_marker` 把 `119 → Blocks(119)` 钉为期望值，即 func2 域缺失是当前代码的确定事实。
- 12.log 已证明同族误读（120→61KB 读）会挂死 SDIO 数据引擎；func2 域值的实际来源是命令/CFM/DATA_CFM 类载荷（TX 每帧请求 CFM，hostid bit31）。
- 15.log 全程无读错误/无 MalformedRxFrame，本次冻结窗口内是否触发未证实（无原始 count 值日志）。判别：记录每次 `ReceiveCount` 原始字节值。

### 5.2【中】CARD_INT 屏蔽窗口（根因之外的结构性差异）

- 新层完成路径也走硬 IRQ + `IrqState` 邮箱，CARD_INT 在 top-half 被屏蔽后直到扫描链结束（`active=None`）才 rearm，窗口大于旧 PIO 轮询层（每总线操作周围屏蔽）。
- 根因门控删除后，rearm+check 依赖控制器在 unmask 后重新感知已保持的电平；若板卡控制器存在边沿采样特性（电平在屏蔽期间断言、此后被固件撤销），仍可能丢失。属板测验证项而非已证实缺陷。

### 5.3【中】Ready 态缺失 V3 wakeup

- 旧驱动每次 TX 前 `wakeup()`，其注释明示睡眠期间 FIFO 写入"看似成功但固件不会真正发送帧"；当前 Ready 态数据路径从不写 fn1 0x02/轮询 0x01 bit4。15.log 冻结期 `int_pending=0x11` 的 bit4（sleep-ready）恒为 1，睡眠交互方向未排除。

### 5.4【低】流控恢复语义

- 厂商：50 次重试、退避 200µs→1ms→10ms、超限丢帧；当前：1ms 无限钉帧（冻结期实测 ~865 次/s CMD52 洪泛，258s 内 22 万+）。信用单位 1536（旧）vs 512（当前），门槛 `<` 修改（工作树）后单信用可放行 512B 帧。恢复路径语义待对齐。

### 5.5【低】TX 帧头长度语义与聚合写

- 未对齐 advertised length（当前 V3）vs 对齐（旧），厂商聚合路径因 .ko 无源码未逐字节核对；工作树已加 `diag tx frame` 头 24 字节日志（`data_plane.rs:415`），下次板测可与厂商 dump 比对。

### 5.6【低】次要发现

- `data_plane.rs:280`：`events` 满 256 时接收帧静默丢弃（13.log"读 214KB、应用层 128KB"40% 丢弃的部分来源）。
- AMSDU 拆包已在工作树实现（`decapsulate_amsdu`）；14.log 全丢弃是 patch 配置开启 AMSDU_RX 后的独立现象。
