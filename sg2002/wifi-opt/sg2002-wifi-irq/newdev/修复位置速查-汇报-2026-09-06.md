sg2002/wifi-irq 分支，8 笔修复，PR 分四组。行号为当前工作树行号，代码处附有同文中文注释（无 [教学] 标记），可顺行号对照阅读。

## 组 1：启动序列（3 笔，全在 device/startup/vendor.rs）

### 1a. ebd0ca2aa — 唤醒写的回读放宽

- **位置**：`device/startup/vendor.rs:38-44`（唤醒写）；`vendor.rs:119-125`（放宽校验主逻辑）
- **修复了什么**：开机序列里唤醒芯片的那次写（fn1 wakeup 写 0x11），"写后立即回读"的字节不再要求等于写入值
- **之前是什么**：芯片还在浅睡，寄存器停在旧值，回读的是 0x01 而不是 0x11；旧代码严格比对 → 开机第一步就报 `SdioWriteReadbackMismatch`
- **修复后怎么了**：对这次写只校验"回读确实是个字节"（形状校验）；芯片醒没醒由后面的 VendorReady 阶段轮询睡眠状态位兜底，不比数值也不丢安全性

### 1b. 83d794e32 — 设备中断使能提前

- **位置**：`device/startup/vendor.rs:53-57`（冷启动序列新增 index 3：fn1 interrupt_enable 写 0x07）
- **修复了什么**：把"打开设备中断"从启动末尾提前到 ROM 邮箱阶段之前，与厂商驱动时序一致
- **之前是什么**：dev 代码到启动最后一步才开设备中断；启动早期固件跑在芯片只读 ROM 代码里，靠设备中断送邮箱回复 → 主机一直等不到 → 超时报错
- **修复后怎么了**：ROM 阶段中断已开，邮箱回复正常到达；这条写的回读同样是写前旧值，一并做形状校验

### 1c. 42c8d340f — 重新初始化序列的同类放宽

- **位置**：`device/startup/vendor.rs:119-125`（校验覆盖 index 2 两个变体）；`vendor.rs:47`（reinit 序列的 index 3 走 fn0 0x04，回读正常仍严格校验）
- **修复了什么**：应用启动后的"重新初始化"序列里，重复的那次唤醒写同样放宽回读校验
- **之前是什么**：与 1a 同一寄存器同一语义，reinit 路径同样报错
- **修复后怎么了**：唤醒写（index 2 不分冷热启动）统一放宽；reinit 的 index 3（fn0 0x04）回读正常回显，仍走严格值校验

## 组 2：AP 模式（1 笔）

### 2a. 4f12a9007 — AP 网卡编号回填固件分配值

- **位置**：`device/control.rs:336`（`APM_START_VIF_INDEX = 51`）；`device/control.rs:338`（`open_access_point_commands`）；`device/mailbox.rs:324`（MM_ADD_IF_CFM 解析新增分支）；`device/mailbox.rs:352`（APM_START_CFM 状态检查）
- **修复了什么**：beacon 上传与 APM_START 命令不再硬编码网卡编号 0，改用固件在 ADD_IF 确认里分配的编号；同时开始检查固件返回的状态
- **之前是什么**：编号硬编码 0，但启动序列已先建了一张 STA 网卡占用了编号 0 → 命令全部发给了错误的网卡，PC 搜不到热点；且固件拒绝时驱动毫无察觉（确认状态从不解析）
- **修复后怎么了**：解析 ADD_IF 确认的状态与编号，回填进 beacon（payload[0]）与 APM_START（payload[51]）；APM_START_CFM 状态非零立即报错，不再静默成功

## 组 4：负载后数据面停摆（3 笔）

### 4a. 79951d9b8 — 卡中断重挂条件放宽

- **位置**：`rdif/owner/progress.rs:514`（`card_irq_rearm_allowed` 判据函数）；调用点 `progress.rs:173`、`progress.rs:465`；回归测试 `progress.rs:578`
- **修复了什么**：允许重新打开卡中断的条件从三条减到两条
- **之前是什么**：还要求"设备当前正处于等待中断状态"才允许重挂；而发送缓冲被占满后，主机进入反复读缓冲状态的退避循环（该循环从不说"在等中断"）→ 卡中断永远不再打开 → 固件有数据发不出、主机收不到、缓冲永不释放，双向卡死（iperf3 负载复现）
- **修复后怎么了**：只要设备已就绪且总线上没有在途操作，每轮循环结束都重新打开并检查卡中断；检查重复执行是安全的

### 4b. 9439e4bea — 发送缓冲读数的芯片差异恢复

- **位置**：`registers.rs:168`（`flow_credits`：V3 读整字节）；`registers.rs:95` 与 `registers.rs:120-128`（`receive_length` 复合编码解码）；`data_plane.rs:398`（`consume_transmit_flow` 发送判据）；`device/mailbox.rs:131` 起（邮箱信用读取配套整理）
- **修复了什么**：三处 V3 专属语义回归厂商行为
- **之前是什么**：
  - 读发送缓冲状态一律 7 位截取 → D80 上"完全空闲 = 128（0x80）"被读成 0 → 发送永久卡死；
  - 接收长度编码按 V1 老规则解码 → 120/127 被当成几十 KB 巨量块数读取，实测挂死 SDIO 数据通道；
  - 发送判据"缓冲数×512 ≤ 帧长就重试"→ 恰好 1 个缓冲放得下 512B 帧时也永远重试
- **修复后怎么了**：按芯片区分读取（D80 读原始字节、其它芯片保持 7 位截取）；按厂商复合编码解码（120/127 → 字节模式，113-118/121-126 → 另一队列的 1-6 块）；判据修正为"0 缓冲或容量 < 帧长才退避"

### 4c. c7a9cab61 — OTHER 软中断的两段式确认

- **位置**：`device/data_plane.rs:203`（`consume_receive_other_ack`：读回待决字节）、`data_plane.rs:228`（`consume_receive_other_clear`：清 bit0 写回）；分流在 `data_plane.rs:137`（`consume_receive_count`）；配套新增 `device/model.rs:376`（IoPurpose 两个新变体）、`device/progress.rs:170-171`（完成分发）
- **修复了什么**：V3 状态字节带 OTHER 位时，补做"读待决寄存器 → 清 bit0 → 写回"的确认，确认后沿同路径继续读数据直到取空
- **之前是什么**：把 OTHER 当空状态直接跳过 → 固件的"设备→主机"软中断挂起位永远不清 → 卡中断线一直被拉着，主机处理循环被饿死、固件等确认 → 负载下数据面停摆
- **修复后怎么了**：OTHER 中断被正确确认并取空；板测全程未再触发该路径，正确性由回归测试与厂商行为对照保证
