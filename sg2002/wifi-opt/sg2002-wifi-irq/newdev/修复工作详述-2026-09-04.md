## 1. V3 wakeup 写回读值校验失配（`ebd0ca2aa`）

- **问题（现象）**：纯 dev 镜像开机 panic：`SdioWriteReadbackMismatch { expected: 0x11, actual: 0x01 }`（931.log）。V3 wakeup 写（fn1 0x02 写 0x11）的 CMD52 RAW 回读字节为写前寄存器值 0x01（芯片尚在浅睡），dev 的值校验要求回读=写入值。
- **具体修复**（`device/startup/vendor.rs`）：
  - `validate_vendor_setup_readback` 新增形状校验分支：`transport_generation == V3 && index == 2 && !reinitialize` 时只校验 Byte 形状、丢弃回读值；其余写仍走 `expect_write_readback` 值校验。
  - 就绪判定不依赖该回读——仍由 VendorReady 阶段的 sleep-status READY 轮询负责。
- **结果**：2 条回归测试（旧实现实证失败 `Err(SdioWriteReadbackMismatch { expected: 17, actual: 1 })`）；板测 2.log 越过 wakeup 写并推进至 ReadRevision。
- **影响范围**：仅 V3 路径的 index 2 写放宽；V1/DC 路径与其余 index 的值校验行为不变。

## 2. ReadRevision 邮箱确认超时（`83d794e32`）

- **问题（现象）**：`AIC mailbox timed out for DebugMemoryRead { address: 1078984704 } waiting for message 0x0401`（2.log）。ReadRevision 的第一条 ROM 调试邮箱确认 5s 未到。
- **根因**：dev 的邮箱确认由 CARD_INT 驱动；D80 的设备中断使能（fn1 0x00）只在启动末尾 ArmChipInterrupt 写 0x07——整个 ROM 阶段（ReadRevision/UploadMain/StartApplication）设备中断从未使能。厂商 `aicwf_sdio_bus_start` 在 ROM 阶段前就写 fn0 0x04=0x07 与 fn1 0x00=0x07。
- **具体修复**（`device/startup/vendor.rs`）：
  - `vendor_setup_operation` 的 V3 分支新增 index 3（非 reinitialize）：写 fn1 0x00=0x07（`INTERRUPTS_ENABLED`），使 ROM 阶段邮箱确认前设备中断已使能。
  - 该写与 wakeup 写同属"RAW 回读字节为写前值"类寄存器，校验同步放宽为形状校验（index 3 非 reinitialize）。
- **结果**：2 条回归测试；板测 3.log 无邮箱超时，ROM 阶段确认链（ReadRevision/UploadMain/StartApplication）全通。
- **影响范围**：仅 V3 启动序列新增一次 fn1 0x00 写；V1/DC 序列不变（其 index 表独立）。

## 3. Reinitialize(2) wakeup 写回读值校验失配（`42c8d340f`）

- **问题（现象）**：3.log panic `SdioWriteReadbackMismatch { expected: 0x11, actual: 0x01 }`。板卡已越过 ROM 阶段，panic 点为 Reinitialize(2)：V3 reinitialize 序列重复写 wakeup 寄存器，回读字节同样为写前值；问题 1 的形状校验只覆盖 `!reinitialize` 变体。
- **具体修复**（`device/startup/vendor.rs`）：形状校验谓词改为覆盖 index 2 的全部变体（reinitialize 与否同一寄存器同一语义）。
- **结果**：1 条回归测试；板测 4.log 完整走完启动序列并发布 wlan0（7.976s NIC 上线），后续 Reinitialize(3)/ArmChipInterrupt 值校验亦实际通过。
- **影响范围**：仅 V3 reinitialize 序列的 wakeup 写放宽。

## 4. AP 事务成功但 PC 搜不到 SSID（`4f12a9007`）

- **问题（现象）**：`wifi-ctl wlan0 ap SG2002 6` 全链成功（6.log）但 PC 搜索不到——beacon 未上电。
- **根因**：AP 路径把 `vif_idx` 硬编码 0；启动序列已创建的 STA vif 占用索引 0，AP vif 的索引由 ADD_IF 确认的 `inst_nbr` 分配（预期 1），确认内容从未被解析；CFM status 也从未校验。
- **具体修复**（`device/mailbox.rs`、`device/control.rs`、`lmac.rs`）：
  - `lmac.rs` 新增 APM 消息常量（`APM_SET_BEACON_IE_REQ/CFM`、`APM_START_REQ/CFM`）。
  - `mailbox.rs` 的 `complete_control_mailbox` 新增 `MM_ADD_IF_CFM` 分支：解析 `[status, inst_nbr, ..]`，status 非零 → `FirmwareRejected`；否则把 `inst_nbr` 原地钉入控制队列后续命令——`APM_SET_BEACON_IE_REQ` 的 payload[0] 与 `APM_START_REQ` 的 payload[51]。
  - `control.rs` 新增 `APM_START_VIF_INDEX = 51` 命名常量（厂商自然对齐 `struct apm_start_req` 52B 布局，逐字段核对）；AP 命令序列改用命名常量；`APM_START_CFM` 非零 status 同样透传拒绝。
- **结果**：3 条回归测试；板测 7.log AP 打开且 PC 可搜到 SG2002。
- **影响范围**：AP 控制事务路径（wifi-ctl ap）；STA 启动路径的 ADD_IF 确认走 startup 链（`parse_add_interface`），不受影响；对 DC 的 AP 路径同样生效（共享代码，无 DC 板卡 AP 实测记录）。

## 5. OTHER 软 IRQ 未确认（`c7a9cab61`）

- **问题（现象）**：11.log 失联后 `wifi-ctl sta` 触发 SM_CONNECT 30s 超时与逐字符回显（CPU 饥饿）。
- **根因**：V3 `OtherInterrupt`（block_cnt bit7）处理缺失软 IRQ 确认。厂商 D80 IRQ handler 在 OTHER 位置位时读 intr-pending（fn1 0x01）、清 bit0、写回；dev 把 OtherInterrupt 当 Empty 直接推进——pending 位永不确认。
- **具体修复**（`device/data_plane.rs`、`device/model.rs`、`device/progress.rs`）：
  - `IoPurpose` 新增 `ReceiveOtherAck(RxPath)`/`ReceiveOtherClear(RxPath)` 两个实体（model.rs），`consume_completion` 新增对应分发（progress.rs）。
  - 新增两段式确认过程（data_plane.rs）：`consume_receive_count` 的 OtherInterrupt 分支 → 读 fn1 0x01（ReceiveOtherAck）→ `consume_receive_other_ack` 链写回 `pending & !1`（ReceiveOtherClear）→ `consume_receive_other_clear` 完成确认。V1 路径不触发（sleep_status 为 None 的 profile 无该分支）。
- **结果**：2 条回归测试；后续板测（13-16.log）全程 `other=0` 未再触发该路径，其正确性由测试与厂商语义锚定。
- **影响范围**：仅 V3 接收扫描链新增确认两段式；V1/DC 扫描不变（守卫测试 `v1_receive_counts_never_trigger_the_v3_other_interrupt_ack`）。

## 6. D80 patch 配置缺失（`f2550689b`）

- **问题（现象）**：旧驱动（#1185 时代）上传 u02 主固件后会写 3 条硬编码 patch 配置（`aicwifi_patch_config_8800d80`），dev 重构后 D80 启动序列无此环节（patch/sys config 仅存于 DC 路径）。板测 14.log 证实移植后序列板上全通，但冻结未根治（非问题 7 根因，为厂商语义恢复项）。
- **具体修复**（`device/startup/firmware.rs`、`device/startup/mod.rs`）：
  - 新增实体 `D80PatchStage`（11 变体）与驱动/完成两个过程：`drive_d80_patch`、`complete_d80_patch_mailbox`；`StartupStage` 新增 `D80Patch(D80PatchStage)` 变体插于 **UploadMain 完成与 StartApplication 之间**。
  - 流程：读 `0x12_0198`（config_base）→ 读 `0x12_01A0`（patch struct 基址）→ 读 `0x12_001C`（固件版本；`>0x0609_0100` 再读 `0x12_01A4` 取重定位缓冲基址，否则固定 `0x16F800`）→ 写 struct：+0 "PTCH"（0x48435450）、+8 "HCTP"（0x50544348）、+4 start_addr、+12 条数 3 → 写 3 对 `[offset+config_base, value]`（0x00b4 2.4G-only、0x0170 AMSDU_RX、0x0188 user_ext_flags=0x03）→ 写 4 个块尺寸 0（+48+i*4）。
  - 读经 `DBG_MEM_READ_REQ`（0x0400）、写经 `DBG_MEM_WRITE_REQ`（0x0402），与 ReadRevision 同机制；确认用 `debug_memory_read`/`require_debug_memory_write` 校验。
- **结果**：5 条回归测试（核心转换测试旧实现实证失败 RED）；板测 14.log：`D80 firmware version 0x06090101` → `D80 patch buffer relocated to 0x00179718` → `D80 patch config applied (3 entries)`，14 笔写全部确认。
- **影响范围**：仅 D80 启动序列新增 17 笔 ROM 调试邮箱操作；DC 路径（`StartupStage::Dc`）完全不变。

## 7. CARD_INT 重挂门控死锁（`79951d9b8`）

- **问题（现象）**：15.log 冻结态探针恒定 `misc_int_status=0x04`（固件有 4 块 RX 数据待交付）、`int_pending=0x11`（dev-to-host 软中断挂起），主机侧零 CARD_INT——固件有数据、主机收不到中断。
- **根因**：`rdif/owner/progress.rs` 的 `card_irq_rearm_allowed` 要求 `card_irq_wait == Armed` 才重挂 CARD_INT；`CardIrqWait` 仅在 `WaitForInterrupt(Until)`/`Idle` 时置 Armed，`RetryAt` 路径不置——TX 信用耗尽后设备进入纯流控重试循环（RetryAt→tick→流控轮询→RetryAt），门控永久 Masked，固件新到的 CARD_INT 永不被检查/重挂，RX 不排空、固件数据面背压、信用永不释放，双向死锁。厂商 Linux 的 IRQ handler 与 TX 路径解耦，无此窗口。
- **具体修复**（`rdif/owner/progress.rs`）：
  - **删减**：`CardIrqWait` 枚举（Masked/Armed）与 `AicOwner.card_irq_wait` 字段及全部赋值点整体删除（净 -42 行）。
  - `card_irq_rearm_allowed` 降为两参：`card_protocol_ready && !sdio_operation_active`——设备侧 `card_irq_needed()`（Ready 或启动确认等待）且无活动 SDIO 操作即重挂并检查；两处调用点（`rearm_and_advance`/`finish_progress`）同步更新。
- **结果**：2 条回归测试（`ready_device_rearms_card_irq_during_flow_credit_retries` 旧实现实证失败 RED）；板测 16.log：冻结态积压消失（0x04=0x00）、CARD_INT 投递恢复（突发期 +110）——第一层死锁腿消除。
- **影响范围**：rdif owner 为 DC/D80 共享层——行为变化为"非等待态也重挂检查"（每次 owner 步进多一次 rearm_and_check）；DC 板卡（AKA）需回归观察（无异常预期，重挂检查为幂等操作）。

## 8. V3 数据面厂商语义恢复（`9439e4bea`）

- **问题（现象）**：问题 7 第二层冻结——17.log 冻结态探针 `flow_raw=0x80`（信用寄存器读 128 = 固件邮箱完全排空），而 starry 的 7 位掩码把 0x80 掩成 0 → "无信用" → 永久钉帧。厂商对 D80 不掩码（`&0x7F` 仅用于 8801/DC/DW），`fc_reg != 0` 即发送。同笔另含两个厂商语义对齐项。
- **具体修复**（`registers.rs`、`device/data_plane.rs`、`device/mailbox.rs`）：
  - **新增实体**：`RegisterMap::flow_credits(self, value)` 方法——V3 读原始字节、V1 保留 7 位掩码；原自由函数 `flow_credits(value)` 删除。
  - **接收长度解码**（registers.rs `receive_length` V3 分支）：改为厂商 D80 IRQ handler 复合编码——`value|(1<<3) > 120` 为 fn2 队列域（127→ByteMode、113-118/121-126→Blocks(1..6)）、120→ByteMode、1..112 为普通块数；消除 119/127 被解码为 61-65KB 巨量读的同族缺陷（12.log 已证 120 误读挂死 SDIO 数据引擎）。
  - **流控判据**（data_plane.rs `consume_transmit_flow`）：`credits*BLOCK_SIZE <= frame_len` 改为 `<`——厂商语义 1 信用可发 512B 帧。
  - **OTHER 确认后同路径重读**（data_plane.rs `consume_receive_other_clear`）：软 IRQ 确认后不再推进路径，改为同路径重读计数直到空（厂商 `while(intstatus)` 排空语义）。
  - mailbox.rs `consume_mailbox_response`：流控字节在取 mailbox 可变借用前用 profile 感知方法解码（借用顺序调整）。
- **结果**：7 条回归测试（`v3_flow_credits_read_the_full_byte_without_the_vendor_mask`、`v3_single_credit_sends_a_single_block_frame`、`v3_other_ack_re_reads_the_same_path_count_until_empty`、接收解码 2 条等，旧实现均实证失败 RED）；板测 17.log 首秒交付 128KB（判据生效），18.log **三次 iperf 全过**（下载 31.2Mbit/s、上传 17.4Mbit/s、双向同时跑满 10s，全程 flow_retry=0），f1.log 干净版镜像复验通过。
- **影响范围**：V3（D80）数据面与邮箱流控语义；V1（DC）行为不变（`flow_credits` V1 掩码保留、receive_length V1 分支未动、`<` 判据对 DC 不生效——DC 为 Direct 流控不经过该检查）。
