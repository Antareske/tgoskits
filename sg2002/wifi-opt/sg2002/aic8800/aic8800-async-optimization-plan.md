# AIC8800 性能优化方案（第二、三阶段）

> 本文件维护 2026-09-27 OCR 审查之后的工作，现有两段：**第二阶段**（§1–§5，以 `ocr-review-20260927.md` 为边界）
> 与**第三阶段**（§6，以 `ocr-review-20260928-bottleneck-round1.md` 为边界）。第二阶段的方案与记录保持原样，作为第三阶段的输入。

## 1. 阶段边界

本方案维护 2026-09-27 OCR 审查之后的工作。OCR 审查全文保存在 `ocr-review-20260927.md`，它把此前已经完成的传输形态探索与后续协议、观测和无线能力工作分开。第一阶段的过程、提交和板测证据保留在 `aic8800-optimization-tracker.md`，本文件只把其结论作为第二阶段的输入。

### 1.1 第一阶段输入

第一阶段已完成并提交的工作包括 credit 本地记账、credit 回退粒度调整、事务和 owner 探针、TX 四帧聚合及帧流布局修复、可配置聚合上限、RX 扫描保持实验和 owner park 分段观测。主要可复用结论如下：

| 结论 | 证据 | 对第二阶段的影响 |
| --- | --- | --- |
| credit 本地记账有效 | 周期 1：CMD52/包由约 1 降到约 0.01 | 保持现有记账与失效条件，不重复设计 |
| TX 聚合有效 | 周期 P6：K=1 约 8.42 Mbps，K=4 约 18.7~19.5 Mbps | 保留现有帧流布局，后续只做选值实验 |
| RX defer 不适合作为默认优化 | 周期 P8/P8b：非零窗口未带来收益，3 ms 使固件传输显著变慢 | 默认值改为 0，非零值只作显式实验配置 |
| owner 与 SDIO 总线不可直接视为并行 | 周期 P3/P4/P6 及 OCR 复核 | 不先增加线程或并发提交，先修正协议流量和无线能力证据 |
| 普通 data confirmation 是无消费者的额外流量 | OCR 对照厂商 `rwnx_tx.c:647-671` 与当前 `protocol.rs` | 第二阶段首轮先关闭普通 data confirmation，并重新计数 |

这些结果不构成“已经达到 40 Mbps 或 58 Mbps”的证明。上行在不同会话之间存在显著波动，后续收益必须以实际协商速率、重传、事务计数和同一测试会话中的观测为依据。

### 1.2 第二阶段成功标准

第二阶段首轮的代码目标是恢复普通 Ethernet data 的厂商一致 confirmation 语义，建立可区分 FIFO 项类型的性能观测，并使默认 RX 扫描不被已否定的延迟策略阻塞。可观察验收条件如下：

1. 普通 data descriptor 的 `hostid` 为 0，普通 data 不产生 firmware data confirmation；
2. EAPOL 和需要 firmware 结果的内部控制帧仍沿专用 confirmation 路径；
3. probe 能分别报告普通 data、data confirmation、control confirmation、indication 和 firmware print；
4. 未配置 FDT 属性时 `rx-defer-ms` 为 0，显式非零配置仍可用；
5. 连接、WPA2 四次握手、TCP TX、TCP RX 和双向路径没有新增错误、重传或停滞；
6. 实体板卡结果记录完整，但在没有同会话对照时只报告观察，不宣称精确吞吐收益。

## 2. 第二阶段首轮实现

首轮只修改已经有明确代码证据支持的行为，不把 capability、DMA 所有权和多事务在飞同时加入。这样一份镜像即可回答协议流量是否被清理以及默认 RX 策略是否安全。

### 2.1 Confirmation 与 typed telemetry

`drivers/net/aic8800/src/protocol.rs` 的 `TxConfirmation` 表达普通 data 与 firmware confirmation 的区别。`drivers/net/aic8800/src/tx.rs` 的普通 Ethernet TX 选择 `TxConfirmation::None`，因此 host descriptor 的 `hostid` 为 0；`drivers/net/aic8800/src/device/data_plane.rs` 的内部 EAPOL/控制发送继续选择 `TxConfirmation::Firmware`。普通 data 的 SDIO 写完成已经是 token 完成依据，不能再依赖一个没有消费者的 data confirmation。

`drivers/net/aic8800/src/device/probe.rs` 将接收 FIFO 项按协议角色计数。计数只作为观测，不改变完成、credit、取消、RX 优先级或 IRQ 顺序。特殊帧的 confirmation 仍需后续补唯一 correlation ID、消费者、超时和取消回收；首轮不把这个独立问题与普通 data 处理混合。

### 2.2 RX defer 默认值

`drivers/net/aic8800/src/device/data_plane.rs` 的 `DEFAULT_RX_DEFER` 改为 `Duration::ZERO`。`drivers/net/aic8800/src/rdif/device/endpoints/device.rs` 继续从该默认值构造适配策略，`drivers/ax-driver/src/net/aic8800/fdt.rs` 继续允许 `aic,rx-defer-ms` 在 `0..=10` ms 内显式覆盖。

零窗口意味着 CARD_INT 事实立即进入扫描路径；非零窗口仍保留用于后续同会话实验，但不再作为产品默认。对应单测必须区分“默认立即服务”和“显式窗口保持”，避免测试把实验配置误当默认契约。

## 3. 后续优化顺序

### 3.0 配置面的取舍原则（2026-09-28）

配置与能力取值必须对**芯片族**与**常见信道**通用，不为本地测试热点或某个信道调参：

- 能力位与固件配置以厂商在**该芯片族**（D80 / DC 等）上的取值为准，逐字节对照后编码；不以"在这台 AP 上更快"为理由做试验性微调。
- 频段/信道相关取值（发送功率表、信道表、带宽声明）按厂商与标准取值，不按本地热点的信道表现裁剪；新增取值要能落到所有常见信道上。
- 细分硬件配置（EDCA/TXOP/RTS 阈值、天线分集、PS 档位、SDIO 时钟档位等）若复杂度、细化程度或测试难度较大，**不作为推进方向**；其中成本极低且能一次定性的事实（如总线速率的读回）可以记录，但不立项。
- 与其在配置面细分，不如继续推进**驱动层异步优化**：把每笔操作的关键路径拆开、让准备与提交解耦、让 TX 提交不被 RX 工作挤占。

首轮板测完成后，按观测结果推进后续工作。每一步都先保留当前可启动的镜像和代码路径，再增加一个主要变量。

### 3.1 D80 HT40/SGI 能力实验

P0a 实板已完成：COM6 活跃数据窗口中 `data_confirmations=0`，确认普通 Ethernet data 的 `hostid=0` 语义在板上可见。Windows cmd 直接运行 iperf3 后测试端波动减小。

HT40/SGI 已上板两轮（板端启动日志打印 `d80-ht40-sgi`）：正向 25.3/28.8/26.7/29.9 Mbps、反向 18.8/15.6/19.4/19.0/20.6 Mbps、双向 13.6/12.5 Mbps，均高于 P0a 轮同向读数，但两轮不是同一会话，按观察记录。上一轮"`-b 100M` 明显偏慢"没有复现（正向三个用例中它居中，反向四个用例中它与不带 `-b` 持平），该测试端变量可以关闭。板端发送窗口的 `credit` 长期见底（`min=2`、回退 500~1300 次/2 s），说明 TX 仍受固件/空口排空速度限制。

D80 的 `MeConfigProfile`（`drivers/net/aic8800/src/lmac.rs`）按显式偏移安全编码 112 字节 `ME_CONFIG_REQ`，DC 使用保守字节。HT40/SGI 段的取值为 LDPC、20/40 MHz、SGI20/40、MCS32 与单流 MCS0–7 mask、HT highest-rate 150；`device/startup/mod.rs` 只按已验证的芯片身份选 profile 并记录 profile 名。payload 测试固定关键字段与字节；不以 C struct 指针转换或 `repr(C)` 作为线格式编码方式。

速率遥测轮的复测读数（`com6-board-20260928-042935.log`）把这一段的结论定死了：259 条样本全部 `width=20MHz format=ht-mf nss=1 sgi=1`，MCS 以 7 与 6 为主、并有少量 5~1，`txfailed=0`，ack 失败约为成功的 15%。即 **HT 侧能力已生效并工作在 HT20 顶档（PHY 65~72 Mbps），带宽仍是 20 MHz**；20 MHz 上已无 MCS/GI 余量，能动的只剩调制格式。

由此更正一处判读：HT40/SGI 轮曾据厂商 Linux 基线的 UDP 76.5 Mbps 推断该热点支持 40 MHz（依据是它超过 20 MHz 单流 HT 的 72.2 Mbps 上限）。厂商 D80 在 2.4 GHz 同时宣告 VHT 与 HE，20 MHz 的 PHY 上限因此是 86.7 Mbps（VHT MCS9）到 129~143 Mbps（HE MCS11），厂商基线完全可以发生在 20 MHz。**AP 的 BSS 宽度重新成为未知量**，差距的确定部分是调制格式：厂商是 HT+VHT+HE 客户端，本驱动此前是 HT-only。

厂商源码的自然 ABI 对照已固定：标准构建 `CONFIG_RWNX_TL4=n`，`mac_htcapability` 为 32 字节、VHT 为 12 字节、HE 为 56 字节，`me_config_req` 的尾部 scalar 从 offset 100 开始；D80 的 `rwnx_set_ht_capa()` 在 HT40/SGI 路径将单流 MCS32、`rx_highest=135/150` 与 capability bits 一起设置。Rust encoder 只复现这些已核实的字段，不依赖 C ABI cast。

厂商参考是 `lmac_mac.h` 的 `mac_htcapability`、`lmac_msg.h` 的 `me_config_req`、`rwnx_mod_params.c:rwnx_set_ht_capa()` 与 `rwnx_msg_tx.c:rwnx_send_me_config_req()`。HT40 路径设置 MCS32 mask 和 `rx_highest=135`，随后 SGI40 将 highest rate 更新为 150；D80 在厂商启动中为单流。固件和厂商 `lmac_types.h` 的标准构建使用 8-bit `u8_l`，配置结构按自然 ABI 对齐得到现有 112-byte 布局。实际协商 bandwidth/MCS/retry 尚未从 Starry 侧读取，板测结果只报告连接、稳定性与吞吐观察，不将性能变化归因于协商档位。

**本轮（VHT/HE 能力，提交 `1fb1bc91c`）**：`lmac.rs` 新增类型化 `VhtCapabilities` / `HeCapabilities`，D80 profile 更名为 `D80Ht40SgiVhtHe`（启动日志打印 `d80-ht40-sgi-vht-he`），取值照厂商 `rwnx_set_vht_capa()` / `rwnx_set_he_capa()` 在 2.4 GHz、单流下的结果：VHT `vht_capa_info=0x03987111`、单流 MCS 0–9（map `0xfffe`、highest 390）；HE `mac_cap_info[2]=0x02`、`phy_cap_info=[0x06,0xe0,0x2b,0x58,0x0d,0xc0,0xcf,0,0x02,0x30,0]`、单流 MCS 0–11（`mcs_80=0xfffe`）、160/80+80 不支持、PPE 阈值 `[0x38,0x1c,0xc7,0x01,…]`；标量 `vht_supp=1`、`he_supp=1`、`he_ul_on=0`。同一改动把 D80 的 `phy_bw_max` 由 40 MHz 改为厂商对 D80 强制使用的 80 MHz（`PHY_CHNL_BW_80`）；厂商 HT 块的 RX_STBC 与 MAX_AMSDU 位属接收侧能力，本轮不跟。DC 保守 profile 字节不变。

厂商 `me_config_req` 的逐字节对照结论（先排除消息布局错位、A-MPDU 与 `tx_params` 取值、关联请求 IE、信道表 flags 四类假设）与 `phy_bw_max` 的偏差记录见瓶颈文档 §2.16。

本地验证：`cargo fmt --all`、`cargo xtask clippy --package aic8800`（base / `rdif` / `host-test` 三组）、`cargo xtask test --since dev` 通过；新增 VHT/HE 金样本单测（固定每个能力字节、MCS map、PPE 阈值与 HE 结构的对齐填充）并扩展 startup 路径的两芯片断言。镜像 `sg2002_starryos_wifi_sta_vhthe_20260928.img` 基于 P0a 镜像只换内核与 `lcn-sta-defer0.dtb`，构建不执行板卡写入。

上板判据是单一的格式判别：读数出现 `format=vht` 或 `format=he-su` 且 MCS 进入 8–11 → 差距可归因到调制格式；仍是 `format=ht-mf mcs=7` → 该 AP 不与本客户端协商 VHT/HE，方向转向 AP 侧与带宽问题，而不是继续加客户端能力位。只要 `width=20MHz` 保持，任何吞吐变化都不得解释为带宽收益。回滚点为 `sg2002_starryos_wifi_sta_stainfo_20260928.img`（等价 `8a350076a`）与 P0a 镜像。

另有一个板载网络栈的独立项：`net/ax-net` 的 `NEIGHBOR_TTL = 300 s` 到期会重发 ARP 并在 `ETHERNET_MAX_PENDING_PACKETS = 128` 装满时丢包，两轮板测各出现一次、都伴随该用例内的 TX 吞吐下滑（详见瓶颈文档 §2.14）。它不是 AIC 驱动问题，是否处理由上层决定。

### 3.2 TX 聚合选值

现有 `aic,tx-aggregation` 和 `aic,tx-aggregate-bytes` 已能在 FDT 中选择一笔 CMD53 的帧数和字节上限。普通 data confirmation 清理并完成新基线后，再分别针对大数据帧和小 ACK 流测试：

| 负载 | 首选变量 | 候选值 |
| --- | --- | --- |
| 板端 TX 大帧 | 字节上限，帧数作安全上限 | 6/12/24/48 KiB |
| 板端 RX 时产生的小 ACK | 帧数上限，字节上限同步放宽 | 4/8/16/32 |

写成形仍采用机会式冲刷，不为等待更多帧增加固定延迟；credit 仍是 firmware buffer 数量约束。每个候选值至少观察 TX、RX、双向、写事务长尾、RX 事务数量、credit 和是否停滞，选择达到平台峰值且不破坏双向公平性的最小值作为默认。

### 3.3 数据面流水线与 DMA

只有在 confirmation、协商速率和聚合形态稳定后，才根据阶段计时决定是否引入 `staged_tx`、可复用 batch buffer、move-only completion 或 exact-size DMA pool。当前单 owner、单 SDIO transaction in flight、`CardIrqWait` 和 `completion-before-card` 顺序都是安全不变量；任何改变都必须重新说明完成匹配、取消、资源回收和 RX 防饥饿。

复制和 DMA 优化不能以“可能更快”作为立项依据。应先把 owner 推进拆成 RDIF 收割、核心状态机、构帧/聚合、DMA/ADMA 准备和 rearm，再用阶段计时确认 CPU 准备是否占据显著比例。没有该证据时保持现有跨内核边界。

阶段二共四轮，代码全部保留在 `sg2002/wifi-opt` 上：

| 轮次 | 内容 | 提交 | 证据状态 |
| --- | --- | --- | --- |
| P0a | 普通 Ethernet data 用 `hostid=0`；typed FIFO 计数；默认 RX defer=0 | `fd80b2b69` | `data_confirmations=0` 在活跃窗口成立（协议层事实） |

随本小结转入待办清单，时机合适时再回来收敛。**本阶段就此暂时搁置，转为推进下面的当下方向。**

### 3.5 当下方向（2026-09-28 起）：通用性下的硬件配置与驱动层异步优化

配置面按 §3.0 的取舍原则执行：只保留与厂商芯片族取值一致的能力位与协议修正，不为本地热点或单一信道调参；
细分硬件配置方向放弃。主要精力转入**驱动层异步优化**，目标是回收下面这段被浪费的墙钟（瓶颈文档 §1 的分解）：

| 组成 | 占墙钟 |
| --- | --- |
| TX CMD53 写 | 52% |
| RX 事务 | 25% |
| 写完成 → 下一笔提交的空档 | 48%，其中 44% 落在同时有 RX 事务的窗口（387 笔 × 2287 µs） |

三个台阶，逐级推进、每级一个镜像一个回退点（小步快跑）：

**A. 写完成即续接写管线（已实板：`2772a4c0e` + 审查修复 `dfdc282cc`，镜像 `sg2002_starryos_wifi_sta_txchain_20260928.img`）。**
实板结果：续接命中约 37%、上界让位 42%，但**未见吞吐提升**——周期 64% 是单笔写自身，credit 均值 7.1、`backoff` 225 次/秒，
说明发送方向受固件缓冲池排空速度（空口/对端）限制，不是提交调度（详见瓶颈文档 §2.18）。该机制保留（已过审查与变异测试、无衰减证据），
**但 TX 侧不再在提交调度上继续投入**；异步线转向 RX 侧（见 §3.6）。
> **⚠️ 本节的方向性结论已在第三阶段被否**（证据链由两个探针窗口拼成、其中一项是恒等式、credit 采样内生，见 §6.1 与瓶颈文档 §2.18/§2.21）；
> "续接机制本身无衰减" 这一条仍然成立，其余判读仅作历史记录。原描述： 一笔写完成后，若核心队列已有帧且缓存 credit 仍允许写，
owner 在该完成路径里直接排出下一笔（缓存读数已用尽时先排一次流控读，由它的完成继续进入写）；
续接每轮协议推进至多一次，驱动路径每次运行清除该上界，因此接收扫描、mailbox 与遥测仍能在两笔写之间轮到自己。
不改完成匹配、credit 语义、取消路径与"完成先于 card 事实"的顺序；探针新增 `chain hit/idle/busy/backoff/not_ready/yield`
六个计数，板测用它判断续接实际生效的比例与未生效的原因。

**B. 准备与提交解耦（prepare-ahead）。** 上一笔在飞时完成下一批的构帧、DMA 准备与 ADMA2 重建，完成中断一到立即提交；
准备阶段对外无副作用，但需要 RDIF 层允许"持有已准备的传输"。

**C. 多笔在飞。** 真正的并发提交，需要重做完成匹配、credit 记账与取消回收——即 §3.3 列出的安全不变量重述；
只有 A+B 之后仍有明显空档才立项。

**RX 优先级的边界（不得突破）**：主线的 RX 优先是为了及时响应 mailbox 命令与保持固件缓冲健康，
因此"A"中的让路**只允许作用于数据帧读取**：

- mailbox 的确认与指示（协议推进）不让路；
- **TX 完成确认不让路**——它直接归还 credit，是下一笔写的闸门；
- 不采用"按时间窗口推迟 RX 扫描"的做法：周期 P8/P8b 已实测这一方向会让固件退化（表现为 credit 见底），
  因此只允许"同轮内顺序 + 每轮上限"，并同时监控 RX FIFO 积压与 credit 读数。

**第一步只观测、不改行为**：把"写完成 → 下一笔提交"的空档按用途拆开计时（数据帧读取 / TX 完成确认 /
control 确认与指示 / 真正空闲），并同时记录 RX FIFO 积压与 credit。据此判断空档中有多少可回收、
回收是否会碰到上面两条红线；未取得该读数前不动顺序。

### 3.6 异步线转向：RX 侧（2026-09-28 起）

> **⚠️ 本节的转向前提已在第三阶段被否**（"RX 受限在交付节奏"的分子口径不全，见 §6.1）；接收侧随后被判定由卡的交批节奏决定（瓶颈文档 §2.25），本节候选不再推进。

TX 侧的提交调度已被实板排除（§2.18），而 RX 事务占 RX 总线时间的约 81%（数据读 134 µs/笔、控制读 51 µs/笔），
且接收是当前较好的方向（接收 32.8 Mbps 对发送 17.3 Mbps）。因此驱动层异步优化的下一步放在 RX 侧，候选按代价排序：

1. **让每次交付更大（已实现，待板测）**：HT 能力位 `MAX_AMSDU`（上限 7935 字节）——厂商按固件上报的
   A-MSDU 支持决定该位，D80 的固件支持由同一 profile 的 VHT 字段（`amsdu_rx_max = 1`）佐证；
   AP 可用 A-MSDU 发送后，固件每笔交付载荷更大，直接压低"每字节的 RX 事务数"。一位能力位，
   与既有能力位同类，不涉及环境调参；接收路径本就有 A-MSDU 解包子帧的分支与单测。
2. **压控制读次数**：RX 扫描里每函数的块计数读（51 µs/笔）与控制类读取的合并/减少。
3. **收尾空读**：`ReceiveLength::Empty` 之后的事务是否可省，需要先测其占比。

判据：RX 事务条数/字节、`[wifi-probe-rx]` 的 `data_reads`、接收吞吐；TX 侧只作为不退化校验（`chain`/`credit` 读数不变差）。

### 3.7 覆盖盘点与建议（2026-09-28）

**已覆盖（有实测支撑）**：① 主机发送路径——credit 本地记账、聚合 K=4/约 6 KB、owner park、写完成续接
（实测命中 37%，但周期 64% 是单笔写自身，收益空间已被证明很小）；② RX 扫描结构——有界推迟（否定结论，默认关闭）；
③ 能力协商——HT40/SGI/MCS32 → VHT/HE → MAX_AMSDU（遥测 `he-su`、协商证据显示 A-MSDU 已被采纳并有交付计数）；
④ 观测面——typed probe、速率遥测、固件自述（`[wifi-fw]`）、协商 IE 解码（`[wifi-assoc]`）；
⑤ 限制项定位——TX 受固件缓冲池/空口排空限制（credit 均值 7.1、`backoff` 225 次/秒），AP 为 20 MHz + 2.4 GHz HE，
会话变量为热点/板卡重启与**天线姿态**。

**覆盖不完全**：① **双向形态**——板端 RX 在双向里塌到 8~11 Mbps（单向 31），最大的一块未归因；
② 写事务每字节成本的分解（总线 / 描述符 / 固件）从未分段；③ credit 池总量与其排空速率的关系（只知长期贴底）；
④ owner 分段计时（构帧/DMA/rearm 占比）——判断是否值得动主机结构的前置证据；
⑤ RX 每字节成本**本轮已补测**（每笔 21~22 KiB、贴总线、占空比约 50%，见瓶颈文档 §2.19）：主机侧已高效。

**未覆盖**：① **5 GHz**——信道表只有 2.4 GHz，而 D80 是双频芯片；带宽与干扰环境完全不同，是能力面最大的一块空白；
② 多笔在飞/流水线（设计边界突破）——TX 侧既已证明限制在外，优先级下调；
③ RX 侧的其它结构手段（控制读合并、收尾空读）——本轮显示每字节成本已高效，优先级下调；
④ SDIO 总线速率/宽度（按 §3.0 搁置，仅保留读回事实）；⑤ 与厂商 Linux 在**同条件**（正确姿态、同一热点、代理关闭）下的对照——
"差距是否存在、差在哪"的最终判据，至今未做。

**实际表现**（正确姿态的最好会话）：接收 31.3/31.2、发送 27.2、双向 21.3/8.4 Mbps；厂商基线（同热点）发送 58.2/58.5、
接收 54.6/53.9 → 差 1.7~2.1 倍。而**两个方向的主机侧路径都已不是已识别的限制项**。

**建议顺序**：① 双向形态归因（零改动，读现有日志即可）；② 5 GHz 能力（能力面空白最大，通用、不涉及环境调参）；
③ 厂商 Linux 同条件对照（先确认其工作频段——若它在 5 GHz，则"差距"的性质完全不同）；
④ owner 分段计时（决定是否动主机结构）；⑤ 明确搁置项保持搁置。

## 6. 第三阶段（2026-09-28 起）：瓶颈重判与观测裁决

### 6.1 阶段边界与前提更正

第三阶段以 `ocr-review-20260928-bottleneck-round1.md`（7 个 reviewer + 三方交叉质证）为边界。该轮审查**否掉了第二阶段的两个方向性前提**：

| 被否的前提 | 否掉的依据 |
| --- | --- |
| "TX 受固件缓冲池排空速度（空口/对端）限制，主机提交调度不用再投入"（§3.5-A） | 证据链由**两个不同的探针窗口**拼成：给出"周期 64% 是单笔写自身"的窗口里 credit 均值是 36.1、回退占写次数 4%，而"credit 均值 7.1、回退 225 次/秒"来自另一个窗口；且 `period ≡ gap + rtt` 是定义式分解，不构成独立证据；credit 采样节奏内生（只在 `consume_transmit_flow` 采样，同会话采样数变化 19 倍且与均值强负相关） |
| "RX 受限在交付节奏（一半时间总线空着 ⇒ 固件/对端没供货）"（§3.6） | "50% 占空比"的分子只算了 RX 数据读；补入 RX 控制读、credit 读与 TX 写后，真实占用是 **58%~69%**。而用来论证"空档被 RX 吃掉"的 `gap rx2+` 桶是**事后**分类（空档越长分到的 RX 越多），同窗 RX 事务总时长只有 95~106 ms 对 500~746 ms |

同时，"纯上行受上游供帧限制 = 否"这条关闭项按**计数**成立、按**时间**不成立：同一行的按时间口径是
`supply none` 占窗口的 **21%~29%**、占全部空档时间的 46%~59%。该项由"已关闭"改为**待判**。

第三阶段接受以下实测结论作为前提（均来自该轮审查，且由 ≥2 个独立实例复算）：

1. **约束的形状是「每笔事务的固定开销 + 事务间空档」决定事务率，不是每字节速率。** 对 771 个上行窗做窗内回归，**0/771 出现负截距**，
   中位固定项 **445 µs**（IQR 366–550）；全量 2169 窗独立拟合 `span ≈ 480 + 0.096·B`，同时命中窗口均值与观测上界。例外是单块（≤512 B）写，仅 147 µs。
2. **两个方向的每字节边际成本相同**：写 9.11~10.43 MB/s、读 9.88 MB/s，折算 85.3 ns/B ≈ 铭牌总线 11.72 MB/s（23.4375 MHz × 4 bit）。
   此前"写 5.7 对读 9.5 MB/s"的差是固定项摊薄程度不同造成的假象。
3. **固定项里至少一半已实测是主机侧**：`owner 20.65% + poll 3.33% + park_sw 12.50% = 36.5% 墙钟 / 360 µs 每笔写`（1447 个 executor 窗口）。
   其中 `handoff`（中断 → 执行器恢复，239~346 µs/笔）**按构造 100% 是内核软件时间**；机制候选是 owner 循环所在的 Fair 线程与协议栈线程同权重、同 700 µs 片长时的**条件抢占被拒**。
4. **每笔字节数被 `packets = 4`（6144 B）钉死**，而 credit **不系统性夹取**：`credit max` 中位 131、1105/1154 个窗口 ≥31（直接读数），
   `aggregate_limit()` 在 credit ≥34 时不夹；把 credit 均值五等分，`backoff`/写从 1.649 掉到 0.000 而速率只从 5.21 变 5.07 MB/s（−3%）。
5. **时钟不是主因**：翻倍上界在 1.15×（窗内口径）到 1.34~1.56×（事务层口径）之间，两者都小于 2×；但厂商侧实际时钟仍无读回，该项保持"待一次读回"。

**仍未定论的一项**：固定项在"设备反压（固件不放行）"与"主机侧 park / 中断恢复 / 拷贝"之间的最终归属。

### 6.2 第三阶段成功标准

1. 上述归属由**观测**给出定论，而不是由推断给出；
2. 每轮读数按**时间口径**报告（已记账事务占窗口比例、`supply_nanos` 三档占比、每类 Σbytes/Σµs），credit 报告带采样偏置，
   `retries`/`ack` 计数的语义与增量口径修正；
3. 聚合上界（`aic,tx-aggregation` / `aic,tx-aggregate-bytes`）在**同一热点会话内**做 K=4 与 K 提高的成对对照；
4. 时钟线由厂商侧一次 `debugfs` 读回坐实或关闭；
5. 任何收益只在同会话对照下宣称；跨会话数字仅作观察。

### 6.3 首轮：观测裁决轮（零行为变更）

首轮**不改任何行为**：不改聚合上界、不改 credit 语义、不改完成匹配与取消路径、不改 RX 优先级、不改 owner 结构。
只增加三组观测与一组口径修正，使下一轮的每一个行为改动都有同会话基线。

**M1 —— 写跨度按提交时 credit 分桶。** `drivers/net/aic8800/src/device/probe.rs` 为每笔写记录提交时刻读到的 credit，
按 `2 / 3–6 / 7–15 / 16+` 四桶分别累计笔数、跨度合计与字节合计。
判读：跨度随 credit 单调上升 ⇒ 设备反压成立；基本平坦（斜率 |Δ| < 50 µs）⇒ 固定项在主机侧。

**M3 —— SDIO 提交/完成边界时间戳。** 在适配层记录一笔 SDIO 请求从"交给主机控制器"到"完成被消费"的两个时刻，
把 `park_hw` 拆成"控制器执行"与"提交延迟"两段。

**M6 —— 已打印字段的按时间口径派生量。** 新增 `[wifi-probe-time]` 三行，直接给出：已记账事务合计与占比、
每类事务的忙时与占比、每类每字节纳秒数（与总线的 85 ns/B 直接可比）、`supply` 三档的按时间占比、
写跨度按 credit 分桶、以及按设备中断切分的前后两段。判读时以这三行为准，原两行的均值只作对照。

**口径修正**（均为报告层，不裁剪任何现有探针）：

- `credit` 报告附"读次数 / 写次数"之比，使采样偏置可见；
- `gap` 的 rx 分桶改名为"空档期间的 RX 事务数"，并注明它只描述共现、不描述因果；
- 明确区分 `ChainMiss::Idle`（`prepare_next_transmit` 之后判定）与 `supply none`（完成时刻采样）两个不同义的量；
- `open_window` 重置 `last_write_done` / `in_flight` / `rx_since_write` / `backoff_since`，消除窗口边界的跨界样本；
- 均值与计数在字段名上区分（`*_us_avg` 对 `*_count`）；修正 `probe.rs` 中与实现不符的采样时刻注释。

**遥测修正**：`accept_station_info` 的打印门不再键在含 `rssi` 的速率描述符上，改为计数器变化即打印（或每周期打印），使逐秒 ack 增量可得；
`retries` 字段改名以体现它是保护帧组的重试上限（配置常数）而非观测到的重传次数；报告 ack 时给出增量而非累积值。

### 6.4 第二轮：聚合上界选值轮（一个行为变量）

把每笔写的帧数与字节数上界从默认的 4 帧 / 6144 B 提高，扫 K ∈ {4, 8, 16, 32}。
两个上界是独立的：`aggregate_limit()` 取 `min(credit − 2, packets)`，而 `bytes` 是另一个上界，
因此两个 FDT 属性必须同时给出；`fdt.rs` 的解析期校验要求 `bytes ≤ queue_size × frame_size`，取值前先核对 DTB 的队列尺寸。

判据用**机制读数**而非仅吞吐数字：`[wifi-probe]` 的 `size blk` 分布与 `bytes/写` 是否真的成形为新 K；
按 §6.1 第 1 条的模型，`K=32`（B ≈ 48 KB）对应 `span ≈ 480 + 0.096 × 48000 ≈ 5.1 ms`、约 9.4 MB/s。
若模型成立而吞吐不随之上升，则说明瓶颈不在聚合粒度；若模型不成立（跨度不随 B 线性增长），则固定项模型本身需要修正。

| 轮次 | 变量 | 结果 | 结论 |
| --- | --- | --- | --- |
| 观测裁决轮 | 无（零行为变更） | 写往返 **35% 是设备报完成之后的主机时间**（`isr` 中位仅 2 µs）；保留位 credit 桶 0 笔 | 判为主机侧，且定位到完成路径而非提交路径（§2.22） |
| 聚合上界轮 | `aic,tx-aggregation` 4 → 32 | 字节/笔 5.6 → 18.7 KB，每字节 189 → 133~144 ns/B，发送 +23~37% | 与 `F + r·B` 模型一致（§2.23） |
| 发送环对照轮 | `aic,queue-size` 32 → 64 | 写更大（34–65 桶 21.7 → 33.3 KB）但**加权 ns/B 不变**、吞吐不变 | 环深不是约束（§2.25） |
| credit 等待轮 | 薄池（< 8）不放小写，等一档再问 | 小写占比 29.3% → **7.4%**、写中位 23.0 → 29.3 KB、发送 36.9 Mbps、慢尾收缩；每字节成本同口径为按笔 174.9 → 152.4、按字节 139.3 → 135.4 | **机制已确立；收益幅度待同会话对照判定**（§2.27） |

**当前位置**：

1. **主机侧的聚合粒度已到本轮实测的上界，但"空口用不掉"的判据不成立。** K=4→32 有效、环 32→64 无效；
   空口读数 `mpdu/ampdu` 在有流量样本里中位 **8.0**、上四分位 **15.0**、最大 **40.0**，
   与我们每笔交出的约 20 帧（29.3 KB）同量级，**不能据此关闭"继续加 K"**（§2.27）。
2. **发送侧剩下的最大已知项是完成路径的 350~400 µs/笔**（唤醒 → 调度恢复 → 取走完成）；它已从一笔的 35% 降到约 13.6%，
   但仍是唯一"已知在哪、且完全在主机手里"的一段。执行方案 §3.5 的 RX 优先级红线不受影响（`isr` 只有 2 µs，说明问题不在中断处理里）。
3. **接收侧可以放下**：实测批上限 63 块（31.5 KiB）、refill 约 8 ms；同口径折算（平均批 42~45 块 ÷ 8 ms）约 **21 Mbps**，
   低于实测接收吞吐（31~34 Mbps），即卡的交批节奏足以供上主机；重武装时卡中断已 asserted 的比例仅约 2%，说明也没有丢通知（§2.25）。
4. **空口侧第一次有了观测手段**（`[wifi-rc]` 的 `mpdu`/`ampdu`），但它给的是观测而非杠杆：
   当前聚合深度在 1~40 之间（中位 8），要判断它是否偏低，需要与同刻的 MCS/rssi 对齐看趋势，或与厂商在同等条件下的读数对照。
5. **已关闭**："上游供帧"（饱和窗口约 7%）、SDIO 时钟（上界 <1.6×）、40 MHz、RX defer、ack 计数比值（口径更正，§2.26）。

**下一步的两个候选**（都还没开始；这两项做完之后的取舍见 §6.8 的设计保留清单）：

1. **完成路径分段**：把写往返的中断后段再拆（唤醒 / 调度恢复 / 取走完成），据此决定是动唤醒路径还是取走完成的软件链；
   同一批里还有 RX 交付链的拷贝与分配（整块 DMA 缓冲先 `new_zero` 再被 DMA 覆盖、到协议栈前约 5 遍拷贝）。
2. **空口侧对照**：把 `mpdu/ampdu` 与同刻 `[wifi-sta-info]` 的 MCS/rssi 对齐，判断聚合深度是否随速率档变化；
   这一步只产出观测，除非能拿到厂商在同等条件下的同类读数。
3. **credit 等待的同会话对照**：按 §6.2 的口径纪律，收益幅度必须在同一热点会话内成对测出才算判定（§6.8 的 A 类定级依据）。

### 6.6 板测协议增补（第三阶段）

沿用 §4.3 的全部约定（两个敏感操作、每轮重启热点、参考臂、代理关闭、姿态确认、会话健康记录），另加：

- **聚合上界对照必须在同一热点会话内成对完成**：先测观测镜像（K = 默认），再测聚合镜像（K 提高），两轮之间**只重启板卡**并记录姿态与 MCS 分布；
  参考臂异常的轮次整对作废、重测。
- 每轮归档 §6.3 的三组派生量，使"设备 vs 主机"的归属判读不依赖事后再算。
- 单次烧录仍按"同一次启动内完成连接、TCP TX、TCP RX、双向"执行，并记录遥测的 `format`/`mcs`/`rssi` 分布与 ack 增量。

## 7. 第四阶段（2026-09-28 起）：把 CPU 的活与总线的活对齐

### 7.1 阶段命题

前三阶段把瓶颈定位为「每笔事务的固定开销 + 事务间空档」，并逐项测出固定项的构成。第四阶段换问题：

> **每笔写的主机侧工作（准备数据相）到底有多少，能不能不与总线串行。**

**硬约束：本板单核**（启动日志 `smp = 1`，设备树只有一个 `cpu@0`）。只有一条线程，
所以"重叠"只能是协作式的——省的是等待时间，不是靠并行。任何以"多一个核去做准备"为前提的设计都不成立。

### 7.2 已确认的事实（读代码 + 实测）

- 一趟写的主机侧要完整搬运 payload **五遍**：`take_tx_frame` 把运行时**池化的 DMA 缓冲** `to_vec()` 成普通 `Vec`（`rdif/owner/output.rs`）、
  建帧（`ethernet_tx_frame`，分配 + 清零 + 拷贝）、拼接（`ActiveTx::append_frame`）、
  `wire_bytes()`（分配 + 拷贝，**每个状态机步都重来一遍**）、
  DMA 缓冲（`rdif/owner/operation.rs` 的 `CpuDmaBuffer::new_zero` + `copy_from_slice_cpu`）。
  每次写还各分配一次 DMA 缓冲，完成后直接 `drop` 释放（接收方向同样）。这是**读代码得出**的，尚无板测计数器。
- 两道挡住"零拷贝到 DMA"的墙：**分层**——`device/` 这层拿不到 `DeviceDma`/`SdioCard`（整个 crate 里 `DeviceDma` 一次都没出现），
  聚合状态机只能产出 `AicAction::SubmitSdio(SdioRequest)`，要池就得从 `rdif/owner` 注入并拆掉
  `SdioRequestKind`/`AicAction` 的 `Clone/Eq/PartialEq` 派生；**所有权**——聚合缓冲**不能** `mem::take` 进请求，
  因为 `continue_transmit_pipeline` 会把请求放进 `io.next`，而 `discard_pending_transmit` 能在提交前丢掉它，
  那笔写之后还要再成形，聚合内容必须还在。
- **TX 自身零重叠**：`prepare_next_transmit` 在 `active_tx` 非空时直接返回，写在飞时不准备下一笔。
- credit 薄时的等待期间，写**已经成形**（`consume_transmit_flow` 先拼后读流控），
  所以等待时间目前只用于重读流控，且每次重试都会再走一遍 `wire_bytes()`。
- 段级读数（前几轮实测）：post-IRQ 396~415 µs、`isr` 2 µs、固定项 F 445~604 µs、`handoff` 239~346 µs。

### 7.3 第四阶段先补的空白

1. `pre` 段内部无分段——准备 / 命令相 / 卡延迟混在一起。**本轮补不了**：`device/` 这层没有任何时钟，
   `now` 一律由运行时在 owner 调用入口传入，同一调用内部量不出准备耗时（量出来恒为 0）。要测就得往设备层引时钟，
   那是另一条改动，本轮不做；
2. 准备段耗时与 memcpy 带宽**没有数**。本轮改用**同会话、同尺寸桶的写跨度 A/B**替代：两臂在同一热点会话内、
   按 `write credit` 分桶的 `avg=` 配对比较，差值就是被消掉那几遍拷贝的时间价值（**不假设 memcpy 带宽**）；
3. park（墙钟 12.5%）期间 CPU 究竟给了谁——**未知**，它决定"拿等待时间做准备"是真收益还是从别人嘴里抢时间；
4. 拷贝次数只有代码推断，没有板测计数器（确定性读数，不受会话噪声影响，是本轮最可靠的判据）。

### 7.4 首轮：一份内核 + 三个 DTB 臂（一次会话测完）

同一份内核，只换 DTB（沿用既有做法：镜像同源、只差设备树）：

| 臂 | 旋钮 | 回答什么 |
| --- | --- | --- |
| A | 现状（准备走原路径、credit 等待开） | 基线 |
| B | 准备走直接路径 | 消掉多余拷贝值多少 |
| C | credit 等待关 | **上一轮 OCR 审查要求的同会话对照**，给"薄池不放小写"定级 |

镜像内容：

- **零行为探针**：每笔写的建帧分配次数与拷贝字节数、追加进聚合的拷贝字节数、交接拷贝字节数、`wire_bytes()` 调用次数
  （全部是**确定性计数器**，不受会话噪声影响，本轮主证）；
- **直接准备路径**（旋钮 `aic,tx-prep-direct`，默认关闭）：建帧直接写进聚合缓冲、去掉追加时的整帧再拷、
  去掉 `wire_bytes()` 的按步全量分配，交给请求的那一份改用可复用 scratch；
  第一遍（`output.rs` 的 `to_vec`）与最后一遍（DMA 缓冲）**本轮不动**，它们属下一轮的跨层所有权重构；
- **credit 等待旋钮**（`aic,tx-credit-wait-us`，0 = 关），默认维持现状值；
- 板测期间跑 `apps/starry/ebpf/sched_trace`（挂 `sched_switch`），**不改驱动**地回答空白 3。这是第二轮瓶颈审查记下的零代价项 M-K1。

判据按可靠性排序：**拷贝次数/字节数（确定性计数器，主证）** > 同尺寸桶的写跨度 A/B（同会话）> 吞吐（同会话内才作方向）。

### 7.4.1 本轮的读数口径，先登记（按 §2.28 的六项）

分析前先定死，避免重演"算完才被审查揪出口径"：

| 读数 | 总体 | 加权 | 范围 | 粒度 | 可比性 | 选样 |
| --- | --- | --- | --- | --- | --- | --- |
| 每笔拷贝次数 / 拷贝字节数 | 每一笔写 | 不适用（确定性计数） | 整段合计 + 按写大小分桶 | 无时间戳 | 新增计数器，无跨提交问题 | 全量 |
| `wire_bytes()` 调用次数 / 笔 | 每一笔写 | 不适用 | 同上 | 无 | 同上 | 全量 |
| DMA 缓冲分配次数 / 笔 | 每一笔写 | 不适用 | 同上 | 无 | 同上 | 全量 |
| 写跨度（代替准备段耗时） | 每一笔写 | 按 credit 桶给 `avg`/`bytes`（探针现有口径） | 活跃窗口集合，并注明窗口数 | owner 调用入口，小写会被量化 | 既有字段 | 全部活跃窗口，不挑；**A/B 必须同会话、同桶配对** |

**本轮特有的两个陷阱，先说在前面**：

1. **准备段的子段之和等于总跨度是计时口径本身**（和 §2.22 的 `irq split` 同一种构造）。
   它是**恒等式，不算验证**；证据只能用子段的绝对值与占比。
2. **"拷贝耗时"是折算，不是实测**：拷贝字节数是确定性的，但从字节数推到时间必须假设 memcpy 带宽，
   而这个带宽本轮**没有测**。除非当轮测出带宽，否则只报字节数与次数，**不把它折算成 µs**、更不折算成吞吐收益。
3. **准备段内部不再分段**：设备层没有时钟（`now` 只由运行时在 owner 调用入口传入），同一调用内量出来恒为 0。
   本轮用"同会话、同尺寸桶的写跨度 A/B 差值"作为那几个被消掉拷贝的时间价值，**不引入时钟**。

### 7.5 本轮不做、留给后续的候选

- **攒批**：等 credit 时把新到的帧并进当前写（等的时间变成"攒更大一批"的时间）。不新增缓冲，但要重算 credit 账，且与"薄池不放小写"的收益相互作用。
- **双缓冲 / 准备与飞行重叠**：需要第二块缓冲，牵动"单笔在飞"契约、token 归属与取消路径——本分支最贵的一条红线，先在 7.4 拿到准备耗时再定。
- **SDIO 描述符链（scatter-gather）**：若 `cv181x-sdhci` 支持，主机可完全不拼缓冲；支持与否待确认。

## 8. 第四阶段第二轮（2026-09-28）：设备层时钟与全归因探针

### 8.1 本轮解决的问题

7.3 说"准备段内部补不了，因为设备层没有时钟"，7.4 的归因探针（`owner step`）把两个界交给运行时写，
而运行时只有 WiFi **控制请求**那条路会调用它——发送写在**数据面**被取走，所以整场会话一个样本都没有。
本轮把这两件事一起改掉：

- **时钟由平台借给驱动**：`AicRdifOptions::probe_clock`（`Option<fn() -> u64>`，与 `rx_defer` /
  `tx_prep_direct` / `tx_credit_wait` 同属"Diagnostic"项），由 `drivers/ax-driver` 填
  `axklib::time::monotonic_nanos`。它与运行时的 `AicInput::now`、与中断戳**是同一个函数**
  （`axruntime/src/klib.rs:278` → `ax_hal::time::monotonic_time_nanos`），所以同域可相减。
  时钟不存在时探针报**无样本**（每项都印自己的 `n=`，并印 `clock=on/off`），不报 0。
- **段由驱动自己量**，不再依赖运行时的调用边界。

### 8.2 分段与它们真正划分的区间（先登记，再算数）

一笔事务（从 emit 时刻到它的完成被取走）：

| 段 | 界定 |
| --- | --- |
| `dispatch` | emit → 传输层接手 |
| `dma` | 取 DMA 缓冲 + 填内容（写）/清零（读）+ 交给设备 |
| `program` | 描述符表与寄存器编程（`submit_*_dma` 调用本身） |
| `bus` | 编程结束 → **结束该事务的中断**；含命令相、卡访问、数据相，以及控制器让 submit 推迟的命令 inhibit 等待 |
| `isr` | 该中断处理函数自身 |
| `post` | 该中断处理结束 → 本步 owner 入口（唤醒） |

一个窗口（每个写周期）：

`周期 = 上述往返 + teardown + form + bytes + pull + release + rx_copy + rx_parse + report + credit 等待 + 残差`

- `teardown`：核心对完成写的记账（归还 token、扣 credit）
- `form`：成形写（取帧、拼聚合）；**在 `prepare_next_transmit` 内部打点**，因此链式续写那条主路径也在里面
- `bytes`：把写自身的字节拷成请求字节（含块对齐补齐），在唯一做这件事的函数里打点
- `pull`：RDIF 环 → 核心队列
- `release` / `rx_copy`：**分开**——写只释放缓冲，读还要分配并整篇拷出；合并会把抢占 TX 准备的那项开销藏起来
- `rx_parse`：接收批次拆解
- `report`：一次窗口上报本身（约 40 行串口输出，几十 ms；它记在**下一个**窗口）

`advance` 行 = 一次 `AicDevice::advance`，按它取走的完成所属类别归档，**没取到完成的步归到 `other`**
（因此每步都有归属，可与段相减）。它与 `steps=` 不是同一个计数器（后者是 owner 循环迭代，一步可含数次）。

### 8.3 本轮相对旧读数的**语义变更**（跨轮不可直接比较）

1. **往返起点从"owner 调用入口"改为 emit 时刻**。旧口径下，续写那一步的跨度里含了它自己的成形与上一笔的收尾；
   新口径只量事务。`write n avg` / `irq split pre` 与既有各轮**不可直接比较**。
2. **`pre/isr/post` 与 `bus` 归到"结束该事务的中断"**，而不是"这段时间里最后一次中断"。
   旧口径会让落在 post 窗口里的卡中断把宿主唤醒时间记进 `bus`（估计 10~20% 的完成受影响，方向与假设相反），
   并在经 rearm 缓存取走完成时整条丢掉 split（现在计入 `split drops=`）。
3. **同一段可被打断**：leg/stage 是任务上下文的墙钟区间，别处中断的处理时间落在其中，而 `isr` 只报完成那一次。
   因此"`isr` ≈ 2 µs ⇒ 中断处理可忽略"这个推论不成立。
4. **仪器自身开销**：一笔饱和写约 30 次读时钟（≈1.5~3.7 µs，占往返 0.13~0.35%），总量上可忽略；
   但每段带一次读数（40 ns 分辨率）的加性偏移，与 `bus by write` 拟合的固定项退化。

### 8.4 本轮修正的历史结论

- **B 臂"每写分配归零"是计数器位置造成的**：`wire_bytes calls` 只在 framed 分支自增，direct 分支同样每笔
  拷一次、也因 `mem::take(tx_scratch)` 每笔重新分配（`tx_scratch` 实际没有复用）。本轮改为两臂都记
  `copies`，`wire_bytes calls` 保留原义并注明只描述 framed 臂；direct 真正消掉的是**每帧缓冲**（`prep frames n=`）。
  §9 的第 1 条结论按此更正。

### 8.7 本轮结果与结论（2026-09-29 实板）

镜像是 `sg2002_starryos_wifi_sta_attrib2_20260928.img`（编译期 STA 凭据 `aasta`；缺凭据或取错 SSID 的两种失败现场见 §8.5）。
日志 `[com COM6] (2026-09-29_065738)`，纯 TX 与双向各取 10 个稳态窗口**分别统计**。

**仪器达标**：`pre` = `dispatch+dma+program+bus` 逐窗闭合（±9 µs / 0.3%），四条腿样本数等于写笔数，
`写笔数 × 周期 = 96.3% dt`。§8.6 要求的五件事全部读到：闭合 ✓、bus 分桶拟合 ✓、八段 ✓、`advance` 四类 ✓、
`split drops` ✓（只落在接收/控制侧）。

**结论一：总线不再是可动项。** `bus` 两项拟合边际 ≈ 11.2 MB/s、截距 ≈ 0，即数据相已达总线原始速率（11.72 MB/s）的 96%，
接收读 99.5%。第三阶段"每笔固定开销 445~604 µs"是旧往返口径（起点在 owner 调用入口）的产物，**按 emit 锚点重测不存在**。
只在总线上做文章已无空间。

**结论二：周期的一半以上不是往返，而是我们自己停着。**

| | 纯 TX | 双向 |
| --- | ---: | ---: |
| 周期 | 5310 µs | 6459 µs |
| 往返（占周期） | 2458（46%） | 2803（43%） |
| 空档 | 2852 | 3655 |
| ├ `advance` 工作 | 362 | 539 |
| ├ `pull` | 105 | 121 |
| ├ credit 退避 | **1017** | 418 |
| └ 其余 | 1354 | 2506 |

**结论三（本轮最重要的机制）：完成路径空手结束，环里的帧没人取。**
写完成时 RDIF 环非空 62.6%/53.9%，但续接只从核心队列取帧，核心随即返回 `WaitForInterrupt`，
owner 立即结束本次调用（`rdif/owner/progress.rs:401-406`），于是同调用中排在后面的环→核心 pull
（`submit_one_tx`，`progress.rs:320`）不执行，下一笔要等下一个外部事件 ⇒ 空档 2.9/3.7 ms。
旁证：`chain write` 0%、`chain flow` 32%/26%、`chain idle` 49%/53%；`supply` 里 core+ring 占窗口 21–23%，
而"哪里都没有帧"只占 19–22%。

**下一步优先级据此改写**（与并行设计文档 `gpt/aic8800-hardware-async-pipeline-design.md` 的对照见瓶颈文档 §2.29）：

1. **首选**：让完成路径在环里有帧时**不要空手结束调用**——在返回等待前做一次有界的环→核心 pull（或在 owner 侧
   允许再走一轮 loop）。改动在 owner，不动核心分层、不动"单笔在飞"，直接冲着那 2.9/3.7 ms 的空档。
2. **次选**：credit 退避（纯 TX 1017 µs/笔）与续接里的 `chain flow`（缓存 credit 落到保留位就改排流控读）合并处理。
3. **`post`（389 µs/笔）** 独立保留为调度归因项。
4. **prepare-ahead（逻辑双槽）降级**：它的价值上界是 `P`/周期 = 7.1%/9.8%（双向 7.2%/9.6%），
   且其证据里"完成前 RDIF 非空 62.6%"恰恰说明**帧已经在环里**——缺的不是"提前成形"，而是"没有去取"。
   若第 1 项落地后空档仍大，再按设计文档的状态机方案推进。

## 9. 第四阶段第三轮（2026-09-29）：完成前交帧

### 9.1 改动（都在 owner 内，两处）

1. `advance_with_cause` 的步内顺序由「init → active → control → pull → tick」改为
   「init → control → **pull** → active → tick」：环里已有的帧在**在飞请求被推进之前**交给核心。
2. 这次交付若换来核心的 `WaitForInterrupt`、而此刻仍有在飞请求，则不结束本轮
   （`handover_keeps_the_step`），继续把该请求推进到完成。

同一处重排把控制请求块也移到了在飞请求之前，这带来本轮的**第二个目标**（见 §9.5）：
控制事务进行期间若有一笔写在飞，取消立即对该写生效。核心分层、单笔在飞、完成先于 card 事实的顺序、
以及"每轮驱动至多续一次"的上界都不动。

### 9.2 为什么必须提前到完成之前（对 §8.7 第 1 项的判读修正）

核心的续写只在**取走完成的那一刻**找帧：

```
consume_completion → consume_transmit_data → continue_transmit_pipeline
                   → prepare_next_transmit   ← 从核心队列取帧
                   → 取不到就记 ChainMiss::Idle 并返回
```

此后到下一笔写之间它不会再找第二次（`drive_ready` 里的 `prepare_next_transmit` 是给"这一笔没有续写"
的那次驱动用的，且它排在 mailbox、遥测与接收扫描之后）。所以 §8.7 设想的"**返回等待前**做一次有界的
环→核心 pull"只能把帧搬进核心，**排不出续写**，那一笔仍要走 `drive_ready` 的老路，先给接收扫描让路。
把 pull 提到完成之前，完成时核心才有一帧可续，续写被排进 `io.next`；而 `io.next` 在下一次 advance 的
**顶部**就被发出（`advance_once` 里它在 `io.pending` 之后、`drive_ready` 之前），因此那一笔绕过了
mailbox、遥测与接收扫描。

### 9.3 判据（同一镜像一轮板测即可读；口径已按 OCR 审查重写）

**本轮同时动了被测量与观测器**，所以先登记哪些量不能跨轮比：

| 量 | 为什么不能在两轮之间相减 |
| --- | --- |
| `supply ring/core`、`rdif_at_write` | 采样点是"写完成那一刻"，而本轮把取帧挪到了该点之前——`rdif_at_write` 按构造会塌到 0，`supply` 三档的构成被重排 |
| `pull avg`、`advance other` 的样本数 | 取帧现在也会在"有请求在飞"的迭代里运行（空取帧与只投喂的推进都进了各自的样本总体） |
| `gap` 各档均值 | 计时起点（emit）相对取帧的位置变了 |

可跨轮比较的是：`chain *`、`tx_writes`、`size blk`/`bytes=`、`period_avg/max`（须与写长度同读）、
`scans/deferred/tx_ready`、`credit backoff`。

验收读数（同一窗口内读，不相减）：

1. **次序的足迹**：`pull in_flight n=/frames=` 显著非零。旧步序下该打点结构上不可能看到在飞请求
   （在飞块的 `Pending` 先 `return`），故此值必然为 0 ⇒ 非零即证明新次序在跑。
   注意它是**足迹不是效果**：若把 `pull in_flight frames` 与 `pull frames` 同量级、
   而 `chain write` 仍 ≈0、`chain idle` 仍停在 49%/53% 量级，结论是"交付了但完成没续接"。
2. **闭合式**：`chain write + flow + idle + busy + backoff + not_ready + yield = tx_writes`（被取消的完成不记账）。
3. **收益**：`chain write`/`chain flow` 上升、`chain idle` 占比下降（上一轮 49%/53%），
   幅度受 §9.4 的上界约束。
4. **不退化**：`[wifi-probe-rx]` 的 `reads`/`bytes`/`rx delivered`、`control n`、
   往返三项（`bus`/`dma`/`post`）与吞吐。

按口径纪律，跨会话吞吐只作观察，机制读数（`chain`、`pull in_flight`）才是判据。

### 9.4 已知上界

核心的"每轮驱动至多续一次"（`io.chain_used`，只在 `drive_ready` 里清）使续写只能落在**每隔一笔**上：
续写发出后那一轮没有走 `drive_ready`，`chain_used` 仍为真，下一次完成会记 `ChainMiss::Yield` 并把这一笔
让给驱动路径（接收扫描）。因此本轮可及的是"约一半的写提前于接收扫描发出"，不是全部；
如果板测显示收益被这个上界卡住，再单独立项讨论它（它会直接影响接收侧的让位比例）。

### 9.5 独立审查的结论与落地（2026-09-29）

一轮 6 实例 OCR 审查（principal ×2、quality ×2、performance、reliability）判定 **REQUEST CHANGES**
（1 阻断 / 3 应修 / 8 建议），对本章的修正有三处：

1. **阻断项**：§9.1 的重排把控制请求块也一并前移，"取消"因此首次在写在飞时被消费——核心要求
   `AbortSdio` 中止该笔写、其载荷按完成上报。这条此前不可达（旧步序下控制块只在无在飞请求时可达），
   而设计文档写着"取消与资源回收的顺序均不变"。审查给出两条路（回退控制块 / 声明为第二目标）；
   **采纳后者**：核心级 `cancellation_releases_the_write_in_flight` 表明 abort-on-cancel 是核心本意，
   回退等于把"写卡住时取消服务不到"重新引入。据此本轮的第二个目标是"声明取消语义"，
   落地为设计文档续接/取消条款改写、owner 提交路径的断言、以及设备级契约用例。
2. **应修（判据）**：新增计数器只是"次序的足迹"，验收判据改为上面的同窗闭合式；
   探针自身的窗口归属缺陷（只被 `report` 取走的计数在空闲窗口被顺延到下一个窗口）一并修掉。
3. **应修（测试）**：本轮主体改动（步内顺序）此前没有任何测试能证伪——把它撤销全部测试仍绿。
   落地了设备级契约用例 `a_handover_before_the_completion_is_what_the_successor_is_queued_from`
   （交付早于完成 ⇒ 完成能排续写；不交付 ⇒ 排不出），并加了对 `self.active` 与核心在飞请求配对的断言。
   owner 层的步序仍无自动化守卫（`AicOwner` 没有 host 测试替身，替身需要可用的 `DeviceDma`），
   这一点由设计文档条款与板测足迹共同承担，登记为实现侧遗留。

其余建议的处置：探针命名与注释、`aic,queue-size` 上界（`fdt.rs`，触发核心静默丢弃需 ≥130）、
谓词改为正说、采样时机命名与"已发布为 advisory"的说明均已落地；
"把取帧移进完成漏斗"（审查中提出、并被指出**删不掉谓词**、只是换编码与换失败形态）登记为
板测之后的候选重构；接收保持窗口非 0 时"队列更常非空会让其条件更易成立"（`bulk_sender`）登记为开放项
（当前 DTB 该旋钮为 0，惰性）。

| `pull in_flight frames ÷ pull frames` | —（本轮新增） | ≈73% |
| `chain` 七项之和 = `tx_writes` | 闭合 | 闭合（**这是恒等式，不算独立验证**） |

`chain yield` 升到 34~39% 是 §9.4 的让位上界按设计工作。`rdif_at_write` 在本轮**按构造恒零**
（取帧已提前到完成之前），**不得与对照臂的 62.6%/53.9% 并列引用**——该信号在本轮失效。

**收益未兑现**

- 下行 **28.5 / 28.6 vs 28.6 / 27.9 Mbps（持平）**；RX 每窗事务数、每字节成本（122 vs 123 ns/B）与字节量一致 ⇒ **接收侧不退化**。
- 上行 **30.1（28.4~32.9）vs 30.2 Mbps（持平）**。周期与空档的"差异百分比"**不作结论**：round-2 复算表明
  它随窗口选入规则在 5493~5905 µs 间变化，落在同会话逐轮散布内。
- 双向板发 25.0 / 26.6 vs 29.5 Mbps：**不可判**（接收形状不同——A-MSDU 942/窗 → ≈0、接收量少 14%、一次接收塌陷）。

**时间到底花在哪（round-2 四条独立预算的收敛结果）**

  （fdrv `aicwf_sdio.c` 时钟块 ∈ `#if 0` 3184…3218、BSP `aicsdio.c` ∈ `#if 0` 1835…1868；活着的两处只服务非 D80）。

- 差距表现为**总线被喂饱的时间比例**：我们 ≈39%（`bus` 1956 µs × 403 笔 / 2000 ms = 788 ms），
  厂商跑 56.4 Mbps 必须让写字节约 7.2 MB/s ≈ 62%。
- 四条竞争候选，**现有读数不能择一**：(a) 主机侧供给节奏（含 cwnd×RTT 自限）；
  (b) 卡/空口反压（credit 池均值 12.2/132、`avg_mpdus` 5~15 对我们交付 32 帧）；
  (c) 每笔固定成本/事务率（~185 笔/s）；(d) **往返串行化**（`supply core` 80.8~85.3%、
  `queue_at_arrival 4+` 81~85%、`park_splits : tx_writes = 1:1` ⇒ 每笔写独占一个"完成→中断→交接→续发"回合）。

**下一步（round-2 之后的优先级）**

1. **零代码**：`lcn-sta-nowait.dtb`（= 现 DTB + `aic,tx-credit-wait-us=0`）同会话对照，判那 15~16% 值不值；
   判据：吞吐不变而总线占用上升 ⇒ 纯损失；写大小塌回小写档且固定成本吃回 ⇒ 保留。
2. **一条新读数**（round-2 五票无多数，四条各自成立）：解析 `chan_time/chan_busy_time/chan_tx_busy_time`

   前三条**已实现**（§9.7，镜像 `…_attrib3_20260929.img`，与 `…_attrib2_20260928.img` 只差内核），帧年龄仍待做。
3. **零成本**：厂商镜像 `cat /sys/kernel/debug/mmc1/ios` 的 `clock:`（应得 25000000），把时钟项彻底闭环；

### 9.7 归因探针深化（2026-09-29 实现，2026-09-30 实板）

上一轮把时间账收敛到「无事务在飞占窗口 46.9~51.9%、执行器 park 占 72~78%」之后，剩下的问题是
**执行器在等谁、空中是不是天花板、帧是不是根本没来**。三处此前只能推断的量改为观测，行为不变：

| 读数 | 出处 | 读法 |
| --- | --- | --- |
| `park_end irq/tx/rx/recycle/ctrl/other/none/timer` | `[netprobe]` | park 按**结束它的发布者**归档；`none` = 到达等待时事件已置位（该 park 从未睡下）；七项之和应等于该窗口的 `waits` |
| `busy=/txbusy= permille` | `[wifi-sta-info]` | 卡的 `chan_busy_time ÷ chan_time`、`chan_tx_busy_time ÷ chan_time`，按上一采样做差、以同一秒的信道窗口为分母 |
| `supply 0/1/2-3/4+` 与 `gap n/avg/max` | `[netprobe]` | 进 poll 时栈侧待发深度，以及相邻两次提交的墙钟间隔 |

**判据（上板前定下）**

1. **闭合**：`park_end` 七项之和 = 该窗口 `waits`；`timer` 只应出现在有截止时间等待的窗口。
2. **停驻去向**：`irq` 占多数 ⇒ 执行器确实在等设备（与 owner 占 22~23% 相符）；`tx` 占比高 ⇒ 协议栈供帧频繁打断停驻；
   `none` 占比高 ⇒ 执行器多数时候到达等待时事件已置位、并不在"睡等"（偏候选 (d) 的串行化图像）。
3. **空口是不是天花板**：`txbusy` 逼近 `busy` 且两者都高 ⇒ 时间花在空中；`busy` 很低 ⇒ 时间不在空中，在主机路径。
   字段单位厂商未文档化，只做**同一字段的差值**，不与 µs 混算。
4. **供给节奏**：`supply 0` 高而 `gap avg` 与设备写周期同量级 ⇒ 协议按链路速率供帧（"没有帧可发"是上层节奏）；
   `supply 4+` 持续非空 ⇒ 主机路径压着帧。
5. 以上四项都在**窗口内**读，不与上一轮做差（本轮同时动了被测量与观测器）。

**结果（2026-09-30 实板，镜像 `…_attrib3_20260929.img`，同一热点会话 4 个用例）**

- **闭合成立**：`park_end` 八项之和 = `waits`，76 窗逐窗通过。
- **停驻去向**：`none` ≈ **50%**（到达等待时事件已置位、从未睡下）；下行 `tx`/`irq` 26%/23%，上行 13%/14%；
  `timer` 下行 0.05%、**上行 18.1%**、双向 14.7%。`wait_kind deadline` 比 `timer` 多 5~12%，不可互换。
- **credit 等待 16.1% 墙钟**（上行，deadline park 4831 ms/30 s），与三条旧读数吻合。
- **供给**：上行 82% 核心有帧 / 18% 哪都没有 / `ring` 0；下行 85% 哪都没有。
- **信道占用失效**：77 个采样全 0；厂商的信道时间在 `MM_CHANNEL_SURVEY_IND`，不在 `get_sta_info`。
  下轮改读 survey 指示，或先打印原始值以区分「字段恒零」与「窗口不前进」。
- **墙钟账（上行）**：在飞 38%，非在飞 62% = 「没有帧」20% + 「有帧却在等」23%（内含 credit 16.1%）。

## 10. 第五阶段第一轮（2026-09-29）：前车成形（在飞窗口内排好下一笔）

§9.7 把可动项定在「两次搬运之间」：上行墙钟里 62% 没有事务在飞，其中「哪里都没有帧」20%
属上层节奏，「有帧却在等」23% 里 credit 自选等待 16.1% 是固件缓冲池策略，剩下约 7% 是
完成→中断→交接→再发的固有延迟。每笔写还要另付约 0.5 ms 的成形与 DMA 准备
（`attrib2`：`pull + form + bytes` 0.38~0.47 ms，DMA 准备 0.14~0.16 ms），这段此前排在完成之后。
本轮把其中的**成形**一段搬进在飞窗口。

### 10.0 阶段前提：为什么是「一个在飞 + 一个后继槽」

本工作线里的「双缓冲」**不是**两笔 CMD53 并发在飞。三条独立证据把边界钉死：

| 证据 | 位置 | 结论 |
| --- | --- | --- |
| 传统 SDHCI 只有一个在途硬件请求 | `drivers/blk/sdhci-host/README.md` | `queue_depth = max_submit_batch = 1` |
| 主机 trait 按单事务建模 | `drivers/blk/sdmmc-host/src/lib.rs` | 一次只接受一个事务 |
| IO 卡以唯一活动请求号拒绝第二笔 | `drivers/blk/sdmmc-protocol/src/sdio/io/mod.rs` | `active_io_request_id`，繁忙返回 `Error::Busy` |

因此本阶段不扩展为多笔总线事务并发、不新增 owner 线程、不引入 Rust `Future`，
也不把硬中断变成数据处理上下文；目标是「一个 host 事务在飞 + 一个 CPU-owned 后继槽」。

### 10.1 改动

1. **协议核心新增 staging 槽**。`DataPlaneState` 增加 `staged_tx`，与 `active_tx` 的分工是：
   `active_tx` 是请求路径读得到的「总线槽」，`staged_tx` 是还没被请求路径看到的「后手」。
   `prepare_next_transmit_inner` 在总线槽空闲时先把 `staged_tx` 提升进去、否则才成形；
   `form_transmit(limit)` 与 `extend_write(&mut ActiveTx, limit)` 改为操作局部写，聚合逻辑仍只有一份
   （`extend_active_write` 里那条「槽在本次遍历中消失」的防御分支随之删除——按 `&mut ActiveTx`
   形参它在构造上不可达）。
2. **只有已经交给总线的写才允许有后继提前成形**。仍在等流控读数的写会按读数继续从 `data.tx` 生长
   （`consume_transmit_flow` → `extend_active_write`）；提前成形的后继会先把帧取走，使它在总线上
   小于刚读到的 credit 所能支持的规模。因此 `advance_once` 只在 `io.pending` 是 `IoPurpose::TransmitData`
   且状态为 `Ready` 时调用 `stage_next_transmit()`，之后再返回 `WaitForInterrupt`——核心不会因此
   产生第二笔提交。成形上限再扣掉在飞写将要花掉的包数（`aggregate_limit().saturating_sub(in_flight)`），
   同一份 credit 不被两笔写重复认领。
3. **token 归属**。成形把帧拿出队列，因此在飞写与后手写各自持有自己的 token：
   `take_active_write_tokens()` 同时回收两个槽，取消（`finish_cancel`）、停机（`drive_shutdown`）、
   失败（`fail`）三条路径各归还一次。`bulk_sender()` 把后手写也算作「本方在发载荷」
   （`rx_defer` 默认 0，当前无行为影响，只是口径更正）。
4. **旋钮与探针**。新增 `aic,tx-prepare-ahead`（0/1，默认 1），
   `AicRdifOptions::tx_prepare_ahead` → `OwnerPolicy::tx_prepare_ahead` → `AicDevice::set_tx_prepare_ahead`，
   供同一内核下的同会话 A/B。probe 的 `chain` 行新增 `staged ready/missed`：每笔写完成时，
   后继是否已经成形。
5. **DMA 活动前缀公共契约**（下一步 owner 双槽的前提，本轮先落地）。
   `memory/dma-api/src/owned.rs` 增 `CpuDmaBuffer::capacity()` 与 `prepare_prefix(len)`，
   `DmaError` 增 `InvalidActiveLength`；`PreparedDma`/`InFlightDma`/`CompletedDma`/`QuarantinedDma`
   全链路携带活动长度——`len()` 返回活动前缀、`capacity()` 返回整个 backing，cache 同步与
   `segment()` 只覆盖 `0..active`，`into_cpu_buffer()` 恢复完整 backing，提交拒绝原样归还。
   `prepare_for_device()` 语义不变。消费方 `sdmmc-protocol`/`sdhci-host`/`dwmmc-host` 的
   `DmaError` 穷尽匹配补上 `InvalidActiveLength` 分支。

6. **停机语义核对（附带）**：确认核心侧停机**不做中止**——`advance_once` 在 `io.pending` 非空时
   先返回 `WaitForInterrupt`，`drive_shutdown()` 只在在飞写按原路径结算之后运行，与正式架构文档
   `docs/design/unified-sdio-aic8800.md` 的描述一致，无需改文档。该函数内部那段 `io.pending` 分支
   因此不可达，留待下次触及该函数时清理。
7. **`dma-api` 的活动前缀当前尚无调用方**：`prepare_prefix` 与全链路活动长度是下一步 owner 侧
   双槽的前提，本轮先落公共契约，还没有运行时代码使用它。

### 10.2 判据（上板后读探针行）

1. **机制**：`staged ready` 占 `tx_writes` 的比例显著非零，且 `staged ready + missed = tx_writes`
   （闭合式）。`staged ready` 恒为 0 ⇒ 在飞窗口内没有成形，机制没跑；`missed` 高而 `ready` 低 ⇒
   owner 在飞期间没有把帧交进来，应先看 `pull in_flight`。
2. **收益**：同一热点会话内 `aic,tx-prepare-ahead=1` 与 `=0` 两臂，比较 `period avg/max`、
   `chain idle` 与上行吞吐。**跨会话数字不作为证据。**
3. **不退化**：`[wifi-probe-rx]` 的 `reads`/`bytes`、控制事务往返、`size blk`/`bytes=` 分布、
   写笔数与 credit 分档——staging 不得改变每笔写的长度分布；`chain` 的 `busy`/`backoff`/`not_ready`
   仍应为 0。

### 10.3 已知上界

本轮只搬走「成形」一段。`take_write_bytes()` 的字节复制与 `ActiveOperation::submit()` 的
DMA 分配/填充仍在完成之后，因此预期增幅明显小于按 `pull + form + bytes` 折算的 6~7% 上界；
把后两段也搬进窗口需要 owner 侧准备好 backing，即下一步的双槽（§7.5 之外的第四阶段候选）。

**与 credit 问题的界线**：16.1% 的 credit 自选等待是固件缓冲池策略，本轮不改变它；
两臂对照时不得把它算作本轮效果，也不得与双缓冲效果混作一个变量。

### 10.4 上板前的预期（保留以对照）

上板前写下的下一步是 owner 侧 DMA 双槽：owner 持有一个（随后是两个）受上界控制的 ToDevice
backing，在 `Staged -> Submitted` 的门控通过之前就把成形写填进去，完成后回收。
它的接口与生命周期要求在这里自足记录：

- **提交点唯一**：`Staged -> Submitted` 才重新检查权威 credit、命令保留量与取消/停止状态，
  之后才消费 credit 并转移 DMA 所有权；准备阶段不得预留信用快照。
- **活动长度**：`dma-api` 的 `CpuDmaBuffer::capacity()`/`prepare_prefix(len)` 与四个 owned 类型
  （`PreparedDma`/`InFlightDma`/`CompletedDma`/`QuarantinedDma`）的活动前缀本轮已就位——
  `len()` 返回活动前缀、`capacity()` 返回整个 backing，cache 同步与 `segment()` 只覆盖
  `0..active`，`into_cpu_buffer()` 恢复完整 backing，提交拒绝原样归还。
- **回收与隔离**：只有 host 完成或 abort 之后确认设备停止访问，才能把 backing 回收为下一准备槽；
  无法证明时进 quarantine。
- **失败与取消**：提交前取消只归还 token 一次；提交后取消先停在飞事务，再处理 staged；
  停机不得在设备仍可能访问时 drop 或复用 DMA。

**当前状态：暂缓**——§10.5 的实测结果没有支持这一步的收益前提，重启条件见 §10.6。

| 上行 iperf3 | 38.0 | 33.4 / 36.9 / 37.2 / 36.4 | 38.0 / 35.3 |

`staged ready + missed = tx_writes` 与 `chain` 七项之和 = `tx_writes` 逐窗精确闭合（79/54/98 窗零违例）。

**② 但两者都没有把总线占空比推上去。** 总线腿占比在三臂之间是 35.8–36.1%，
上行吞吐的臂间差（0.6%–5%）落在运行间散布之内——`ahead0` 只有一次运行，
双向 TX 里成形开的臂反而快 2.4%，合池 A 33.20(n=7) 对 B 33.40(n=2)，
逐秒 Mann-Whitney p = 0.081。**结论是判不出次序，而不是某一臂更好。**

**③ credit 等待的构成被查清了，这是本轮最有用的一条。**
旋钮 `aic,tx-credit-wait-us` 只作用于 `consume_transmit_flow` 的**薄池分支**（`credits 3..=7`）；
**保留量分支（`credits <= 2`，`IO_RETRY` 200 µs）占 credit 等待约 78%，旋钮管不到**，
遥测（1 s / 2 s）、邮箱、启动与 SDIO 寄存器重试等截止时间来源同样不受它影响。
因此 §9.7 那条"上行 16.1% 墙钟"**不是空转**：等待在等固件池回填，好让下一笔聚合成更大的写。
去掉它之后写从 20.9 KB 掉到 18.6 KB，而占空比与吞吐都不动。

**④ 两条实现问题（未修，下一步的前置）。**

1. `stage_next_transmit` 的 `limit = aggregate_limit().saturating_sub(in_flight).max(1)`
   把减法放在策略上限**之外**：credit 充足时把成形上限从 32 帧压到 `32 − s_prev`。
   正确写法是 `min(credits - 2 - in_flight, 32)`——credit 紧时两者等价，
   credit 充足时后者不截断。判别性证据是该缺口只出现在"照缓存 credit 直接发出、不再走流控读"
   的带宽带里并随 credit 增大而扩大；**要证否需补逐笔 `s`/`s_prev` 插桩**，现有日志做不到。
2. 探针 `supply core/none` 只看 `data.tx`，看不到 `staged_tx`，
   于是成形开启的臂 `none` 虚高（24–26% 对 15.9%）。**下一轮必须先修，否则同样的误判会再来。**

### 10.6 下一步

按本轮证据，**不建议继续在这两个旋钮上调参**：两者的机制足迹都已被量清楚，
而限制项都不在它们身上——总线腿占比稳定在 36%，上行非在飞时间里最大单项是"没有帧可发"（栈侧供给节奏）。
下一步按性价比排序：

1. **补一个对照臂**（零代码）：把现成的 `attrib3` 镜像当第三臂，在同一热点会话里与 `ahead0`/`ahead1`
   用相同用例序列交错 2–3 次。它一次能分清"会话差异"与"本轮重构的公共路径改动"——
   `ahead0` 与 `ahead1` 都含那次重构，B 不是它的对照。
2. **修上面两条实现问题**，然后重跑同样的 A/B，看写长度差是否消失。
3. 只有 1、2 都做完且成形仍无总线层面收益时，才谈"是否降级 staging 槽"。
   注意即便吞吐不动，成形仍在 `chain idle` 上留下 7–10 个点的差，它是机制账，不是收益账。

## 11. 第五阶段第二轮（2026-09-29）：以「让 SDIO 尽可能忙碌」为目标重构

### 11.1 目标变更与验收口径

前几轮以吞吐为收益指标，两轮改动（前车成形、无等待）都有明确机制足迹，却都没有抬高总线占空比。
本轮改变目标：**不再追求吞吐显著提高，改以「异步架构使 SDIO 尽可能忙碌」为达成目标**。

验收分三层（口径先定，再读数）：

| 层 | 量 | 地位 |
| --- | --- | --- |
| A 架构 | **驱动侧空档**：总线槽为空、且任一单元有 ready offer 的墙钟，**按原因分类** | 必须达成 |
| B 机制 | `completion_to_commit`（取走完成 → 下一笔提交），出分布不出均值 | 回归守卫 |
| C 结果 | `bus_leg_share` 总线腿占比 | **仅观测**，不作验收 |

A 层必须分类后再看。其中「已成形却仍在等」是可消除的一类；「栈里没有帧」与「固件池读到 ≤2」
不是驱动的账。把这两类混进同一个百分比，A 就永远是个没有意义的数（§9.6 与第四阶段的读数已给出反例）。

### 11.2 前提更正：可动物不是当前编排

既有编排里的「每次调用推进一个可见转移」「`io.pending`/`io.next` 单槽」「一次完成结束一次调用」
「`chain_used` 让位」都是**实现产物，不是物理约束**。以它们为抓手思考重构走不出串行瓶颈。
本轮的物理约束只有两条：SDHCI 一次只允许一笔事务在飞（`queue_depth = max_submit_batch = 1`），
以及本板单核（`smp = 1`）。其余可动。

### 11.3 改动边界

| 层 | 能否改 |
| --- | --- |
| `drivers/net/aic8800/**`（含 `device/`、`rdif/owner/`、`rdif/device/`） | 主攻 |
| `drivers/ax-driver/src/net/aic8800/**` | 按需 |
| `drivers/blk/sdmmc-*`、`sdhci-host` | 默认可不动；若存在更好或更合理的异步实现则做 |
| `drivers/interface/rdif-eth`、`net/ax-net` 对驱动可见的**接口形状** | 不动 |
| `net/ax-net/src/queue_runtime/**` 内部 | 能不动就不动；确需动时先报备并带读数 |

### 11.4 动手前的三条硬判据（先量后建）

三条不通过，后面全部重做：

1. **交接空档的归因**。方案曾假设「2 次 owner 调用 + 1 个协议轮」会让交接空档坍缩；
   既有读数（`polls` 与 `owner_calls` 约 1:1、完成路径 350–400 µs/笔而 `isr` 仅 2 µs）
   指向抢占/唤醒延迟。先把这段按「调度恢复」与「驱动代码」分开计时，再决定这一步值不值。
2. **「单笔主机工作 ≤ 在飞窗口」**。只有 `settle + pick + form + copy + DMA 编程` 不超过本次在飞窗口，
   「有活即在飞」才成立。而按条数占 81% 的 RX/控制腿恰恰是短事务（CMD52 约 51 µs、credit 读约 86 µs、
   单块读约 134 µs 含约 90 µs 固定开销），对这些腿流水线前提不成立。先量每类事务的
   「在飞窗口 vs 主机工作量」，再定哪些腿该流水、哪些腿该串。
3. **`More` 路径的真实贡献**。方案曾把「poll 返回 `More` 时 owner 不被推进」当成大空档；
   饱和窗口实测 `owner_calls ≈ polls`，`finish_idle` 几乎每次都跑到，它的贡献可能约等于零。
   先计数，再决定要不要动 `ax-net`。

### 11.5 目标架构

「有界总线对象 + 独立推进单元」。

- **适配层（`rdif/owner/`）**：`AicOwner` 坍缩为薄壳，`advance`/`rearm_and_advance` 保留同名 trait 方法、
  内部转调 `OwnerDrive::round`，rdif 对外形状不变。新增 `BusManager`（持 `SdioCard`、唯一在飞槽、
  request-id 发生器与 `DmaStager`，**必须持有完整的 `ActiveOperation<H>`**，它是 IO 请求、枚举与主机
  总线操作三条完成通道共用的一把锁）、`Arbiter`（无 I/O、按
  错误/终止 > 控制 > RX > 普通数据写 > 遥测 选一笔）、`Harvester`（把一次完成翻成带 `Home` 的结局并
  扇出 credit 失效）、`TxLedger`（token 与 rdif DmaBuffer 的唯一权威表）、`DmaStager`、
  `OutputSink`（`try_publish` 尽力而为，**绝不 gate 仲裁**）。
- **纯 core（`device/`）**：`AicDevice` 改为容器，持 `Shaper`（含 `WritePool`）、`Receiver`、
  `ControlPlane`、`LifecycleFsm` 四个单元与 `EventMailbox`，不再有一进一出的 `advance`/`AicAction`/`AicInput`。
- **唯一入口 `OwnerDrive::round`**：排空事实 → 逐笔结算 → 每次结算后立刻仲裁并提交 →
  无活时让生产者预成形 → 重武装两个中断源并返回等待。

### 11.7 S6 的独立审查要求

S6 引入 DMA 所有权与取消语义的实质变化，动手前需独立领域审查**设计**，合入前审查**实现**。
下列五项必须逐条给出方案，缺一不可：

1. `ActiveOperation<H>` 的所有者与归还路径（含 `InFlightDma` 的 `ManuallyDrop` 语义）；
2. 三条完成通道（IO / 枚举 / 总线操作）共用一把槽的建模；
3. **park 不能由槽占用决定**：`HostProgressWait::Register` 类事务没有完成中断，
   必须由在飞操作自己的等待类型决定（`rdif/owner/progress.rs:540-555`）；
4. **取消三件**：总线控制通道、取消屏障（提交门前排空所有「已成形未提交」）、abort 后 DMA 隔离；
5. `WifiControl` 是第二条 owner 入口且带 `quiesce` 窗口（`executor/wifi.rs:96`、`startup.rs:234`），
   S6 必须和它对齐。

另有一条工程风险：`Arbiter` 不得用 `*const Option<Offer>` 借出生产者槽位——同步完成会在 `submit`
内回调生产者，存在别名与悬垂风险；用索引或 `&mut` 显式传递。

### 11.8 S0：已落地的仪器（2026-09-29）

`aic8800` 侧（`device/probe.rs`，另有 `data_plane.rs`、`rdif/owner/{operation,progress}.rs` 的调用点）：

- `owner_flush_blocked`：发布环满导致整步不推进的次数（`[wifi-probe]` 的 `flush_blocked=`）；
- 总线空转段：`note_tx_harvest_at` 取**完成中断进入时刻**为总线空闲的起点，`book_tx_harvest_gap`
  在块 DMA 提交前收口，量出「总线从空闲到再次被占用」的整段墙钟
  （`[wifi-probe-time]` 的 `harvest_to_bus=…us/… long=…`）。取中断进入时刻而不是核心取走完成的时刻，
  是因为后者已经把「调度恢复」算掉了，而判据 1 要拆的正是这一段。
  **收口点只有两个：块读与块写分支。** `Direct`（CMD52 类，含 credit 读与大部分 mailbox/控制）与
  `Bus` 分支既不调 `bus_begin` 也不收口，落在它们之间的空档既不进均值也不进 `long`，被静默丢弃；
  因此该读数的覆盖口径是「块 DMA 事务之间的空档」，引用时必须带上这一条
  （2026-09-30 复核 C2/C4 更正：本节原先写作「每一次事务提交」，与实现不符）。
  超过 20 ms 的空档不计入均值、单独计进 `long`——那是「栈里没有帧」的停摆，不是驱动自己的交接；
- credit 保留量分支单列：`credit_reserved_backoff`（`[wifi-probe]` 的 `reserve backoff=… avg=…us`），
  与薄池分支的 `backoff=` 分开；
- credit 双认领：`note_credit_over_claim`，记下成形时超出 credit 预算的笔数与超出的包数
  （`[wifi-probe]` 的 `credit_over n=… pkts=…`）。

`ax-net` 侧（`queue_runtime/executor/`，本阶段唯一一次触及该目录，均为打印既有或新增计数、无行为变更）：

- `more_round`：`poll` 返回 `More`、因此该轮不推进 owner 的次数（`[netprobe]` 的 `more=`）；
- `rearm_race`：重武装时发现已有工作发布的次数，即「若无该复查就会丢掉的唤醒」
  （`[netprobe]` 的 `rearm_race=`）。

判据 2（每类事务的在飞窗口 vs 主机工作量）由既有的 `[wifi-probe]` 分类往返与
`[wifi-probe-time]` 的 `legs`/`stages` 两栏共同回答，未新增计数器。

验证：`cargo fmt --all` 干净；`cargo xtask clippy --since dev` 与 `cargo xtask test --since dev` 全过；
`cargo test -p aic8800 --features host-test` 161 + 1 全过。S0 无行为变更，可与既有 `ahead1` 镜像直接 A/B。

### 11.9 S1：后继写的成形上限（2026-09-30）

缺陷在 `stage_next_transmit` 把减法写在了取最小值之后：`min(credits - 2, policy) - in_flight`。
它有两个方向都错的后果：

- **credit 充足时低估**。策略上限管的是**一笔写**，不与在飞写共享，只有读数共享。把在飞写也从策略里减掉，
  会在 credit 明明够一整轮突发时把后继压缩到 `policy - in_flight`；`.max(1)` 再兜底成一帧。
- **credit 紧张时高估**。`credits - 2 - in_flight` 归零时，`.max(1)` 仍然成形一帧，
  于是「在飞写将要花掉的固件缓冲」被后继再认领一次。

改为 `successor_limit(in_flight) = min(credits - 2 - in_flight, policy)`，未知读数取 0，
且在预算为零时**不调用** `form_transmit`——它无论如何都会先取一帧，靠传零是拦不住的。

`note_credit_over_claim` 因此恒为 0，它从「缺陷的证据」转为「双认领的回归守卫」。

同一轮修正一处探针口径：`write_done` 的 `core_ready` 原先只看核心队列与内部队列。成形到 `staged_tx`
的帧已经离开队列，只读队列会把「核心手里正握着后继」报成 `supply none`。`staged_tx` 计入后，
`supply` 三档才描述真实供给。

验证：新增两条单测（credit 充足时后继取满策略；读数已被在飞写花完时不成形），
都在改前的实现上必然失败（分别读到 1 帧与「仍成形了一帧」），改后通过。
`cargo fmt`、`cargo xtask clippy --package aic8800`、`cargo test -p aic8800 --features host-test`
（163 + 1）全过。

### 11.10 上板结果与判据裁决（2026-09-30，日志 `(2026-09-30_095951)`）

一次启动内四个用例（下行 31.6 Mbps、上行两遍 15.4 / 32.4、双向 RX 11.6 / TX 23.1 Mbps），
读数来自新增的仪器本身。完整口径与数字见跟踪文档「第五阶段第二轮」；此处置放两条判据的裁决
与由此产生的阶梯修订。

**判据 3（`More` 路径）——贡献≈0**：`more` 全日志合计 155 / 200473 polls = 0.077%，91 窗中 76 窗为 0。
**S8 删除**，`ax-net` 的执行器循环不必动。

**判据 1（交接空档归因）——唤醒/调度恢复是整段里最大的一项**（数字按 2026-09-30 复核更正）：

- 总线从空闲到再次被占用的整段（`harvest_to_bus`）重测段逐窗 696–836 µs（均值 753）；
  完成中断的 `post` 逐窗 368–455 µs（均值 413）。
- 占比**必须写口径**：逐窗比值再平均是 45.6–63.9%，按样本加权（各自求和再相除）是 **36.0%**——
  差在分子只算 TX、分母含读写。**以样本加权的 36% 为准**；此前写的「55–65%」是把「均值到最大值」当成了区间，
  且分子分母跨总体，作废。
- `post` 的**终点不是「核心取走完成」**，而是「中断处理退出 → 取走该完成的那次 `advance` 拿到的时钟」
  （执行器在调 `rearm_and_check` 之前读钟）；取走完成本身发生在同一次调用内、且在那次交接与写准备之后。
- 「驱动自己那段 = 整段 − `post`」**是跨总体的减法，不能这么叫**。同窗能被 `legs` 直接量到的下游成本
  只有下一笔写的 `dma`（125–158 µs）与 `program`（42–64 µs）。
- 替代解释已被否证：`post` **不是**执行器一轮循环的节拍——`corr(post, P) ≈ 0`（`P = dt/iters`），
  且 `post` 与执行器自己独立测的 park 交接（中断→wait 返回）逐窗几乎相等（比值 0.88–1.00，逐窗相关 0.87）。
  执行器是阻塞等通知唤醒的，重测段 89% 的等待由通知结束。
- **上一版写的「`rearm_race` 60.6% ⇒ 执行器频繁被重新调度而不是停在 park 上」方向是反的，已撤回**：
  越是从头到尾停在 park 上的空载窗该比值越高（17 个空载窗 `rr/oc = 74.9%`，且这些窗
  `waits × wait_us / dt ≈ 0.999`，即整窗停在 wait 上）。`rearm_race` 不是「没在 park」的证据。

**对 S6 的意义**：S6 的「合并两次 owner 调用」最多触及那 244–342 µs 里属于编排的一部分，
动不到占大头的唤醒延迟。S6 仍是把完成匹配与取消做成一等结局的正确结构，
但**不应再以「收回交接空档」作为它的收益理由**。

**两条前提不成立、已删除的步骤**：`flush_blocked=0`（91/91 窗）⇒ S7 删除；
`long=0`（91/91 窗）⇒ 本轮没有超过 20 ms 的停摆。

**回归守卫通过**：`credit_over n=0 pkts=0`（91/91 窗）；`chain` 七项之和与
`staged ready + missed` 均逐窗等于 `tx_writes`（91/91 窗）。

**口径更正（两项）**：

- 保留量分支占 credit 重试 67.7–70.4%，此前按代码推算写作「约 78%」。
- credit 等待**不可与 `accounted` 相加**（复核 C2）：该跨度里含重试读自身的往返（该窗 ≥23 ms、约 1.2 点），
  且退避期间 RX 不被挡住，`rx`/`rx_ctrl` 可落在等待跨度内。正确写法是「credit 把发送路径按住的墙钟占比」。
  它也不是常数：段内饱和窗（n=33）中位 15.9%、均值 18.3%、分布 7.0–45.8%，上行第一遍明显更高。
  另：credit 等待与 deadline park **是同一段**（credit 分支设 `retry_at` → 变成 park 的 deadline），
  不是可与 park 并列的另一个可动量。

**上行的两遍对照（本轮最有信息量的一条）**：同一次启动内背靠背的两遍上行，
驱动侧行为几乎一致（每笔写 20.5 对 20.4 KB、保留量占比 70.2% 对 69.7%、`staged ready` 51.3% 对 57.7%），
但交付的「每线上字节」从 0.49 变到 0.91，iperf3 交付 15.4 对 32.4 Mbps。
**退化的变量在 SDIO 之下**，不是本轮的改动；`mcs`/`rssi` 也不支持「退化段链路更差」的简单解释，
成因未定位，按既有约定不在驱动侧追。

**S1 的 C 类足迹**：`staged ready` 率由 `ahead1` 的 85–90% 降到 51–58%，`chain idle` 7.8–9.3%。
本轮无同会话对照臂，跨会话差值不作证据。

### 11.11 复核带出的新线索：owner 一次调用的固定开销（2026-09-30）

独立复核注意到一条本轮仪器里已存在、但 §11.10 没有读的账，本机已自行复算确认：

| 段 | owner 调用/秒 | 括号 µs/次 | 括号占墙钟 | 其中 `device.advance` 四类合计 | 残差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 上行第一遍 | 1856 | 130.2 | **24.2%** | 7.5% | 16.7 点 |
| 上行重测 | 1603 | 155.4 | **24.9%** | 8.2% | 16.7 点 |
| 双向 | 1313 | 165.1 | **21.7%** | 7.3% | 14.4 点 |

口径：括号 = `[netprobe]` 的 `owner_us × owner_calls`（`executor/mod.rs:744-751` 用单调钟夹住
`irq_control.rearm_and_check`），分母 = 该段窗口时长之和；`device.advance` 取 `[wifi-probe-time] advance`
的 `tx/rx/control/other` 四类 `n × avg`。两者是同一次调用内的量与子量，相减合法。

**`rearm_and_check` 不是一次纯重武装**：`rdif/device/endpoints/startup.rs:242-251` 里它调的是
`owner.rearm_and_advance(now)`，即**一整次 owner 推进**（publish flush、取 IRQ latch、
`device.advance`、提交路径、两个中断源重武装、发布）。因此这 130–165 µs 是「一次 owner 调用」的
总成本，而 `device.advance` 只占其中约三分之一；**余下 14–17 点墙钟落在 owner 脚手架里，目前没有任何分解**。

这是本轮读到的**最大的、且完全在 `aic8800` 与 `ax-driver` 边界内**的未分解项——比 `post`（8–9 点）、
比主机侧每笔准备（约 3.6 点）都大。它也是把「拆碎状态机」的收益理由接回来的唯一入口：
如果这 14–17 点里有相当一部分是「每次调用都要走的固定脚手架」，那减少调用次数或把脚手架移出
关键路径就有实打实的收益；反之若它主要是被打断的墙钟，则不可动。
**动手前必须先分解**（用 `#[inline(never)]` 分段或分段计时把 flush / latch / advance / submit / rearm / publish
各自的开销量出来），未标定不得优化。
