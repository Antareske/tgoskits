## 1. 结论速览（2026-09-28，第三阶段四轮之后）

**阶段边界已推进到 `ocr-review-20260928-bottleneck-round1.md`（瓶颈归属审查）。** 该轮否掉了"TX 受限在固件缓冲池/空口、应转向 RX 侧"
这一第二阶段的方向性结论（§2.18 的更正），此后第三阶段走了四轮，当前认知如下（按对下一步的影响排序）：

⓪ **主机侧的聚合粒度已到本轮实测的上界，但"空口用不掉"的判据不成立（§2.23、§2.27）**：K=4→32 实测有效
（每字节 189 → 133~144 ns/B，按字节加权），环 32→64 无效（判据是吞吐不变；按笔加权的成本不变）。空口读数 `mpdu/ampdu` 在有流量的 63 个样本里
**中位 8.0、上四分位 15.0、最大 40.0**，与我们每笔交出的约 20 帧（29.3 KB）同量级，
**不能据此判定"空口用不掉更大的 K"**；该方向回到开放，需与厂商同等条件下的同类读数对照。

① **"薄池不放小写"确实改变了写的分布，但收益幅度须按同一口径读（§2.27）**：credit 落在保留位之上、批次阈值之下时先等一档再问，
使小写（credit 3–6）占比从 29.3% 降到 **7.4%**、写中位升到 29.3 KB、发送 **36.9 Mbps**，每秒序列的慢尾收缩。
每字节成本同口径为 **按笔加权 174.9 → 152.4（−12.9%）**、**按字节加权 139.3 → 135.4（−2.8%）**；
对照臂同会话内的自然波动是 167.5~174.9（按笔）、139.3~151.9（按字节），即按笔口径的改善超出该波动、按字节口径的改善落在其内。
两条口径都取自整段会话的合计值，而两臂分属不同会话，**收益幅度尚未在同会话对照下判定**。

② **发送侧剩下的最大已知项是完成路径的 350~400 µs/笔（§2.22）**：写往返中这一段是设备报完成**之后**的主机时间
（唤醒 → 调度恢复 → 取走完成），而 `isr` 中位只有 **2 µs**，说明不在中断处理里。它在一笔里的占比已从 35% 降到约 13.6%。

③ **接收侧可以放下（§2.25）**：卡侧批上限实测 **63 块 = 31.5 KiB**（`65+` 桶零样本）、refill 平均约 **8 ms**；
按同一口径（平均批 42~45 块 ÷ 平均间隔 8 ms）折合约 **20.7 Mbps**，低于实测接收吞吐（31~34 Mbps），
即卡的交批节奏足以供上主机；重武装时卡中断已 asserted 的比例仅约 **2%**，说明也没有丢通知。主机侧没有余量可挖。

④ **空口侧第一次有了观测手段（§2.27）**：`[wifi-rc]` 的 `mpdu`/`ampdu` 给出固件实际聚合深度。
该行取自 `me_rc_stats_cfm`，是**固件采样区间**的累计量（不是 2 s 窗口量），`avg_mpdus` 为 16.16 定点数；
语义细节未与厂商核对，只作趋势。

⑤ **已关闭的项**：上游供帧（饱和窗口约 7%）、SDIO 总线时钟（翻倍上界 <1.6×）、40 MHz（该 AP 的 BSS 就是 20 MHz）、
RX defer（负面结论）、`ack` 计数比值（口径更正，§2.26）、环深（§2.25）。

**已更正的历史判读（保留备查）**：本文件此前的 ⓪"TX 的限制项已定位在固件/空口，不在主机调度（§2.18）"**不成立**——
那一轮的证据链由两个探针窗口拼成、其中一项是恒等式、credit 采样内生，详见 §2.18 顶部与 §2.21。

**周期 P8 的墙钟构成（2026-09-27：TX 写 52% / RX 事务 25% / 空档 48%）已不再代表当前工作点**——
那是 K=4、环 32 时期的读数；当前工作点的构成见 §2.22（饱和窗口写事务占 73~77%、`accounted` 83~85%）与 §2.27（小写占比 7.4%，每字节成本按笔 152.4 / 按字节 135.4 ns/B）。

## 2.1 事务级成本结构（实测，周期 P3/P4/P6）

- 一笔写的成本随长度增长：512 B 约 148 µs，1536 B 约 700 µs（周期 P3/P4）。
- 一笔 4 包的写（约 6 KB）约 1086~1141 µs，折合 **275 µs/包**，比"一包一写"便宜约 2.5 倍（周期 P6）。
- 读方向：一次单块读（≤512 B）**134 µs**，其中数据相约 44 µs → **约 90 µs 是与长度无关的固定开销**（周期 P6，上行窗口 2178 笔均值）。
- CMD52 字节读约 51 µs，credit 读约 86 µs（同上）。

**判读**：这块板子上"做一笔事务"的固定成本是几十到一百多微秒，所以优化目标是
**减少事务条数**，而不是提高单笔搬运速度。

### 2.2 成本结构修正（实测，周期 P8，2026-09-27）

周期 P8 的上行窗口给出了更准的分母，**先前的"总线忙 77%"读法需要修正**：

- **数据相只占约 23% 墙钟**：上行 2 s 内写线上字节 4.86 MB + 读 0.5 MB ≈ 5.4 MB，
  按 11.72 MB/s 折算约 **461 ms**（更正：原写作 229 ms，是把 5.4 除以 23.4375 这个 MHz 数值的结果）。
- **其余全是"事务条数 × 每笔往返"**：该窗口 5573 笔事务（TX 写 850 + RX 数据读 1716 +
  RX 控制读 2791 + credit 216），每笔往返 100~200 µs 量级。
- **RX 事务占事务条数的 81%**，其中控制读（2791/2 s）= 每次数据读一次状态读（1716）
  + 每次扫描一次收尾空读（1075）——都是"每次读 / 每次扫描必付"。
- ⚠️ **已作废（§2.12）**：当时的"上行 ACK 是滴流、1687 帧/s、一帧约 590 µs"其实在数**我们自己**的确认回读，
  速率由我们自己的发送节奏决定，是自指的量；"1 ms 窗口没有余量"的机制解释随之失效
  （负面 A/B 结论本身仍成立：1 ms 无收益、3 ms 灾难）。
- **上行 ACK 是滴流**（作废）
  1 ms 窗口只能攒 1~2 帧，而基线已经是 1.77 帧/读——**现窗口没有余量**（周期 P8 结论）。

### 2.2b RX 侧的形态（实测，周期 P6）

- ⚠️ **本节数字已被 §2.12 更正**：统计里的"接收帧"多数是本驱动自己 TX 的确认回读，不是 PC 的 ACK；
  下面的 frames/read、事务/帧、每帧成本需按 §2.12 重算。
- 上行窗口：3849 个接收帧（当时认定为 PC 的 TCP ACK，74 字节级）用了 2178 笔数据读 + 3735 笔控制读
  = **每帧约 1.5 笔事务、约 125 µs 总线时间**；其中 2139/2178 笔读是 ≤512 B 的单块读。
- 下行窗口：819 笔数据读带回 5037 帧（**6.1 帧/读**、均 9.2 KB/读），是正常形态。
- 扫描结构：`ReceiveCount`（读状态字节）→ `Blocks(n)` 直接 `ReceiveData(n×512)`，字节模式才多一次长度读；
  D80 命令与数据同为 Function 1，**单路径**；DC 为双路径（2/1）。
- 结论：上行读得碎不是机制缺失（固件会合并，下行已证明），而是**去得太早**——CARD_INT 一到就扫，
  固件里只有 1 个 ACK。

### 2.3 执行器与 owner 的时序（实测，周期 P6 / P8 的 `[netprobe]`）

上行窗口 2 s 内：`iters=13478`、`polls=11144`（均 9 µs）、`waits=6062`（均 170 µs）、
`owner_calls=11128`（均 **67 µs**）、`irq=11725`、`tx_submit=3464`（协议层交给驱动的帧数，
对 933 笔写 ≈ **3.7 帧/写**）。

- **`owner_us` 的语义**：它是 `finish_idle` 里 `rearm_and_check` 的耗时，而 `rearm_and_check`
  走的是 `AicPollIrqControl::rearm_and_check` → `AicOwner::rearm_and_advance`，
  **即整整一次 owner 推进**（收割完成、跑核心状态机、提交下一笔、再用寄存器 rearm）。
  所以 67 µs 是"每轮 owner 工作的总价"，不是寄存器操作的时间。
- **`wake` 的语义（重要更正）**：探针在 `schedule_irq()` 记中断时间戳、在 `finish_idle` 结束时取差，
  所以 `wake=161 µs` 是"**最近一次中断 → 本轮 owner 推进结束**"，约等于执行器迭代周期
  （13478 次 / 2 s = 148 µs），**不是**"中断到唤醒"的调度延迟。先前把它读成唤醒开销是错的，
  由此得出的"161 µs 唤醒延迟"结论作废。
- **周期 P8 补充**：`owner_us` 的 67~69 µs 与"一笔被轮询的 CMD52 事务"的耗时同量级
  （控制读 62 µs、credit 读 58~63 µs）。按事务数核对：上行窗口 5573 笔事务对着 9954 次 owner 推进，
  约 56% 的推进里含一笔轮询事务——所以 `owner_us` **主要是总线/事务时间，不是纯 CPU 工作**，
  "37% 墙钟"与 §2.2 的事务时间大幅重叠，不能当成额外的软件开销叠加。
- 若要继续归因这 67 µs，需要在驱动侧把一次 owner 推进拆成
  「RDIF 收割 / 核心状态机 / 提交准备（构帧、DMA 分配与拷贝、ADMA2 重建）/ rearm 寄存器」
  四段。驱动核心**没有时钟源**（时间由调用方以 `AicInput::now` 传入，设计上是刻意的），
  因此该拆分要么由执行器侧提供两个新钩子，要么由驱动记录"调用入口时间戳"间接推算。

### 2.4 串行契约与它的代价（代码事实 + 折算）

- 契约（`docs/design/unified-sdio-aic8800.md`「四层职责」「事务与 IRQ 所有权」）：
  Driver Core 不建线程、不持 OS 锁、不 sleep/yield；Capability Adapter 不依赖
  `ax-sync`/`ax-task`/`axruntime`；运行时的固定 CPU owner、定时唤醒、IRQ 注册与队列调度归
  `net/ax-net` 与 `axruntime`。设计文档记录的理由是"同步包装器会隐藏取消/超时，驱动线程会绑定 OS"，
  目的是让同一份驱动能被 ArceOS / StarryOS / Axvisor 共用（Axvisor 场景下驱动不能自带线程或独占调度）。
- 代价：**单 owner、单事务在飞**。一笔事务的生命周期是
  `准备 → 提交 → 等完成（park） → 收割 → 准备下一笔`，其中准备与收割都与总线**串行**，
  无法用等待窗口掩盖（对比：厂商用两个独立线程把 RX/TX 拆开，互不阻塞）。
- 折算：若一次 owner 推进的 67 µs 中有一半是准备/收割，11128 次即约 370 ms ≈ 墙钟 19%，
  这部分是"打破串行"能拿到的上界（**推论**，需 §2.3 的分段实测确认）。

### 2.5 credit（实测 + 厂商对照，已核实）

- 信用是固件**空闲缓冲个数**，一个数据包扣一个；保留位 2（`DATA_TX_RESERVED_CREDITS`）与厂商
  `DATA_FLOW_CTRL_THRESH = 2` 同值。
- 厂商同构：`aggr_count == fw_avail_bufcnt - DATA_FLOW_CTRL_THRESH` 时停止聚合、完成后
  `fw_avail_bufcnt -= aggr_count`（`aicwf_sdio.c`）。厂商命令路径另有按字节的检查
  （`len > buffer_cnt * BUFFER_SIZE`，`BUFFER_SIZE = 1536`），那是命令路径的保守限制。
- 读数常态 75~119（min 2 / max 132），回退占比小（上行窗口 116 次 × 573 µs ≈ 3%）。

### 2.6 聚合与帧流契约（实测 + 厂商核对，周期 P5–P7）

- 固件把一笔 CMD53 当**帧流**遍历，步长 `4 + align4(声明长度)`，读到长度为 0 终止；
  逐帧补齐 512 会让第 2..K 帧被静默丢弃（周期 P6 的根因）。
- 一笔写的两个上界（帧数 / 字节）已可配置（`aic,tx-aggregation`、`aic,tx-aggregate-bytes`），
  默认沿用已上板的值：4 帧 / 6144 字节。满帧（1532 字节）在 6144 下只能装 4 帧，
  所以**上行大帧流由字节上界决定，下行 ACK 小帧流由帧数上界决定**。
- 厂商 K 是模块参数 `tx_aggr_counter`，**默认 32**，且被同一次流控读数截断（与我们同构）。

### 2.7 空口能力（实测，来自厂商镜像）

- 厂商镜像（`2026-01-14-16-03-d4003f`，对应设计文档已锁定的 vendor commit `d4003f15b…`）
  的驱动由 `/etc/init.d/S25wifimod` **无参数** insmod，全部取默认值：
  `ht_on=1`、`vht_on=1`、**`he_on=1`**、`mcs_map=2`（VHT MCS0-9）、`he_mcs_map=2`（HE MCS0-11）、
  `ldpc_on=1`、`stbc_on=1`、`ant_div=1`、`ps_on=1`；射频功率表备有 `lvl_11ax_mcs0..11_2g4`。
- 本驱动的 `me_config_payload()` 当前按 `MeConfigProfile` 编码：DC 保留 conservative HT20 字节；D80 的 HT40/SGI profile 设置 HT40、SGI20/40、MCS32 及对应 HT rate。两个 profile 都保持 VHT/HE 段全零、`ant_div_on = 0`；D80 profile 已完成两轮实板测试（读数见 §2.9(a) 与 §2.13）。
- 厂商会在固件未报 `MM_FEAT_VHT_BIT`/`MM_FEAT_HE_BIT` 时强制关掉 VHT/HE。
  所以"厂商跑到 58.5 Mbps"的确切机制仍需板上读数确认（`dmesg | grep "HT supp"`、`iw dev wlan0 link`）。

## 2.9 与厂商 Linux 的差距构成（2026-09-27，数据来自 `../iperf3-tests/`）

对照数据出自同目录 `../iperf3-tests/`（Linux/STA 与 StarryOS/STA 两套，同一台 Windows PC 热点、
同一套用例与参数；PC 端用 Cygwin iperf3，数字含 PC 端影响，但两侧同口径可比）。

| STA / TCP / P1 | StarryOS 基线（优化前） | **现在** | 厂商 Linux | 现在 / 厂商 |
| --- | --- | --- | --- | --- |
| tx（板→PC，上行） | 7.30 | **17.2~19.5** | **58.2~58.5** | **约 1/3** |
| rx（PC→板，下行） | 20.3 | **25.9~30.4** | **46.4~54.6** | **约 1/2~0.6** |
| bidir 板→PC | 3.32 | 12.1 | 53.6 | 约 1/4 |
| bidir PC→板 | 1.85 | **10.7** | 5.8 | **约 1.8×（反而更好）** |
| UDP tx | 卡死板子 | 卡死板子 | 73.8 | — |

**关键形态：差距几乎全在"板子的发送方向"。**

- 上行（板子自己发）只有厂商的 **1/3**；双向里的板→PC 只有 **1/4**；
- 而接收方向（PC→板）到厂商的 **1/2~0.6**，双向里的 PC→板甚至**比厂商还好 1.8 倍**。

这条不对称与**空口能力位**这一假设相容：板端发送和接收使用的 rate control 信息来源不同，但同一份吞吐不对称数据不能证明是本机 capability 限制。HT40/SGI 现以 D80 专用实验 profile 测试，是否协商成功以及是否影响上行，仍需 firmware rate telemetry 或等价实测支持。

旁证：同一份数据里，厂商在 **AP 模式**（板子自己当 AP，hostapd 20 MHz、实测协商 802.11n 65 Mbps）
只有 40.8~44.8 Mbps，而在 **STA 模式**（连 PC 热点）能到 58.2~58.5 Mbps。
说明 PC 热点这条链路能给到 65 Mbps PHY 以上（40 MHz 或 HE），**是我们没有去要**。

### (a) 空口能力位：原始配置只报 LDPC，HT40/SGI 已进入受控实验

第一阶段和 P0a 镜像中的 `me_config_payload()`（`lmac.rs`）HT capability info 为 **`0x0001`**，即只有 LDPC 位。第二阶段 D80 HT40/SGI 实验改为 `0x0063`，已在实体板卡运行两轮（板端启动日志打印 `d80-ht40-sgi`）。**实测**：正向 25.3/28.8/26.7/29.9 Mbps（P0a 轮 16.4/20.7）、反向 18.8/15.6/19.4/19.0/20.6（P0a 轮 16.0）、双向 13.6/12.5（P0a 轮 9.69/6.14），均为跨会话观察。协议协商结果仍不可读，因此这些提升不能归因到 capability。

| HT/ME 字段 | 含义 | P0a 基线 | D80 HT40/SGI 实验 | 厂商 D80 默认路径 |
| --- | --- | --- | --- | --- |
| HT bit 0 | LDPC | 1 | 1 | ME_CONFIG 编码时追加 LDPC bit |
| HT bit 1 | 支持 20/40 MHz | 0 | 1 | `use_2040` 默认打开 |
| HT bit 5/6 | SGI20/40 | 0/0 | 1/1 | `sgi` 默认打开，HT40 时设 SGI40 |
| MCS mask[4] | MCS32 | 0 | 1 | `rwnx_set_ht_capa()` 在 HT40 下设置 |
| MCS highest | 最高 HT rate | 65 Mbps | 150 Mbps | HT40 为 135，SGI40 分支改为 150 |
| `phy_bw_max` | 最大带宽枚举 | 80 MHz | 40 MHz（已改） | 厂商对 D80/D80X2 强制 `use_80`，故为 80 MHz |
| VHT/HE support | 能力开关 | 0/0 | 0/0（已改） | 厂商 D80 在 2.4 GHz 同时开启 VHT 与 HE |

> **2026-09-28 更新**：`phy_bw_max` 与 VHT/HE 两行已被「第二阶段 VHT/HE 能力」轮改动（`1fb1bc91c`）：

### (b) 每笔事务的开销：我们把自家天花板的另一半用掉了

- 上行每包墙钟 ≈ 600 µs（19.5 Mbps、1460 B/包），而总线数据相只要约 130 µs；
- 每帧 RX 要 1.05~1.34 笔事务（状态读 + 数据读 + 每次扫描的收尾空读）；
- **每笔会 park 的事务**：传输 834 µs + 软件交接 **170 µs**（2026-09-27 实测）；
- 单 owner 单事务在飞：一笔在飞时既不能处理接收也不能准备下一笔，厂商是两个独立线程；
- 多数 CMD52（状态读、应答）是 **owner 内轮询**完成的（50~150 µs/笔），期间单 owner 被占住。

### (c) 还没试过的 TX 侧形状差异

厂商一次聚合最多 32 帧、缓冲 96 KB（`MAX_AGGR_TXPKT_LEN`），默认参数下的写形态远大于我们的
4 帧 / 6144 字节。K 与字节上界已做成可配（周期 P7），但**选值轮一直没跑**。

### 审查告诫（2026-09-27 OCR，照录）

- **上下行不对称不能单独证明因果**：厂商树里部分动态兼容检查位于 `#if 0`，不能当作现成的安全门；
  需要 typed 能力 + **实测 negotiated width/MCS/retry/channel** 才能把因果钉住；
- "修正能力位就能到约 40 Mbps"是**推断而非保证**，必须先有同会话 A/B/A；
- 厂商的 TX/RX 两线程**不等于 SDIO 并行**（它们在 SDIO host 锁上串行），不宜作为"并行度"论据。

### 结论

- 差距集中在**上行**（1/3~1/4），而接收方向已接近厂商（1/2~0.6，双向里还更好）；
  这与"能力位偏低专门压低上行"的机制一致，**空口能力位是首要抓手**；
- 其次是每笔事务的开销（交接 170 µs、轮询、单事务在飞）与未做的聚合选值——它们同时压低两个方向，
  所以是接收方向仍然差 1.8 倍的原因；
- 两者都是驱动侧软件，互不冲突。

## 2.11 UDP 路径：瓶颈在驱动之上（实测，2026-09-27，P6 镜像、板端作 client）

板端 `iperf3 -c <PC> -u -b 100M`（PC 作 server，因为板端作 UDP server 时报 `Address in use`）：

| 用例 | 结果 |
| --- | --- |
| UDP tx（板→PC） | **1.05 Mbps**（1.25 MB/10 s，898 个数据报，**丢包 0%**，jitter 7.8~10.5 ms） |
| UDP tx 首轮 | 534 Kbps（458 个数据报，0% 丢包；随后 PC 端 server 中止） |
| UDP `-R`（PC→板） | 1.05 Mbps，0% 丢包，jitter 7.8 ms |
| UDP `--bidir` / 多流 | PC 侧 Cygwin 工具的限制（`unable to read from stream socket`），与板端无关 |
| 同会话 TCP（板作 client） | **15.6 Mbps**（55.6 MB/30 s） |

**关键证据（驱动侧探针）**：UDP 期间的窗口里 `supply … none = 93/93、179/180、178/178、180/180`
——**驱动一次都没有拿到第二帧**；写形态是 `3 块/笔`（一帧一笔，K=1 无法聚合），
速率 **约 90 包/秒（11 ms/包）**，而驱动在这 11 ms 里是**空闲的**。

**结论**：UDP 的上限**在驱动之上**（socket/协议栈/系统调用一侧），不是 aic8800 驱动的问题；
对照厂商同一块板：UDP tx **73.8** > TCP 58.2（UDP 更高），而我们是 UDP 1.05 ≪ TCP 15.6（相差 10 倍且方向相反）
——栈的 UDP 发送路径存在明确缺陷。

**两个可查的具体缺陷**

1. **~90 包/秒的上限**（驱动空闲、0% 丢包 → 是发送端被 socket 卡住）：判别手段很便宜——
   ① `-u -b 10M`（低速率能否达标：能→是 pacing/反馈路径问题，不能→是硬上限）；
   ② `-u -l 64` 与 `-l 1400` 对比（限的是"包速率"还是"字节速率"）。
2. **板端作 UDP server 报 `Address in use`**（所以本轮只能把角色反过来）：属可复现的小缺陷（socket bind/reuse）。

**为什么值得管**：① 它本来是我们测"路径容量（不受 TCP 流控影响）"的仪器，现在用不了；
② 基线数据记录过"UDP 与多流用例会卡死板子"——本轮 1 Mbps 下没卡死，说明卡死可能与速率/背压有关。

## 2.12 普通数据帧逐帧索要固件确认（2026-09-27 OCR 审查提出，已双向核对源码）

**事实（代码层，已核对）**

| | 请求确认的条件 | hostid |
| --- | --- | --- |
| 厂商 `rwnx_tx.c:647-671` | 仅 management（0xd0/0x10/0x30）+ EAPOL(`0x8e88`) + WAPI(`0xb488`) | `(1<<31) \| 唯一序号`，且有 `need_cfm` 消费者 |
| 厂商（普通数据） | 不请求 | **`0`** |
| **本驱动旧行为** | **每一帧以太网 TX 都置位** | **恒为 `0x8000_0001`**（无含义的固定 ID） |
| **第二阶段 P0a 当前代码** | 普通 data 不请求；内部 EAPOL 暂保留 | 普通 data 为 **`0`**；特殊帧仍待唯一 ID |

旧行为的 RX 侧对 `DataConfirmation` 只 `log::trace!` 后丢弃（`data_plane.rs`）——即**索要了、读回来了、然后丢掉**。当前代码已经通过 `TxConfirmation::None` 消除普通 data 的请求，并通过 typed probe 区分各类 FIFO 项；P0a 实板活跃数据窗口的 `data_confirmations=0`，见下文。

**后果（强相关推断，非直接测量）**：每个发出的数据包会让固件多回一个确认帧，我们要为它付一次接收路径
（CARD_INT → 扫描 → 状态读 + 数据读，可能还有尾空读）。审查给出的算术吻合：
窗口里 `rx_parsed − rx_done ≈ tx_submit`（3849−468≈3464、3912−489≈3434）。

**这同时更正了 §2.2/§2.10 的口径**：那些"接收帧"里多数是**我们自己 TX 的确认回读**，不是 PC 的 ACK；
因此 `frames/read`、`事务/帧`、"ACK 每约 590 µs 滴流"这类推导**全部作废**（当时把确认当成了对端流量），
"1 ms 窗口没有余量"的机制解释随之失效（它测的是我们自己的回声）。

**第二阶段首轮 P0a 已实现并完成实板验证（2026-09-27）**：普通数据经显式 `TxConfirmation::None` 构造，hostid 改为 0；内部 EAPOL 暂保留原有确认标记，特殊帧的唯一 ID、消费者与超时仍未实现。探针新增 `tx_writes`、`rx_items`、`rx_data_frames`、`tx_data_confirmations`、`control_confirmations`、`control_indications` 和 `firmware_prints` 字段，避免把不同 FIFO 项混成“接收帧”。COM6 活跃数据窗口中 `data_confirmations=0`，证明普通 data 确认流量按预期消失；完整 TCP 吞吐读数和 `-b 100M` 观察见下文及原始日志索引，不构成同会话因果对照。

第二阶段首轮同时将 `DEFAULT_RX_DEFER` 改为零，未配置 FDT 属性时立即服务 CARD_INT；`aic,rx-defer-ms` 的显式非零值仍保留为实验旋钮。该默认策略与 P0a 已在同一镜像完成板测；这轮结果不替代非零 defer 的旧版对照。

**第二阶段首轮实板已完成（2026-09-27）**：镜像基于第一阶段 `ab0` 镜像，仅更新内核和 `lcn-sta-defer0.dtb`；FIT、rootfs 与配置校验通过，镜像 SHA-256 见 `aic8800-optimization-tracker.md`。COM6 日志显示正常启动并获得 `192.168.137.229/24`；Windows cmd 直连 iperf3 的完整轮次记录了板端接收 16.4/20.7 Mbps、双向板端 TX/RX 约 9.69/6.14 Mbps、反向板端 TX 16.0 Mbps；P0a 活跃窗口的 `data_confirmations=0`。`-b 100M` 反向完整轮次板端 TX 为 6.71 Mbps，但普通轮次与 `-b` 轮次尚未严格配对复测。特殊帧仍需唯一 ID、消费者与超时契约，再单独实现。

## 2.13 D80 HT40/SGI profile 实板（2026-09-28）

`lmac.rs` 将以明确 vendor layout offsets 和类型化的 `MeConfigProfile` 编码 `ME_CONFIG_REQ`。D80 选择 `D80Ht40Sgi`：HT capability `0x0063`（LDPC、20/40 MHz、SGI20/40），单流 MCS0–7、MCS32、HT `rx_highest=150`、`phy_bw_max=40 MHz`；DC 继续原 `Conservative` profile。两者都不启用 VHT/HE、STBC 或 antenna diversity。HT40 的 `rx_highest=135` 会按 vendor `rwnx_set_ht_capa()` 在 `sgi` 分支再更新到 150；`rwnx_send_me_config_req()` 将最终值和 capability 交给 firmware。该编码已通过 Rust 单元测试、三组 AIC clippy 和增量标准库测试；能力镜像已构建并通过 FIT、DTB、rootfs 自检，镜像内核与本轮编译产物逐字节一致。最终镜像文件名与 SHA-256 见 `aic8800-optimization-tracker.md`。

该改动仍是实验配置，不说明 firmware 与 AP 实际协商到 40 MHz 或 SGI。板端启动日志只打印所选 profile（`d80-ht40-sgi`），串口 probe 只覆盖吞吐与数据面事务；channel、协商 bandwidth/MCS、retry、GI 尚未观测。两轮板测的读数与判读见 `aic8800-optimization-tracker.md` 的「第二阶段 HT40/SGI」小节。

## 2.14 ARP 表项 300 s 到期事件（实测，2026-09-28；属板载网络栈）

### 厂商基线的解释换位（更正）

HT40/SGI 轮曾据厂商 Linux 基线的 UDP 76.5 Mbps 推断"该热点能给 40 MHz"（依据是它超过 20 MHz 单流 HT 的
72.2 Mbps 上限）。该推断不成立：厂商 D80 在 **2.4 GHz** 上同时宣告 VHT 与 HE（`rwnx_main.c` 的 2.4 GHz band
带 `.vht_cap` 与 `iftype_data = &rwnx_he_capa`；HE 能力位含 `20MHZ_IN_40MHZ_HE_PPDU_IN_2G`），
20 MHz 下的上限因此是 VHT20 MCS9 的 86.7 Mbps 或 HE20 MCS11 的 129~143 Mbps，厂商的 58.7/76.5 Mbps
完全可以发生在 20 MHz。**AP 的 BSS 宽度重新回到未知**，不能再用厂商基线作为"AP 支持 40 MHz"的证据。

确定的差距是**调制格式**：厂商是 HT+VHT+HE 客户端，本驱动此前是 HT-only 客户端。

### 厂商 `me_config_req` 逐字节对照与由此产生的改动（提交 `1fb1bc91c`）

对照厂商 `lmac_msg.h` / `lmac_mac.h` / `rwnx_msg_tx.c` / `rwnx_mod_params.c` / `rwnx_main.c` 与
`drivers/net/aic8800/src/lmac.rs`，排除了四类假设：消息布局错位（HT 32 / VHT 12 / HE 56 / 标量 100–109，
逐字节吻合）、A-MPDU 与 `tx_params` 取值、关联请求 IE（厂商同样只放 `sme->ie`，HT/VHT/HE IE 由固件生成）、
信道表 flags（该 ABI 无 HT40 位）。`sm_connect` 的信道提示两边的"未知"分支也一致。

唯一取值偏差是 `phy_bw_max`：厂商对 D80/D80X2 强制 `use_80`，D80 发送 `PHY_CHNL_BW_80`（2）；
DC 按固件上报的 RF 带宽得 `PHY_CHNL_BW_40`（1）。本驱动此前写反（保守=2、D80=1），本轮把 D80 改为 2。

D80 在 2.4 GHz、单流下厂商实际发送的能力取值已照此编码：VHT `vht_capa_info=0x03987111`、单流 MCS 0–9
（map `0xfffe`、highest 390）；HE `phy_cap_info=[0x06,0xe0,0x2b,0x58,0x0d,0xc0,0xcf,0,0x02,0x30,0]`、
单流 MCS 0–11（`mcs_80=0xfffe`）、160/80+80 全不支持、PPE 阈值 `[0x38,0x1c,0xc7,0x01,…]`；
标量为 `vht_supp=1`、`he_supp=1`、`he_ul_on=0`。厂商 HT 块的 RX_STBC 与 MAX_AMSDU 位本轮有意不跟
（接收侧能力，涉及 A-MSDU 接收路径）。

### 下一步的判据

镜像 `sg2002_starryos_wifi_sta_vhthe_20260928.img`（提交 `1fb1bc91c`）的读数是**单一的格式判别**：出现 `format=vht`
或 `format=he-su` 且 MCS 进入 8–11 → 差距可归因到调制格式；仍是 `format=ht-mf mcs=7`
→ 该 AP 不与本客户端协商 VHT/HE，方向转向 AP 侧与带宽，而不是继续加客户端能力位。

**实板结果（2026-09-28）**：第二遍会话 204 条读数全部 `format=he-su`，MCS 以 9~11 为主（11:60、10:38、9:29），
即**判定为"调制格式差距"**：板端已在 HE20 的顶档（MCS11 = 1024-QAM，PHY 约 143 Mbps）发送。同一遍吞吐为
接收 30.6 / 发送 26.9 Mbps，约合 PHY 的 19%~21%，说明限制已不在空口档位而在主机侧路径与聚合形状；
但该结论必须先扣除会话变量——同一镜像第一遍只有 15.7 / 2.50 Mbps 且读数塌到 legacy 档（§2.17）。
只要 `width=20MHz` 保持，任何吞吐变化都不得解释为带宽收益。

## 2.17 热点状态是跨会话第一变量（实测，2026-09-28）

同一镜像 `sg2002_starryos_wifi_sta_vhthe_20260928.img`、同一块板、同一条命令集，两个相邻会话：

| 会话 | 板卡/热点动作 | 接收（PC→板） | 发送（板→PC） | 遥测读数 | `rssi` |
| --- | --- | --- | --- | --- | --- |
| 第一遍 | 上电后直接测 | 15.7 Mbps | **2.50 Mbps**（13 s 中断） | `he-su` 低 MCS 与 `non-ht mcs=3` 混跳，ack 失败约 31% | −31~−41 dBm |
| 第二遍 | 板卡拔电 + 热点重开 | 30.6 Mbps | **26.9 Mbps** | `he-su`，MCS 9~11 为主 | −18~−26 dBm |

**结论：会话内的性能第一变量可能不是我们改的代码。** 会话间波动归到**两个敏感操作（重启 PC 热点、重启板卡）**
与**天线姿态/板卡放置**——后者已在 §2.19 用实测读数定位（扰动时 MCS 塌到 3~7 而 `rssi` 反而更高，是发射侧变差的形态）。
本例两者（热点与板卡）同时重启，故未分离到其中某一个。在第二遍的读数里 HE 已经协商成功
（`format=he-su`、MCS 11 = 1024-QAM），所以"调制格式"这一条差距已经补上；但发送方向两遍相差 10 倍，
远大于任何一轮驱动改动的效应量。

成因尚未归因：两遍之间**同时**重启了热点与板卡，存在两个候选。

| 候选 | 支持 | 反证/待查 |
| --- | --- | --- |
| PC 热点侧状态（信道漂移、单射频与 PC 自身 station 连接分时、适配器省电、ICS 状态） | 双向都变慢、ack 失败升高、固件 RC 掉到 legacy 档 | 本板上报的 `rssi` 差 13~15 dB，信道/路径损耗变化解释不了 |
| 板卡侧 RF 状态（固件校准或增益/功率索引在该次上电后不正常） | `rssi` 变低（本板接收增益低）+ ack 失败升高（对端听不清本板）+ 双向都慢，单一原因全部解释 | 两遍驱动启动日志无差异；主机侧发送功率表是固定常量，本驱动不读 RF feature 寄存器 |

本驱动把所有帧的发送交给固件，固件自己的速率控制掉到 legacy 档是"空中链路变差"的结果；
下行方向（完全由 AP 决定发射）同样腰斩，因此"StarryOS 收发路径把 AP 拖坏"这一支证据最弱，
但不能完全排除（例如本板以异常功率持续发送会恶化同信道环境）。

**判别实验**（按序，均便宜）：

1. 只重启热点（板卡保持运行）→ 恢复则指向热点；只拔电重启板卡（热点不动）→ 恢复则指向板卡 RF 状态。
2. 热点刚重开后不做任何改动，每 5 分钟一轮 60 s 参考测量、持续 1 小时：单调下滑说明与在线时长相关
   （且短间隔复跑会掩盖它，从而把退化误归因到当轮改动）；某点阶跃则对应一个事件，可与 PC 侧日志对齐。
3. 厂商 Linux 镜像同一协议两遍：厂商也塌则与本驱动无关。
4. 测试期间记录 PC 侧热点信道、station 接口状态/信道与自身流量（单射频分时是首要怀疑对象）。

**协议后果**：每次测量前重启热点并等约 1 分钟；每轮先跑参考臂，参考臂不在历史正常区间就丢弃该轮；
把遥测读数（`format`/`mcs` 分布、ack 计数）随轮次归档作为会话健康记录。**跨会话的吞吐对比不再作为收益证据**——
本文件此前各轮的"跨会话提升"（§2.9(a)、§2.13）均按此降级为观察。

## 2.18 写管线续接实板：空档不是 TX 的限制项（2026-09-28）

镜像 `sg2002_starryos_wifi_sta_txchain_20260928.img`（提交 `dfdc282cc`，含写完成即续接下一笔的改动），
日志 `com6-board-20260928-162606.log`。大流量窗口（`tx_writes` 约 800~1200 / 2 s，单笔约 6 KB、600 笔/秒）：

| 量 | 读数 |
| --- | --- |
| 单笔写往返 | 1.03~1.06 ms（占 1.66~2.0 ms 周期的 **64%**） |
| 完成→下一笔提交的空档 | 1056 笔 × **207 µs**（无 RX 事务）+ 147 笔 × 3.4 ms（有 RX 事务）≈ 周期的 36% |
| 续接命中 | `chain write` 约写次数的 **37%**、`chain flow` 5%；上界让位 `yield` **42%**；`idle`（完成时队列空）17% |
| 完成时帧在哪 | `supply core` 83%、`ring` 14%、`none` 3%（大流量窗口） |
| **credit** | 最忙窗口均值 **7.1**、`min=2`（保留位）、`backoff` **225 次/秒**（此时该计数器只含保留位退避，见 §2.28） |

> **⚠️ 本节结论已更正（2026-09-28 瓶颈审查，见 §2.21）**，更正后的事实如下：
>
> 1. 上表的读数**取自两个不同的窗口**："单笔写往返 1.03~1.06 ms / 占周期 64% / 空档 1056×207 + 147×3.4 ms / 续接比例"
>    来自 `tx_writes≈1203` 的窗口（该窗 credit 均值 **36.1**、回退仅占写次数 **4%**）；
>    而"credit 均值 7.1、`backoff` 225 次/秒"来自 `tx_writes≈950` 的窗口。两者不可拼成一条因果链。
> 2. `period ≡ gap + rtt` 是**定义式分解**（三者同用 owner 调用入口时间戳），"周期 64% 是单笔写自身"不含独立信息。
> 3. 写往返 1061 µs 中**有 318 µs（30%）是设备中断之后的主机侧交接延迟**（`park handoff`，实测），
>    因此"写自身 = 固件/空口"这一二选一在结构上排除了主机。
> 4. credit 采样节奏**内生**：只在 `consume_transmit_flow` 采样（`data_plane.rs:604`），读取频次由缓存读数被花光驱动，
>    同会话内采样数变化 19 倍且与均值强负相关 ⇒ `avgx10` 不是时间平均。

结论（更正后）：**续接机制生效，但提交调度不是限制项**——这是本节唯一站得住的部分。
"发送方向受固件缓冲池排空速度（空口/对端）限制"**不成立**：该判断的三条依据（跨窗口拼表、恒等式、内生采样）均被推翻；
写往返里的非数据时间有 30% 已实测属主机侧。TX 的真实限制见 §2.21。
空档只剩 207 µs 一档，续接能省的正是这一档；3.4 ms 的大空档发生在"完成与下一次提交之间插入了带 RX 事务的驱动路径"
（上界让位），而这部分被上界换取的是接收侧不被饿死，不该为吞吐牺牲。

该轮吞吐：接收（PC→板）**32.8 / 32.1 Mbps**（历次最好，与"RX 侧受主机路径限制"一致）、
发送（板→PC）17.3 / 19.3、双向 17.0 / 8.63 Mbps。读数全为 `he-su`、MCS 6~11，但低档（6/7）占比高于上一轮（9~11 为主），
两会话不可直接比较；因此本轮只能下"未见提升"的结论，不能把 TX 数字的差异归因于本次改动。

**方向修正**：TX 侧不再在提交调度上投入（限制项在固件/空口）；驱动层异步优化转向 **RX 侧**——
RX 事务占 RX 总线时间的约 81%（数据读 134 µs/笔、控制读 51 µs/笔），且 RX 是当前较好的方向（32 Mbps）。
候选：让每次交付更大（HT `MAX_AMSDU`，AP 可用 A-MSDU 发给我们）、压控制读次数、收尾空读。

| 每笔数据读 | **21~22.5 KiB**（13~14 个项/帧，即固件每笔已打包约 13 个满长 MPDU） |
| 每笔读耗时 | **2.29~2.45 ms** → 约 9.5 MB/s |
| 该速率对比总线 | 25 MHz × 4 bit 的理论上限 12.5 MB/s → **每笔读基本贴着总线跑**（开销约 24%） |
| 窗口吞吐 | 10 MB / 2 s = 40 Mbps（对应 TCP 31 Mbps） |
| 读占用窗口的比例 | 440 笔 × 2.3 ms ≈ 1.0 s / 2 s ≈ **50% 占空比** |

> **⚠️ 本节结论已更正（2026-09-28 瓶颈审查，见 §2.21）**：
>
> 1. "读占用窗口的比例 ≈ 50%"的分子只算了 RX **数据**读。补入同一窗口的 RX 控制读（556 × 255 µs）、credit 读与 TX 写（248 × 188 µs）后，
>    **已记账事务占用是 63%**（另有独立复算得 58.2% / 61.5% / 69.0%），**"一半时间总线空着"不成立**。
> 2. 上表的分母用的是 25 MHz × 4 bit = 12.5 MB/s，而实际时钟是 **23.4375 MHz = 11.72 MB/s**（§2.20）⇒ "开销约 24%" 实为 **19.5%**。
> 3. 本节的 ≥8 KiB 大读口径正确，但同一窗口里还并存 ≤512 B 的单块读（固定开销占其跨度约 70%），
>    因此"每字节成本已贴着总线"只在大读相成立，不能写成 RX 的普遍结论。

结论（更正后）：**RX 大读的每字节成本确实接近总线**（9.43~9.5 MB/s，为原始总线的 80%）；
但"RX 的限制在交付节奏、固件/对端没持续供货"这一判断**不成立**——它的前提（总线一半时间空着）来自口径不全的分子，
且"总线空闲"与"固件无货"是两个断言，现有探针只覆盖了前者（`card_irq_rearm_allowed` 要求"无事务在飞"，
使"固件此刻有货"在主机侧的可观测窗口被自己的事务遮住）。A-MSDU 确实在用（只在低吞吐窗口出现，
`amsdu=` 达 684，与吞吐呈反相关），对总吞吐没有解释力。

### 会话变量的进一步定位：天线姿态（2026-09-28）

用户在一轮 Linux 对照测试中发现**天线姿态与板卡放置方式严重影响 TX、略影响 RX**，怀疑金属天线座与其他焊点短接、
或引脚与其他材料接触导致天线/信道异常。三份日志的读数吻合这一判断：

| 日志 | 姿态 | MCS 分布 | `rssi` 范围（中位） | 吞吐 |
| --- | --- | --- | --- | --- |
| `…180304` | 悬空正确姿态 | **9~11 为主**（76/55/45） | −43..−17（−26） | RX 31.3/31.2、TX 27.2、双向 21.3/8.39 |
| `…180941` | 故意摆弄 | 9~11 减少，跌到 7 一带 | −39..−13（−25） | TX 23.3 |
| `…181130` | 故意摆弄 | **塌到 3~7** | −32..−8（−23） | RX 29.3 |

扰动时**速率控制塌到低档而 `rssi` 反而更高**——这正是发射侧变差的形态（对端听不清本板 → ACK 失败 → RC 降档），
与"天线匹配/接地被改变"相符，而单纯的距离变化只会让 `rssi` 一起变差。
因此 §2.17 把会话变量归给"PC 热点状态"是不完整的：**姿态/放置是同一量级的变量**，且它对 TX 的影响更大。
板测协议相应补充：**每次测量前确认板卡为悬空正确姿态**，并把当轮 MCS 分布与 `rssi` 一并归档。

## 2.20 同床对照：厂商 Linux 与我们的差距是均匀 ~2 倍（实测，2026-09-28）

用户在同一天、同一热点（SSID `aasta`、网关 192.168.137.1）、同一块板上跑了一轮**厂商 Linux** 与一轮 **dev 主线内核**，
日志分别归档在日志目录的 `linux-wifi/` 与 `dev主线wifi/`（两者均为测试床上的对照，不含本工作树改动）。

| 运行 | 发送（板→PC） | 接收（PC→板） | 双向 板发/板收 |
| --- | --- | --- | --- |
| 厂商 Linux（找到较好姿态后的最后三轮） | **56.5** | **50.4** | 48.9 / 12.1 |
| 厂商 Linux（同日志中姿态不佳的轮次） | 5.35~22.1 | — | — |
| 我们（StarryOS，正确姿态最好会话，§2.19） | 27.2 | 31.3 | 21.3 / 8.4 |

三条结论：

1. **差距与频段无关（用户已在 Linux 侧直接读数确认）**：厂商 STA 连到 SSID `aasta` 时读到的链路是
   **freq 2412 MHz（信道 1）、20 MHz 带宽、信号 −22 dBm**——即厂商确实工作在 2.4 GHz，与我们的 20 MHz 2.4 GHz 完全同频段同带宽。
   配合"同一个 Windows 热点"这一事实（Windows 移动热点按设置只工作在一个频段；本板只声明 2.4 GHz 信道却能在该热点上关联 → 热点是 2.4 GHz），
   且 TCP 56.5 Mbps 在 2.4 GHz 20 MHz HE（PHY 143）下占 40%、在 5 GHz VHT80（433）下只占 13%——数值形态也只符合 2.4 GHz。
   因此"厂商跑在 5 GHz"这一可能被排除：**差距是同一频段与带宽下的真实差距**。
2. **差距是均匀的 ~2 倍**（发送 2.1 倍、接收 1.6 倍、双向发送 2.3 倍）。
3. **双向的接收塌陷不是本驱动的缺陷**：厂商在双向里同样是"板收 12.1 对单向 50.4"，跌幅比例（24%）与我们（27%）几乎一致
   → 该形态属于测试床/TCP 行为，**从待归因项中移出**。

### SDIO 总线速率：已查清，且**不是差距的原因**（更正）

上一轮我据厂商日志里的 `Mode: SD High Speed (50MHz)` 推测"厂商跑 50 MHz、我们 25 MHz、差距可能来自总线速率"。
调查后该推断**不成立**，两点更正：

1. `Mode: SD High Speed (50MHz)` 是**模式名**（SD High Speed 模式最高支持 50 MHz），不是实测速率；同一段日志的相邻行写着
   `Bus Speed: 25000000` —— 厂商的实际总线速率也是 **25 MHz**。
2. 厂商板级 DTS 对此有明确取舍：`build/boards/sg200x/sg2002_licheervnano_sd/dts_riscv/sg2002_licheervnano_sd.dts`
   在 `wifisd` 节点把 `//max-frequency = <50000000>; //45Mhz; //40Mhz; //35Mhz; //30Mhz;` 全部注释掉，最终取 `25 MHz`；
   基线 `soph_base.dtsi` 里该节点虽写 50 MHz，但板级文件覆盖为 25 MHz。

本驱动侧同样是有意为之，且**代码里就写着原因**（`drivers/blk/cv181x-sdhci/src/clock.rs:29-53`）：

```
ClockSpeed::Default | ClockSpeed::Sdr12 => (25_000_000, false, SDR12),
// SG2002 SDIO1 becomes unreliable during large CMD53 firmware
// writes above 25 MHz even though the card advertises SHS.
ClockSpeed::HighSpeed | ClockSpeed::Sdr25 => (25_000_000, true, SDR25),
ClockSpeed::Sdr50 | ClockSpeed::Sdr104 | ClockSpeed::Ddr50 | ClockSpeed::Hs200 => Err(Unsupported),
```

即"超过 25 MHz 不稳定"是**本项目自己的结论**，方向上也与厂商板级 DTS 的取舍一致（厂商 DTS 把 50/45/40/35/30 全部注释掉；
但厂商 BSP 运行期会覆盖该上限，见下）。
两条控制器是分开的：microSD 在 SDIO0（`0x4310000`，`cvitek,cv181x-sd`），AIC8800 在 SDIO1（`0x4320000`，`cvitek,cv181x-sdio`），
各自有独立寄存器、IRQ 与 pinmux → **改 SDIO1 的速率不会影响卡槽**（但速率策略写在共享的 `clock.rs` 里，改它会影响两路的策略）。
本驱动实际时钟 = 375 MHz ÷ (2×8) = **23.4375 MHz**；SDIO 卡已通过 CCCR 切到 High Speed 模式（`sdmmc-protocol` 内），
只是策略把该模式映射到 25 MHz 而非 50 MHz。

**结论（分两半，注意第二半是"未定"而非"否"）**：

1. **我方这一侧**：23.4375 MHz 是**有意封顶**，且要提高它面对的不是"改个数字"，而是本项目**缺失的 UHS-I 信令与 tuning 支持**
   （见下）。改善卡槽无关，改的是 Wi-Fi 那一路。
2. **厂商那一侧：不能断言"厂商也跑 25 MHz"。** 厂商板级 DTS 把该节点上限写成 25 MHz，但厂商 BSP 驱动对 D80 直接请求
   **150 MHz** 并**绕过内核钳位**；而**整个记录里没有任何一次 Wi-Fi SDIO 时钟读回**（见下）。
   → 因此"两边同为 25 MHz"是我基于 DTS 的**推断**，不是实测。该项由"关闭"**降级为"待一次读回定论"**：
   在厂商 Linux 上读一次 `debugfs` 的 mmc `ios`（`/sys/kernel/debug/mmc*/ios` 的 `clock:` 字段）即可终结，
   **这是当前性价比最高的一次补测**——若厂商实际跑在 100/150 MHz，则"总线速率"要重新回到待归因项。

#### 该结论的出处与强度（追查记录）

"超过 25 MHz 不稳定"在全部记录里**只出现一次**：`drivers/blk/cv181x-sdhci/src/clock.rs:37-38` 那两行注释本身。
`git log -S "becomes unreliable"` 指向唯一提交 `0fc626fa4`（`refactor(sdmmc): unify SDIO protocol and AIC8800 driver (#2201)`），
该提交在**同一处 diff 内**把 `program_clock(50_000_000, …)` 改成 `program_clock(25_000_000, …)` 并加上注释
→ 25 MHz 封顶是**有意为之**，但它的理由**只以这两行断言存在**：没有配套设计文档、测试、errata 引用或测量记录，项目内也无第二处复述。
强度判定：**证据等级低（单一断言）**，但它是被追踪的正式源码注释，且方向与厂商板级 DTS 的取舍一致。

需要注意一处**内部不一致**，当前封顶的注释理由并不能由它解释：早期个人笔记 `www/before-refactor/wifi-analysis.md` 记录 50 MHz 失败的原因是
**PHY delay 未配置导致 DAT CRC error**，并在补上 `MSHC_CTRL|=bit1` + `PHY_CONFIG|=bit0` + `TX_RX_DLY=0x01000100` 之后记录了 50 MHz **成功**
（`+ 50MHz SDIO + PHY + 修空转 | 13.7M`）。这三个 PHY 设置**当前代码确实会写**（`board.rs:154-160`），
也就是说"PHY delay 缺失"这条旧原因与现行注释并不一致——注释所依据的失败条件没有被记录下来。

平台侧的其它事实（用于界定"能不能更高"）：

- 生效速率是 `min(DTB max-frequency, 25 MHz)`：`clock.rs:41` 对 `HighSpeed/Sdr25` **硬编码** `25_000_000`，
  `clock.rs:43-45` 直接把 `Sdr50/Sdr104/Ddr50/Hs200` 判为 `Unsupported`
  → **只改 DTB 的 `max-frequency` 不会提高总线速率**，必须同时改 `clock.rs` 策略。
- `HOST_CONTROL2::UHS_MODE` 在本项目里只有 `SDR12`/`SDR25` 两个取值，UHS-I 的 SDR50/SDR104/DDR50 信令**目前连表达都不支持**。
- 本项目**没有 tuning 实现**：`cv181x-sdhci` crate 里没有 `ExecuteTuning` 处理，`tuning` 只出现在测试断言与 `sdmmc-host` 的 bus-op 枚举/CMD19/CMD21 定义中；
  而厂商驱动有完整的 `sdhci_cv181x_general_execute_tuning` 与 1.8 V 切换流程。**UHS-I 需要 tuning，这是真正的门槛，而非寄存器上限。**
- 厂商侧不存在"平台把 150 MHz 钳到 50 MHz"这一说法：厂商 D80/D80X2 走 `FEATURE_SDIO_CLOCK_V3 = 150000000`
  （`aic8800_bsp/aic_bsp_driver.h:528-529`、`aic_bsp_driver.c:2120-2128`），且该赋值**绕过内核钳位**——
  它直接写 `host->ios.clock` 后调 `ops->set_ios()`（`aic_bsp_driver.c:1742-1744`），不经过 `mmc_set_clock()`；
  `sdhci.c` 的 `f_max` 只会被**抬高**到 `max_clk`，`sdhci-cv181x.c` 的 `get_max_clock()` 返回 `f_src = 375 MHz`。
  **厂商树里找不到任何把 SDIO 时钟钳到 50 MHz 的代码**——所以此前笔记里"被平台钳制到 50 MHz"一句没有代码支撑。
- 运行期记录里，本驱动只提交过两次时钟操作：`SetClock(Identification)`（400 kHz）与 `SetClock(Default)`（25 MHz），
  随后打印 `sdio: SD speed selected HighSpeed`。`SdioRequestKind::SetClockHz` 虽然已定义并在 `operation.rs` 中被匹配，
  但**从未被构造**，即驱动在初始化之后不再请求更高时钟（`BusOp::SetClockHz` 在 `host2.rs:152-157` 是实现了的）。

另一处需要更正的前提：记录中所有 `Mode: SD High Speed (50MHz)` 的出现，**都紧跟在 `Bus Speed: 25000000` 之后、且都属于 u-boot 打印的 `cv-sd@4310000`（microSD 卡，SK64G）**。
`(50MHz)` 是 u-boot 对 `SD_HS` 的**枚举标签**（`u-boot-2021.10/drivers/mmc/mmc.c:149`），该字符串在厂商树中仅此一处。
**记录中不存在任何 Wi-Fi SDIO 控制器（`wifi-sd@4320000`）的时钟读回**，厂商 Linux 串口日志里连 u-boot banner 与 mmc/sdio 时钟行都没有。

**据此，"我方提高时钟"若要验证，工作量不是改一个数字**：需要先补 UHS-I 信令表达与 tuning、再改策略、再实测信令完整性；
且其收益取决于上面第 2 半的答案——**先把厂商那一侧的读回拿到，再决定是否值得投这条路**。
此外，我方的实测约束仍然成立：RX 每笔读已贴着 25 MHz 总线跑（§2.19），TX 的周期六成是单笔写自身、credit 见底（§2.18），
所以即使总线翻倍，也不必然按比例反映到吞吐上。

## 2.21 瓶颈归属审查：形状是「每笔固定开销 + 事务间空档」（实测+复算，2026-09-28）

一轮以"驱动瓶颈到底在哪"为问题的多智能体审查（7 名 reviewer 独立判定 + 三方交叉质证，全文见
`ocr-review-20260928-bottleneck-round1.md`）对全部板测日志逐窗重算后，收敛到以下结论：

| 结论 | 依据 |
| --- | --- |
| **约束的形状是"每笔固定开销 + 事务间空档"决定事务率，不是每字节速率** | 对 771 个上行窗做窗内回归，**0/771 出现负截距**，中位固定项 **445 µs**（IQR 366–550）；全量 2169 窗独立拟合 `span ≈ 480 + 0.096·B`，同时命中窗口均值（预测 5.05 MB/s、实测 5.052）与观测上界（1154 窗无一超 5.72 MB/s）。例外是单块（≤512 B）写，仅 147 µs |
| **两个方向的每字节边际成本相同** | 写 9.11~10.43 MB/s、读 9.88 MB/s，折算 85.3 ns/B ≈ 铭牌总线 11.72 MB/s。此前"写 5.7 对读 9.5 MB/s"的差是固定项摊薄程度不同造成的假象（写每笔 6144 B、固定项 516 µs；读每笔 21246 B、固定项 463 µs） |
| **固定项里至少一半已实测是主机侧** | 1447 个 executor 窗口（Σdt≈3010 s）：`owner 20.65% + poll 3.33% + park_sw 12.50% = 36.5% 墙钟 / 360 µs 每笔写` |
| **`handoff` 按构造 100% 是内核软件时间** | 中断 → 执行器恢复的两端时间戳都在软件里，区间内无总线操作；TX 重窗实测 346 µs × 1182 = **20.4% 墙钟**（约占单笔写的 34%）。机制候选：owner 循环所在的 `net-queue-cpu0` 与 `net-protocol` 同权重、同 700 µs 片长，唤醒时的条件抢占被拒（`fair_wakeup_preempts`） |
| **每笔字节数被默认的 4 帧 / 6144 B 钉死** | 两个入库 DTB 都没有 `aic,tx-aggregation` / `aic,tx-aggregate-bytes` 属性；厂商对应 32 帧 / 96 KB |
| **credit 不系统性夹取** | `credit max` 中位 **131**、1105/1154 个窗口 ≥31（直接读数）；`aggregate_limit()` 在 credit ≥34 时不夹。把 credit 均值五等分，`backoff`/写从 1.649 掉到 0.000（40×）而速率只从 5.21 变 5.07 MB/s（−3%） |
| **时钟不是主因** | 翻倍时钟的上界在 **1.15×**（窗内口径）到 **1.34~1.56×**（事务层口径）之间，两者都 < 2×；厂商侧实际时钟仍无读回（§2.20 保持"待一次读回"） |
| 空口税 | **口径已更正（§2.26）**：`ack_fail_stat`/`ack_succ_stat` 的跳动频率只有 MPDU 速率的 1/4~1/5，不是每帧统计；原先"首次尝试失败率 24%~28%"的读法不成立，该行降级为"计数器读数，口径未定" |

**仍未定论**：固定项在"设备反压（固件不放行）"与"主机侧 park / 中断恢复 / 拷贝"之间的最终归属。
裁决它需要两条测量（缺一不可）：**把每笔写跨度按提交时 credit 分桶**、**SDIO 提交/完成边界时间戳**。

同时被该轮审查记录在案的口径缺陷（本节其余各处的更正即由此而来）：分母混用 25 MHz 与 23.4375 MHz、
`period ≡ gap + rtt` 被当作独立验证、credit 采样内生、`gap` 的 rx 分桶是事后分类、
`ChainMiss::Idle` 与 `supply none` 不同义、`retries` 是配置常数却被当作重传统计量、"累计 ack 失败 15%" 出自另一会话且是累积值。

| 16+ | 21242 | 1036 µs | 5453 | 190 |

- **保留位桶在三个测试里都是 0 笔**：这一会话里设备从未把我们压到最小写。`min=2` 是本地记账的停止线，不是设备事实。
- 跨度**随 credit 下降而变短**（788 对 1036 µs），因为写里装的帧更少（3189 对 5453 B）；每字节成本反而更高（247 对 190 ns/B），
  这是固定项摊薄在更少字节上的形态，**不是**"设备不让我们发"的形态。
- 用最忙窗口的三个桶拟合 `span ≈ F + r·B`：**F ≈ 604 µs、r ≈ 91 ns/B**（总线 85 ns/B，即边际效率约 93%）。

**M3 —— 按设备中断切分往返：post 段全是主机软件时间。** `[wifi-probe-time]` 的 `irq split` 把每笔事务的跨度切成
"进中断前（`pre`）"与"出中断后（`post`）"两段。两段之和等于该笔跨度是**计时口径本身**（同一个起止时刻按中断时刻切开），
不构成对分段正确性的验证；成立的是两段的**绝对值与占比**——`post` 段两端的时间戳都在软件里，按构造不含总线活动：

| 方向 | pre（中断前） | post（中断后） | post 占往返 |
| --- | --- | --- | --- |
| TX 写（饱和窗口，中位） | **724 µs** | **396 µs**（最高 449） | **35%** |
| RX 数据读（22.3 KiB/笔） | **2150 µs** | **245 µs** | **10%** |

post 段按构造不含任何总线活动（两端时间戳都在软件里）：它是 ISR 体 + notify + 调度唤醒 + owner 恢复并取走这笔完成。
执行器探针的 `handoff`（中断 → 执行器恢复，332 µs）独立给出同量级的值。

**M6 —— 按时间口径的占用（饱和窗口）**：`tx` 事务占窗口 **73%~77%**、`accounted` **83%~85%**、`supply none` 约 **7%**。
纯 TX 测试整段的 `supply none` 是 39%（27.2 s / 70.6 s），但其中 **22.9 s 落在 16 个未饱和窗口**（约占整段的一半窗口，写笔数合计只有 3313 对饱和窗口的 23000+）
——饱和时供帧不是限制项。RX 测试里 `rx` 事务占窗口 **48%~55%**，每笔 22.3 KiB、**105~108 ns/B**。

### 归属

**每笔写 1133 µs 的构成**：数据相约 522 µs（6114 B ÷ 11.72 MB/s）+ 中断前非数据约 200 µs（控制器/设备/ISR 投递）+ **中断后主机 396~415 µs**。
三块里最大且唯一与"已知在临界的方向"无关的一块是**主机在设备报完成之后的 396 µs**：把它去掉，写跨度降到约 737 µs，
同一窗口的发送上限从 28.3 抬到约 **43 Mbps**——与同床对照里厂商比我们多出的那部分同量级。

因此本轮把 §2.21 的"待定归属"判为**主机侧**，且定位到**完成路径（ISR → 唤醒 → 恢复 → 取走完成）**，不是提交路径、不是总线、不是空口：
- 提交侧无余量可言：饱和窗口里写事务已占 77% 窗口、`accounted` 85%，`supply none` 仅 7%；
- 设备侧只有约 200 µs/笔（中断前非数据），且 M1 显示设备压力只改变写的大小、不改变每字节成本；
- RX 方向的同一段只有 10%，说明这不是全局的唤醒问题，**是写路径完成处理特有的**。

### 本轮暴露的观测缺口（下一轮补）

1. **credit 最高桶（16+）太宽**：要回答"能否一笔装 32 帧"需要知道有多少笔的 credit ≥34（`aggregate_limit()` 在 credit ≥34 时不再夹取）。
   当前数据只能说 81% 的写在 16+ 桶里。
2. **post 段内部未分段**：396 µs 里"ISR 体""notify 唤醒""调度恢复""取走完成"各占多少还没分开；
   零代码代价的下一步是打开已注册未启用的 `sched:sched_switch`。
3. **IRQ 时间戳可能被同窗的 CARD_INT 覆盖**（非事务相关的卡中断也会更新该戳），使 post 偏短、pre 偏长；量级判断不受影响，但精确定位前需要按事务类型过滤。

## 2.24 与厂商驱动的机制对照：差异在"喂"与"取"的节奏，不在 FIFO 语义（源码只读对照，2026-09-28）

对厂商树（只读参考，路径不入库）的两个方向做了逐点对照，结论先说：**流控/FIFO 的语义两边完全一致，差异在主机侧"喂"与"取"的节奏。**

### 被排除的差异

| 曾经怀疑 | 实际 |
| --- | --- |
| 固件**推送** credit、我们只轮询 | 厂商那份代码里推送通道同样停用（处理函数仍在注册表，但 `txq->credits += update`、回执里的 `cfm.credits`、`txq->credits--` 全被注释），实际同样直读 0x03 寄存器 |
| 聚合公式不同 | **逐字相同**：厂商 `min(tx_aggr_counter=32, fw_avail_bufcnt − 2)`，我们 `min(packets, credits − 2)`；两边都永久留 2 个不填 |
| 厂商 RX 预投缓冲、设备推 | 厂商 RX 同样是**纯主机拉**：先读块计数再整批读走，全树没有向卡预投 RX 缓冲的路径 |
| 厂商 RX 不复用/零拷贝 | 默认同样是每次分配、读入后再 memcpy 出包（预分配池需显式开关，且取用时仍 memset） |
| "命令与数据共用池" | **核实成立**（同一个 0x03 寄存器同时门控数据写与命令写）；但"RX 排空会抬高该池"**未找到任何厂商主机代码支撑**，不应写成代码事实 |

### 真正的差异

**TX——聚合点前面有没有积压。** 厂商是 **pull**：SDIO 发送线程在即将聚合的那一刻，才从一个**授权 64 帧的 txq + 8192 深的 SDIO 队列**里按需取帧；
我们是 **push**：帧先进一个 **32 槽**的 SPSC 环，`submit_one_tx` 一次推进取完就 `break`。于是我们的写长真实上界是
`min(K, credit−2, **那一刻环里已有的帧数**)`，**第三项最小**——这正是 §2.23 里"credit 34–65 允许 32 帧、实际只装约 17 帧"的原因。
另外厂商的发送线程被提为 SCHED_FIFO、一醒就排到空或排到 credit 见底、**中途不让路给 RX**；我们显式限制"每次推进只续发一笔"给 RX 让路（`data_plane.rs:776-784`）。

**RX——一次中断取一批，还是轮询到空。** 厂商：一次中断 = **一次读**，把卡报出的整批（计数字节 × 512 块）一次取走，**读完不回读计数**；
我们：武装扫描 → 逐 path 轮询计数 → **读到空为止**（每笔数据读多付约 1.2 次计数读），且卡中断在每个 action 边界被置 Masked、
只在"无事务在飞"时重武装（`rdif/owner/progress.rs:551-556`）。量化：每笔读的 4.37 ms 周期里约 **1.86 ms** 不落在任何事务里。

### 由此得到的三个待验读数（已做出镜像）

1. **卡片报的块数分布与上限**：`rx count empty/blocks/...`、`blocks max`、`blocks 1/2-8/9-32/33-64/65+`——判断 21~22 KiB 是不是卡自己的批上限。
2. **refill 节奏**：从"读到空"到"再看到数据"的间隔（`refill n/avg/min/max`，超过 0.1 s 计入 `idle` 不参与统计）——判断是卡的自定时还是我们的轮询步调。
3. **mask 语义**：`irq rearm n=… card_pending=… completion_pending=…`——重武装时卡中断是否仍 asserted，即被遮蔽期间到的通知是否还在（决定我们是否在白等卡下一拍）。

## 2.25 接收侧三问的答案与加深发送环的对照（实测，2026-09-28，提交 `4c07118b5`）

### 接收侧三问：卡在什么节奏上

| 问题 | 读数 | 结论 |
| --- | --- | --- |
| **卡片报的批上限** | 三臂一致：**块数最大 = 63**、`65+` 桶**零样本**、`64~127` 之间无任何样本；忙窗里 `33-64` 桶占多数 | **实测批上限是 63 块 = 31.5 KiB**（32 位掩码理论上界 127 块从未出现）。我们实测每笔约 40 块（20 KB），即用了上限的约 63% |
| **refill 节奏** | 从"读到空"到"再看到数据"：**avg ≈ 7.5~8.7 ms**、min ≈ 0.2 ms、max ≈ 30~55 ms（>0.1 s 记 idle） | 同口径取值（**平均**批 42~45 块 = 21~22 KiB ÷ 平均间隔 8 ms）≈ **21 Mbps**，低于实测接收吞吐（31~34 Mbps）⇒ 卡的交批节奏**足以供上**主机；批上限 63 块 ÷ 平均间隔 8 ms 是不同口径的拼装，不能直接与吞吐相比 |
| **mask 期间的通知** | `irq rearm` 里 `card_pending` 仅 **1.8%~2.4%** | 通知基本不丢，与标准 SDIO 电平语义一致 ⇒ **43% 空档不是"我们在等下一次边沿"造成的** |

| --- | --- | --- | --- |
| 字节/笔 中位 | 19740 | **22971** | 19715 |

| credit 66+ 桶 字节/笔 | 14396 | **24218** | 19254 |

把这两者对齐——**credit 低时先等，不要立刻发小写**——是当前唯一有量化依据的发送侧候选：
它直接冲着那 29% 的 263 ns/B 小写去，而这批写在加权成本里占了近一半。

## 2.26 更正：`ack_succ_stat` / `ack_fail_stat` 不是每帧统计（结构核对 + 量级检验，2026-09-28）

**结论：本文档此前多处把这两个计数器的比值当作"空口首次尝试失败率"，这个读法不成立，一律降级为"口径未定的计数器读数"。**

### 结构核对

厂商 `struct mm_get_sta_info_cfm` 的字段名是 `rate_info@0` / `txfailed@4` / `rssi@8` / `chan_time@12` / `chan_busy_time@16` /
**`ack_fail_stat@20`** / **`ack_succ_stat@24`** / `chan_tx_busy_time@28`，共 32 字节（与我们 `STA_INFO_CONFIRMATION_LEN = 32` 一致）。
名字是 "stat"，不含单位；而且**厂商驱动全树从未使用这两个字段**（除结构定义），因此没有可继承的语义——"失败率"是从字段名推出来的。

### 量级检验（三臂，只取有实际流量的秒）

| 臂 | Mbps 中位 | 推算 MPDU/s（按 1500 B/帧） | `ackok_d + ackfail_d` 中位 | **(ok+fail) / MPDU** |
| --- | --- | --- | --- | --- |
| A1 | 32.5 | ≈2708 | 556 | **0.21** |
| B1 | 32.5 | ≈2708 | 677 | **0.27** |
| A2 | 33.5 | ≈2792 | 772 | **0.32** |

计数器跳动频率只有 MPDU 速率的 **1/4~1/5**，所以它不可能按帧计数；更可能是**每次空口聚合尝试 / 每个 BlockAck** 一级的统计。
若按"每次 A-MPDU 尝试"读：`fail/(ok+fail) ≈ 24%~30%` 意思是"约四分之一到三成的聚合里至少有一个 MPDU 失败"，
对应**每 MPDU 的首次失败率只有百分之几**——属于 802.11 的正常范围，而不是异常高的空口税。

### 受此影响的既有表述（均降级）

§2.19 的"累计 15%"、§2.21 的"空口税 24%~28% 真实但不可叠加"、§2.17 的"ack 失败约 31%"、
§2.25 与跟踪文档中的"ack 失败率三臂相近（29/26/26%）"——它们作为**计数器读数**仍然成立，但**不能再用作链路质量或空口税的证据**。
同一批读数在别处的残余用法一并按此处理：§2.16 的 `ackok`/`ackfail` 会话末计数与"约 15%"、
§2.17 里"ack 失败约 31%"以及把"ack 失败升高"当作两条推断支撑项的用法——
这些位置保留原始读数，但不再由它们单独支撑因果判断。

### 顺带发现的空白：三个从未解析的信道时间字段

## 2.28 读数口径与已知观测盲区（2026-09-28）

第三阶段的结论都建立在探针与遥测读数上，下面几条是**读这些数时必须先约定的事**，以及当前**测不出来**的部分。

### 每字节成本的两种口径

同一批日志可以算出两个数，量级差 20%~30%，不能混用：

- **按笔加权**：先算每个 credit 桶的 `Σ跨度 / Σ字节`，再按各桶的**笔数份额**加权。它回答"一次写平均每字节花多少"，
  小写多的时候被拉高。
- **按字节加权（`Σt/ΣB`）**：整段的 `Σ跨度 / Σ字节`。它回答"整段流量平均每字节花多少"，大笔占主导。

两者在 §2.23、§2.25、§2.27 中都出现过；引用时必须写明是哪一种。窗口内比值（如小写占比）不受此影响。

### 计数器语义的变更

`[wifi-probe-time]` 的 `backoff=N avg=X` 在提交 `3cb53bb17` 之前只统计**保留位退避**（credit ≤ 2 时的 200 µs 重试），
之后**同时**统计新增的薄池等待（credit 3~7 时 300 µs 的重问）。跨该提交比较该计数器无效；
§2.22 及更早引用它的窗口（如"`backoff` 225 次/秒"）只在本提交之前成立。

### 每个数落进文档前必须先登记的口径（2026-09-28 起）

历次审查揪出的错误全都发生在"算完之后"，且每一处单看都能自圆其说。因此**先写口径、再算数**，每条读数按下面六项登记：

| 项 | 要写清的 |
| --- | --- |
| 总体 | 分子、分母各自覆盖哪些笔/窗口/会话 |
| 加权 | 按笔加权、按字节加权、还是不加权（计数比） |
| 范围 | 单窗口、活跃窗口集合，还是整段会话合计 |
| 粒度 | 时间戳取自哪一刻（当前是 owner 调用入口），窗口内的量是否被量化 |
| 可比性 | 计数器语义是否跨提交变过（见下一节） |
| 选样 | 全量，还是明确的、与结论无关的选取规则 |

**硬性禁止**（每一条都实际犯过）：

- 跨口径相减或相除（如按笔加权减按字节加权）；
- 拿最大值配平均值（如批上限 ÷ 平均间隔）；
- 用按构造成立的量作验证（分段之和等于总跨度、占比之和为 100%）；
- 取"最后 N 个"或"最忙的那几个"样本而不给全分布；
- 把单窗口的数当整段写；
- 用跨会话吞吐作收益证据（只作方向）。

**本阶段首选的证据形态是确定性计数器**（拷贝次数、拷贝字节数、调用次数）：它们不受加权、窗口、样本选取影响，是唯一能"一眼核对"的证据。

## 2.29 全归因探针首轮实板：总线已近满速，空档是我们的（2026-09-29）

镜像 `sg2002_starryos_wifi_sta_attrib2_20260928.img`（基座 q64、DTB `lcn-sta-defer0`、编译期 STA 凭据 `aasta`），
日志 `[com COM6] (2026-09-29_065738)`。配置 `clock=on agg=32x49152`（framed 路径）。
按窗口分两段，各 10 个稳态窗口：纯 TX 80.769–98.786 s（375 笔/窗、21063 B/笔、31.6 Mbps 探针口径）、
双向 104.789–122.796 s（298 笔/窗、24923 B/笔）。**两段不混算**。

### 仪器本身：闭合成立

`pre` = `dispatch + dma + program + bus`，21 个窗口内逐窗落在 ±9 µs（量值 1855–2569 µs，即每段一次读时钟的加性偏移）；
四条腿的样本数与写笔数相等（如 428/428/428/428 对 428 笔），**每笔写的四段都被量到**；
窗口内 `写笔数 × 周期 = 96.3% 的 dt`。`split drops` 只落在接收/控制侧，发送侧零丢失。

### 一条被推翻的旧结论：不存在"每笔固定开销"

`bus` 按写长分桶（<=4k … 32k+，各桶 n 与字节见日志）两项拟合：**边际 ≈ 11.2 MB/s、截距 ≈ 0 µs**，
即数据相跑在总线原始速率 11.72 MB/s 的 **96%**；接收读同口径 11.66 B/µs = **99.5%**。

因此第三阶段赖以立论的"每笔固定开销 445~604 µs（与承载字节基本无关）"是**旧往返口径的产物**：
旧口径把起点定在 owner 调用入口，续写那一步自身的成形与上一笔收尾都被算进"往返"。
按 emit 锚点重测，**命令相与卡访问的开销小到量不出来**——"命令/卡访问"不是可动的杠杆。

| 段 | 纯 TX µs/笔 | 双向 µs/笔 |
| --- | ---: | ---: |
| `bus` | 1869 | 2218 |
| `post`（中断→我们开始跑） | 389 | 372 |
| `dma` | 140 | 154 |
| `program` | 53 | 55 |
| `dispatch` | 3 | 3 |
| 往返合计 | 2458（周期的 46%） | 2803（43%） |

### 周期账：一半以上不是往返

| | 纯 TX | 双向 |
| --- | ---: | ---: |
| 周期（完成→完成） | 5310 µs | 6459 µs |
| 空档（周期−往返） | 2852 µs（54%） | 3655 µs（57%） |
| ├ owner advance 工作 | 362 | 539 |
| ├ `pull`（环→核心队列） | 105 | 121 |
| ├ `release + rx_copy` | 14 | 71 |
| ├ **credit 退避等待** | **1017** | **418** |
| └ 其余（停着没跑） | 1354 | 2506 |

总线占用：纯 TX 的写占窗口 **35.0%**（双向 33.1%），接收读另占约 8%；**总线上有近六成时间什么都没有**。

### 机制：完成路径空手结束，环里的帧没人取

三个读数并排看即得：

- `rdif_at_write` 非空 **62.6%**（纯 TX）/ **53.9%**（双向）——写完成时 RDIF 环里**已经有帧**；
- `chain idle` **49%/53%**、`chain flow` 32%/26%、`chain write` **0%**——续接要么找不到可续的写，要么改为先读流控；
- 代码：续接只从**核心队列**取帧（`prepare_next_transmit`），而环→核心的 `pull` 在 owner 的 `submit_one_tx`
  （`rdif/owner/progress.rs:320`）；核心在无事可做时返回 `AicAction::WaitForInterrupt`，owner 对此
  **立即结束本次调用**（`progress.rs:401-406`）。于是同一次调用里排在后面的 `submit_one_tx` 不会执行，
  下一笔写要等下一个外部事件（新帧到达通知、卡中断或到期）才发出 ⇒ 空档 2.9/3.7 ms。

`supply` 分类与此一致：纯 TX 下 core 17.8% / ring 5.4% / none 18.8%，双向下 core 5.9% / ring 15.1% / none 22.2%
（占窗口；三类只覆盖空档的约 85%，首个 gap 无前序完成时不计，缺口已知）。
"哪里都没有帧"（上游）只占 19–22%，**"有帧却不在飞"（core+ring）占 21–23%**。

### 与并行设计文档的对照

同日志、同子集的独立复算（`gpt/aic8800-hardware-async-pipeline-design.md` §1.2）**基础数字全部复现**：
`P`(pull+form+bytes) 379/465 µs、`dma` 140/154、`bus` 1869/2218、`post` 389/372、
`dispatch+dma+program+bus` 2065/2446、环非空 62.6%/53.9%、深度≥4 56.4%/49.4%、`queue_at_arrival` 非空 95.2%/95.8%。

分歧在读数的分母与遗漏项：
1. 该文档以**服务周期**（P+往返+post = 2843 µs 纯 TX）为分母，得出"最多遮蔽 13.3%/18.3%"；
   实测周期 5310 µs，服务周期只占 **54%**，换到吞吐口径即 **7.1%/9.8%**。
2. 该文档未列 **credit 退避**（纯 TX 1017 µs/笔，比 `P` 的 379 µs 更大）。
3. 该文档未使用 `chain` 计数器；而其引用的"完成前 RDIF 非空 62.6%"恰是"帧已在环里、只差一次 pull"的证据——
   也就是说，缺的不是"提前成形"，而是**完成路径里没有把环里的帧取出来**。

### 归因探针的语义变更（2026-09-28 第二轮，跨轮不可比）

1. **往返起点 = emit 时刻**（旧：owner 调用入口）。续写那一步的跨度不再含自己的成形与上一笔的收尾。
2. **`pre/isr/post` 与 `bus` 归到"结束该事务的中断"**：旧口径取"这段时间里最后一次非 spurious 中断"，
   落在 post 窗口里的卡中断会把宿主唤醒时间记进 `bus`、同量压低 `post`；经 rearm 缓存取走完成时整条 split 被丢弃
   （现计入 `split drops=`）。方向与"时间花在设备上"的假设相反，量级估计占完成的 10~20%。
3. **leg/stage 是可被中断的墙钟区间**：别处中断的处理时间落在其中，而 `isr` 只报完成那一次，
   故 `isr ≈ 2 µs` 只能说明**该次**处理很短，不能说明中断处理总量可忽略。
4. **每段带一次读时钟的加性偏移**（时间基 25 MHz，40 ns 分辨率），与 `bus by write` 拟合的固定项退化；
   仪器总开销约 30 次读数/笔（0.13~0.35% 往返），总量上可忽略。
5. **`prep` 行不再对称**：`wire_bytes calls` 只描述 framed 臂；两臂的每笔字节拷贝次数在 `copies n=`，
   direct 臂真正消掉的是每帧缓冲（`prep frames n=`）。§2.23 与 §2.27 中"每笔分配归零"的说法按此更正。

### 已知的观测盲区

- **credit 分桶的边界压在阈值上**：等待阈值是 8，而桶边界是 `7-15`，所以事后无法从分桶判断某笔是"等到 8 才发"还是"等满预算后按 7 发了"。
  若要分辨，需要把桶边界改到阈值两侧。
- **`3-6` 桶混有尾写**：`spend_tx_credit` 在池子见底时会把剩余 credit 一次花掉，这类尾写与该桶里的普通小写混在一起。
- **写跨度的时间戳粒度是 owner 调用入口**：窗口内的量会被量化（`class_min` 为 0 即此故），故分桶里的最小值恒为 0，只看平均值与合计。
- **两条遥测共用唯一 mailbox 且 `stopped` 是单向门**：任一遥测超时停机后不再恢复，长会话后段可能没有读数。

## 2.30 round-2 证据审查对 §2.29 的两处更正（2026-09-29）

§2.29 的两条结论在独立的证据与归因审查（5 实例，含厂商对照）后被改写：

1. **「总线不再是可动项」应限定为「在当前 23.4375 MHz 下，每字节不再是可动项」。**
   审查中一度把"厂商对同一颗 D80 请求 150 MHz"列为最强差距候选（源码链：`aic_bsp_driver.h:528-529`
   的 `FEATURE_SDIO_CLOCK_V3`、`aic_bsp_driver.c:2126-2127` 对 D80 的赋值），复核执行路径后否掉：
   D80 只走 `aicwf_sdiov3_func_init`（选择点 fdrv `aicwf_sdio.c:823-827`、BSP `aicsdio.c:335-340`），
   而**两侧 v3 函数里的时钟块都被外层 `#if 0` 包住**（fdrv 3184…3218、BSP 1835…1868），
   活着的两处时钟块只服务非 D80 的 `aicwf_sdio_func_init`。厂商 D80 与我们同吃板级 DTS 的
   `max-frequency = <25000000>`，达成 23.4375 MHz（差 1.067×，折到整窗约 +2.2%）⇒ 不再是差距候选。
   同时 `clock.rs:38-42` 那条"25 MHz 以上不可靠"的注释**失去"与厂商的差距"这个身份**。
   仍可动的是**占用率**：我们 ≈39%（`bus` 1956 µs × 403 笔 / 2000 ms = 788 ms），
   厂商跑 56.4 Mbps 需要 ≈62%。

2. **「空档里 45% 是哪里都没有帧」是推断，不是观测。**
   `supply` 三档是在**写完成那一刻**的瞬时采样、被 `close_gap` 摊到整个空档上；本轮 `supply core` 占
   80.8~85.3% 而该桶空档均值仍有 1.1~1.8 ms ⇒ "帧已在手"不预示短空档。同轮还测出周期账与空档账之间
   300~580 µs/笔的系统偏差（`close_gap` 锚在 owner 调用入口、`emitted` 锚在即时读钟），
   故本项目里"周期 − 往返 = 空档"应改为 **"周期 = 空档 + 步内成形时间 + 往返"**，三段各自注明口径。

时间预算的正确形状（同轮四条独立预算收敛）：全部 SDIO 事务在飞占窗口 45~50%，
**无任何事务在飞占 46.9~51.9%**，执行器 park 占 72~78%（owner 22~23%、poll 2.5%）；
其中可归因的是 credit 自选等待 15~16%（我们自己的策略 `aic,tx-credit-wait-us`，此前从未出现在任何空档归因里）
与"完成时两处都空"的瞬时状态（17% 的笔 × 均值 6~12 ms，推断强度）。
结论措辞改为：**"搬运方式不再是可动项，可动项在两次搬运之间。"**

## 2.31 归因探针第二轮实板：停驻去向、供给节奏与失效的信道占用读数（2026-09-30）

镜像 `…_attrib3_20260929.img`（与 `…_attrib2_20260928.img` 只差内核，仪器改动、行为不变），
同一热点会话内 4 个 iperf3 用例：下行 20 s / 下行 30 s / 上行 30 s / 双向 30 s。

### 停驻去向（`park_end`，76 窗逐窗闭合、八项之和 = `waits`）

| park 结束于 | 下行 | 上行 | 双向 |
| --- | ---: | ---: | ---: |
| 无发布者（到点时事件已置位，从未睡下） | 50.0% | 50.0% | 49.9% |
| 协议交帧（`tx`） | 25.3~25.7% | 12.7% | 13.4% |
| 设备中断（`irq`） | 22.4~23.0% | 14.0% | 14.7% |
| 截止时间（`timer`） | 0.05% | **18.1%** | 14.7% |
| 缓冲归还（`recycle`） | 1.5~1.6% | 5.0% | 6.8% |
| 取帧（`rx`）/ 控制（`ctrl`）/ 其他（`other`） | 0.2% / 0 / 0 | 0.1% / 0 / 0 | 0.4% / 0 / 0 |

**一半的 park 没有睡。** 这一条修正了早先把 park 时长整体当作「睡等」的叙述：执行器多数时候是在
上一轮 poll 期间已经被唤醒、再走一次等待，而不是在等设备。

`wait_kind deadline` 比 `timer` 多 5~12%：前者是「用了定时等待且返回时刻在截止点上」，
后者要求「且没有发布者」。两者不可互换。

### credit 自选等待被独立证实

上行由截止时间结束的 park 合计 **16.1% 墙钟**（4831 ms / 30 s，均 680 µs/次，7103 次），
与 §2.29 的三条读数（15~16%）一致；次数与 `credit backoff`（7642）同量级。
这是执行器侧对同一等待的第三类独立记账（另两类是驱动侧 `credit busy` 与空档分解）。

### 供给节奏

上行 82% 的 poll 开始时核心有帧、18% 哪都没有、`ring` 为 0；下行 85% 是「哪都没有」（只有 ACK）。
上行 `supply 4+` 占 10.4% ⇒ 协议栈是突发式交付，不是持续积压。

### 上行墙钟账（30 s，全部窗口内读数）

| 项 | 值 | 性质 |
| --- | ---: | --- |
| 事务在飞 | **38%**（写总线腿 36%、收 1%、控制 0.9%） | 观测 |
| ├ 写往返 | 2515 µs/笔 = 总线腿 1951（78%）+ 主机 564 | 观测 |
| └ 总线效率 | 写 89 ns/B、收 87~96 ns/B（≈ 物理底速） | 观测 |

**与上一轮数字的关系（不可混算）**：§2.29/§2.30 的「事务在飞 45~50%、无事务在飞 46.9~51.9%」出自上一会话的

**搬运算到底了**（每字节效率 96% 物理底速、`ring` 空档归零）；差距是**占空比**：我们 38%，

### 信道占用读数失效（`chan_time` 三字段）

## 2.32 credit 等待的构成，与两个发送侧旋钮的足迹（2026-09-29 实板）

两次对照（同一内核、同一基座，两两只差 DTB 里的一个属性）把发送侧两个旋钮量清了。

**credit 等待不是空转，而且大部分不归 `aic,tx-credit-wait-us` 管。**
`consume_transmit_flow` 里有两条会设 `retry_at` 的信用分支：薄池分支（`credits 3..=7`，
等 `tx_credit_wait`，默认 300 µs）与保留量分支（`credits <= 2`，等 `IO_RETRY` 200 µs）。
旋钮只作用于前者。把旋钮设为 0 后，**保留量分支与其余截止时间来源（遥测 1 s / 2 s、邮箱、
启动、SDIO 寄存器重试）都不受影响，前者占 credit 等待约 78%**。
因此 §2.31 那条「上行 16.1% 墙钟」不是空转：等待在等固件池回填，以便下一笔写得更大。

**把旋钮设为 0 的实际后果**（`aic,tx-credit-wait-us=0` 对默认 300 µs，严格单变量，实测）：

| 指标（上行窗口） | 默认 300 µs（四次运行） | 设为 0 |
| --- | ---: | ---: |
| `write credit` 3-6 档份额 | 4.8 / 4.9 / 6.4 / 5.4% | **20.2%**（逐窗 64/68 ≥10%，对照组四次合计 6/203） |
| 每笔写字节 | 20.6–21.8 KB | **18.6 KB** |
| 写周期 | 4483–4718 µs | **3914 / 3984 µs** |
| `chain idle` | 8.0–8.7% | **6.3 / 7.1%** |
| 发射相位 deadline 等待占比 | 11.0–13.7% | **8.2 / 10.5%** |
| **总线腿占墙钟** | 35.9–36.1% | **35.8%（不动）** |

**「前车成形」的足迹**（在飞窗口内排好下一笔）：`staged ready` 占完成笔数 85–90%，
关掉时恒为 0 且逐窗闭合；`chain idle` 17.6% → 10.0%；写周期缩短。
**总线腿占比同样不动**，两臂吞吐判不出次序（合池 33.20 Mbps n=7 对 33.40 n=2，
逐秒 Mann-Whitney p = 0.081）。

**由此确立的判读规则**：上行非在飞时间的限制项不在被这两者搬动的那段时间里——
最大单项仍是「没有帧可发」（栈侧供给节奏），credit 等待里约 78% 属于旋钮够不到的保留量分支。
判断 5% 量级的改动**不能靠吞吐**（同一镜像两次开机可差 24%，且该差本身来自链路状态变化），
只能靠机制计数与阶段账。
