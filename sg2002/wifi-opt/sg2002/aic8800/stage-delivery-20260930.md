## 3. 现状读数（实板，`com6 2026-09-30_001748`，4 个 iperf3 用例）

### 3.1 停驻去向（`park_end`，76 窗逐窗闭合、八项之和 = `waits`）

| park 结束于 | 下行 | 上行 | 双向 |
| --- | ---: | ---: | ---: |
| 无发布者（到点时事件已置位，从未睡下） | 50.0% | 50.0% | 49.9% |
| 协议交帧 `tx` | 25.7% | 12.7% | 13.4% |
| 设备中断 `irq` | 22.4% | 14.0% | 14.7% |
| 截止时间 `timer` | 0.05% | 18.1% | 14.7% |
| 归还缓冲 `recycle` | 1.6% | 5.0% | 6.8% |
| 取帧 `rx` / 控制 `ctrl` / 其他 `other` | 0.2 / 0 / 0 | 0.1 / 0 / 0 | 0.4 / 0 / 0 |

`wait_kind deadline` 比 `timer` 多 5~12%（差值是「等到截止时刻才被通知」），两者不可互换。

### 3.2 credit 自选等待：上行 16.1% 墙钟

4831 ms / 30 s、7103 次、均 680 µs，次数与 `credit backoff`（7642）同量级；
与 §2.29 的三条旧读数（15~16%）吻合，是执行器侧的第三类独立记账。

### 3.3 栈侧供给

上行 82% 的 poll 开始时核心有帧、18% 哪都没有、`ring` 恒为 0；下行 85% 是「哪都没有」（只有 ACK）。
上行 `supply 4+` 占 10.4% ⇒ 协议栈是**突发式交付**，不是持续积压。

### 3.4 信道占用读数失效

77 个采样全部 `busy=0 txbusy=0`（含上行 30 Mbps 期间）。`get_sta_info` 的
`chan_time`/`chan_busy_time`/`chan_tx_busy_time` 在厂商树里**主机侧从不消费**；
厂商真正使用的是 `MM_CHANNEL_SURVEY_IND` 的 `chan_time_ms`/`chan_time_busy_ms`。
**故本轮不能判「空口是不是天花板」**；当前探针分不清「字段恒零」与「窗口不前进」，两者都印成 0。

### 3.5 上行墙钟账（30 s，窗口内读数）

| 项 | 值 |
| --- | ---: |
| 事务在飞 | 38%（写总线腿 36%、收 1%、控制 0.9%） |
| ├ 写往返 | 2515 µs/笔 = 总线腿 1951（78%）+ 主机 564 |
| └ 总线效率 | 写 89 ns/B、收 87~96 ns/B（≈ 物理底速） |
| 非在飞 | 62% |
| ├ 哪里都没有帧 | 20% |
| └ 有帧却在等 | 23%，内含 credit 等待 16.1%，余约 7% 为完成→中断→交接→再发的固有延迟 |

**搬运方式本身不可动**（每字节 96% 物理底速、`ring` 空档归零）；差距在**占空比**（38%）。

### 3.6 吞吐与链路健康

下行 27.6 / 30.5、上行 **32.0**、双向板发 29.2 / 板收 6.31 Mbps；
逐秒中位 28.3 / 30.3 / 32.6。无错误、无超时、`deferred=0`；全程 `he-su`、MCS 5~11、rssi −24~−28 dBm。
